Design study · Protected branches

Wiffletree merges into feature branches. Protected branches stay yours.

Static study for a proposed OpenSpec change. Each repository gets a list of protected branches. Its default branch on GitHub and its configured base are always on it. When the coordinator asks, Wiffletree merges a ticket’s pull request itself, but only into a branch that is not protected, only in an allowed owner’s repository, only at the reviewed commit, and only with passing checks and no conflict. Every merge into a protected branch, including the final feature branch into main, stays the human’s. The study shows (a) the protected-branches block on the Repositories page, (b) tickets and their PR line after Wiffletree merged one, and (c) the Inbox card when the review ended blocked. New parts have a red edge. Sample data is simulated.

(a) Each repository row gets a Protected branches list, collapsed to one line until opened. The lock rows cannot be removed: the repository’s default branch, which GitHub reports, and its configured base. When the base is changed, the old base stays protected only if it is also the default branch or on your list. Rows with the GitHub mark come from GitHub’s own branch protection and rulesets: Wiffletree reads them and treats them as protected too, but cannot change them. The list accepts exact names and patterns, and shows which branches on origin a pattern matches now. A pattern that cannot be read, or a name with a remote in front, is refused with the reason. In a repository whose owner is not allowed, Wiffletree merges nothing, so the list there only matters once you allow the owner.

(c) A waiver lets the coordinator accept and publish a blocked review without asking. A merge is harder to take back, so after a blocked review it always asks you, in every repository, with the waiver’s reason and the findings still open. The other conditions cannot be approved away: a protected base, an owner you have not allowed, a head that is not the reviewed one, failed checks or a conflict are refused before any card is raised.

  • Recommendations for the open questions, for the proposal to settle:
    1. Merge method: follow GitHub. Use the first method the repository allows, in the order squash, merge commit, rebase, and always pass --match-head-commit with the reviewed head. No per-repository setting until one is needed.
    2. Where the list lives: on this Mac, beside the allowed owners, the base and the checks command. It is not synced through the settings repository, so another machine cannot loosen it.
    3. GitHub’s protection: yes, as an extra guard. At each merge Wiffletree reads whether GitHub protects the base branch or a ruleset applies to it. A branch GitHub protects is protected here too. If GitHub cannot be read, nothing is merged.
    4. The ticket after a merge: Wiffletree accepts it in the same step, because merge_ticket already checks everything accept_ticket does. A merge you make on GitHub keeps today’s flow: the coordinator is told and accepts.
    5. Stacked tickets: when a ticket merges, each open ticket stacked on it takes its base. Wiffletree changes that pull request’s base on GitHub to the same branch, and the PR keeper rebases its branch where the repository is kept. A rebase that leaves the change as reviewed keeps the review; otherwise the coordinator is told. Wiffletree does not delete the merged branch.
  • Unchanged: Wiffletree does not create feature branches on GitHub (you do), and it never approves, closes or comments on a pull request. The PR keeper never merges; only merge_ticket does, and only the coordinator calls it.
  • What this does not stop. GitHub does not protect main in the Sage-Social repositories, and an agent’s shell runs with your credentials, so a shell can still run gh pr merge. This change makes Wiffletree’s own merge the only one the instructions permit, and checks every use of it.
  • The ruleset row, the Sage-Social repository and its develop base are examples, marked “Example”. Ticket names and PR numbers are drawn from this repository’s recent history and are sample data.
  • This is a static design study, not the GPUI implementation.
