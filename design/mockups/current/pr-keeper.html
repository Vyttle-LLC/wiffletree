Design study · PR keeper

Keeping open pull requests up to date

Static study for the pr-keeper OpenSpec change. Today Wiffletree watches each ticket’s pull request and tells the coordinator when it conflicts or its checks fail. With this change it can also act: rebase the branch when the base moves, let a small model try a conflict or a failed check once, and sort new comments. Watching and rebasing use no model. Every push goes through the same checked operation agents already use, and only in repositories whose owner you allowed. It never merges, approves, closes or comments. Everything here is off until you turn it on. Sample data is simulated.

Rebase when the base branch moves Plain Git, no model and no review. Waits until the base has been quiet for 2 minutes, then replaces the branch on GitHub with the rebased one (a force-push that refuses to overwrite anything Wiffletree has not seen).
Try to resolve conflicts The PR keeper’s model tries once. Its result must change only the conflicted files, pass the repository’s checks and pass a Light ▾ review before anything is pushed. If not, the try is thrown away and the coordinator is told. Needs the rebase trigger above.
Try to fix failed checks Only when the checks also fail on this machine. One try, the same gate and review, and only in files the pull request already changes.
Sort new comments Reads each new comment and sorts it: needs a change, a question, or no action. Tells the coordinator about the first two. Never replies, resolves or reacts.

Wiffletree never merges, approves, closes or comments on a pull request. The model is chosen in Models → PR keeper.

(d) The ticket’s card says what the keeper last did and why the review still stands. A rebase that leaves the change exactly as reviewed needs no new review. A fix the model made is reviewed first, and that review is recorded as one more cycle on the ticket, marked as the keeper’s. A try that is thrown away leaves no cycle, no finding and no commit on the ticket.

(e) The coordinator hears from the keeper only when something needs it: a try that was thrown away, checks it could not reproduce, comments that need a change or an answer, and commits someone else pushed. A clean rebase and a fix that passed send nothing. The messages carry fixed wording, numbers, paths and links; no comment text, title or author name is copied in.

One of these for every rebase of every pull request, each time the base moves. A card goes stale and is replaced whenever the base moves again before you answer.

(f) Where you have not allowed the owner, you said you want to be in charge before anything is made public. The recommendation is that the keeper does nothing there. The alternative keeps it on and puts every push in your Inbox.

  • What uses a model. Watching, the quiet timer, rebasing, pushing and the gate are plain code. The model runs for three things only: one try at a conflict, one try at a failed check, and sorting comments.
  • Where it works. The keeper never works in the ticket’s worktree. It rebases and fixes in its own checkout of the pull request’s head, and the ticket’s branch moves to a finished result in one step, only while the worktree is clean, unchanged and no agent is in a turn there.
  • One try per problem per head. A conflict or failed checks at a given head commit get one try. After that the coordinator has it until the head changes.
  • What it cannot stop. Agents still run with permission prompts bypassed, so an agent’s shell, the keeper’s included, can run git push with your credentials. The app checks everything it sends itself; it does not sandbox a model.
  • This is a static design study, not the GPUI implementation.
