Design study · Repository owners

Where agents may open pull requests without asking

Static study for the repository-owners OpenSpec change. Wiffletree lists the GitHub organizations and users your repositories belong to. You tick the owners you allow: there, agents may push a ticket’s branch and open and update its pull request without asking. Everywhere else, each push and each pull request waits for your approval. Wiffletree never approves, merges, closes or comments on a pull request. It shows (a) the Repositories page, (b) what you see when an agent asks in a repository whose owner you have not allowed, and (c) what happens where you have, including a review that ended blocked. Sample data is simulated.

(a) A new block sits above the repository list. It has one row for each GitHub organization or user that owns a repository in the workspace, with how many repositories it owns here and whether they are private. Nothing is ticked until you tick it. A fork is listed on its own, so ticking MHohlios does not allow a public fork under MHohlios. A repository with no GitHub remote has no box, because there is nowhere to push. Each repository row then says which rule applies to it. The owner comes from the repository’s origin remote; whether it is a fork, and whether it is private, come from GitHub.

(b) In a repository whose owner is not ticked, the agent’s request stops in your Inbox. Wiffletree writes the card, not the agent: it names the repository and whether it is public, the branch, the exact commit and that the review passed there. Approving runs that one step, for that one commit. The pull request is a second card, because it is a second thing leaving your machine, and it shows the title and description in full. Every later push to the same pull request asks again. To stop being asked for an owner, allow it on the Repositories page.

(c) In an allowed owner’s repository the same request runs with no card, and the agent gets the result as a message from Wiffletree. A review that ended blocked always asks you, in every repository. The card says so and lists the findings that are still open; in an allowed owner’s repository it is one card for the commit, and elsewhere the same notice and findings appear on each step’s card. The remaining checks cannot be approved away: the commit being pushed is the one the review looked at (or one with the same changes, such as a squash), the branch is the ticket’s own, and nothing on GitHub is overwritten that Wiffletree did not put there. There is no operation for approving, merging, closing or commenting at all.

  • What this does not stop. Agents run with their provider’s permission prompts bypassed, so an agent’s shell can still run git push or gh pr create with your credentials. This change makes the app’s own operation the only path the instructions permit and the only one that needs no shell, and it checks every use of that path. Closing the shell needs scoped credentials or a sandbox, which this change does not add.
  • Reading GitHub for this page is one read-only gh api graphql call for the whole workspace (33 repositories cost 1 rate-limit point here), repeated at most daily and when a repository is added.
  • Counts are this workspace’s, read on October 12, 2026: 34 repositories, all with a GitHub origin. Sage-Social has 29, which are 28 GitHub repositories, because two folders are clones of the same one. MHohlios has 3, Vyttle-LLC 1 and celadon-theme 1. It has no forks. The fork and the repository with no GitHub remote are examples, marked “Example”, because the design has to handle them. Which owners are allowed here is also only an example.
  • Settled with the human on October 12, 2026 (see openspec/changes/repository-owners/design.md): a fork is its own entry; owners only, with no per-repository override; merging is always the human’s; the ticket’s coordinator or its implementer calls publish_ticket; each step is approved separately; and a blocked review can be published only with the human’s approval. “Allowed” names an owner on this list. “Approve” is kept for your answer to an Inbox card.
  • This is a static design study, not the GPUI implementation.
