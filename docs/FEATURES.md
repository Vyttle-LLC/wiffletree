## Install

**The installer.** The README's one command downloads the signed and notarized app from [Releases](https://github.com/Vyttle-LLC/wiffletree/releases/latest), checks it with Gatekeeper, moves it to `/Applications` and opens it. Run it again any time to reinstall. To install somewhere else, set `WIFFLETREE_INSTALL_DIR=~/Applications`. If you prefer to do it by hand, download `Wiffletree-<version>-macos-arm64.zip`, unzip it and drag `Wiffletree.app` to Applications.

**First run.** The first time you open Wiffletree, a welcome screen lists the CLIs it found signed in and offers a model setup suggested from them. Review it on the Models page and press **Save**; no agent starts until a setup is saved. Then press **⌘N**, add a repository, and tell the coordinator what you want built.

**Updates are automatic.** The app checks hourly, downloads new versions in the background and shows a card in the sidebar with what changed. Click **Restart to update**, or quit Wiffletree from its menu bar icon. To check right away, click the version number at the bottom of the sidebar.

**The menu bar icon.** Agents keep working after you quit the app, and a menu bar icon shows how many are.

## Safety

Agents run with their provider's permission prompts bypassed so they can work unattended. Add only repositories you are comfortable letting them change.

Wiffletree itself pushes a ticket's branch and opens its pull request only through its own checked operation: without asking in repositories whose GitHub owner you allow, and after your approval everywhere else. It merges a ticket's pull request only through its own checked merge, which the coordinator asks for, only in those repositories and only into a branch that is not protected. It never merges into a protected branch and never approves, closes or comments on a ticket's pull request.

A Space's repository is different: Wiffletree pushes straight to its `main`, with no pull request and no review. Every log entry, issue change, Space edit and compile is a commit there, which is what makes a Space shared. That model has risks you accept by using it:

- **Anyone with write access can change anything** in the repository: the Space's instructions, its issues, its wiki and its log entries. Give write access only to people you would let do that.
- **A slip stays in history.** Each Mac scans what it pushes and holds back a file that fails, but a slip made outside Wiffletree reaches `main`. Each Mac scans what it pulls and raises an alert, and removing the text adds a new commit; the old text stays in Git history until someone cleans it, as [How to clean history](clean-history.md) explains.
- **Every issue change is a commit,** so the repository's history grows with each edit, comment and move, and keeps them for good.
- **No volunteer means no wiki updates.** Log entries still land, but the wiki changes only when a Mac that compiles runs. The Brains page says when no Mac does.
- **Protect history needs an admin.** It adds a GitHub ruleset that blocks force-pushes and deleting `main`; without an admin the warning stays, and someone can rewrite history.

If you turn on the PR keeper, Wiffletree also rebases a ticket's open pull request and replaces the branch on GitHub, which changes every commit id on the pull request: whenever its base moves with "Keep it rebased" ticked, or, with only "Keep it free of conflicts and failed checks" ticked, only when the pull request conflicts or its checks fail.

Agents can still run any command on your Mac with your credentials. Wiffletree's guard puts its own `git` and `gh` first in every agent's shell: they refuse pull request writes, every other GitHub write and every push but an implementer's to its own ticket's branch, in a repository whose owner you allow and before its pull request is open. It is a guardrail, not a sandbox: a full path to `git` or `gh`, or a call to GitHub with your token, still gets through. That includes the PR keeper's model, which gets one try at a conflict or at failed checks when "Keep it free of conflicts and failed checks" is ticked: Wiffletree checks only what the try leaves behind, which files changed and whether your checks command passes, and has that reviewed before pushing it. Your checks command runs as you wrote it.

## Projects and the coordinator

**Projects are outcomes, not repositories.** A project is a feature, a bug or any goal you want reached. Repositories are attached to it, and one repository can serve many projects at once.

**You talk to one coordinator.** Each project has a coordinator that owns the goal and the conversation with you. It plans, asks you the questions that matter and reports the result. You do not have to manage the agents underneath it.

**Blocked is not the same as needs-you.** Workers report blockers to the coordinator, which resolves most of them. Only the coordinator escalates to you, and it gathers its questions in one Inbox so you answer them once.

**Projects can have a parent.** A project a coordinator creates is a child of its project, or its sibling under the same parent, one level deep and in the same Space. Parent and child coordinators can message each other, and a child's reports reach its parent's coordinator; siblings cannot talk. You file projects with **Move under…** in the project menu, and you close a parent only once its children are closed. Mark a project that never finishes, such as Platform, as **Standing**.

**Software does the routine work; models do the thinking.** Git state, status, polling and usage tracking are ordinary deterministic code. Models are woken only for decisions that need reasoning, so coordinators sleep between events instead of polling.

**You can see how far along the work is.** The app derives the progress bars from each agent's checklist, each ticket's stage and its review results. The coordinator's strip shows the project's phase, one segment per ticket and how many tickets are accepted. The Agents panel, opened from any of the project's conversations, lists every ticket with its agents, their models and their progress, and marks an agent that is stuck.

## Tickets

**Each ticket is its own workspace.** The coordinator breaks the work into tickets, one repository each, with its own branch and worktree. It assigns an implementer, then verifies with one call that runs every tester and reviewer in the chosen review level at once on the same commit, and accepts the result.

**Tickets are small, isolated and tested by someone else.** Every ticket gets its own Git worktree and branch. An implementer builds it, and a separate tester checks it against the acceptance criteria. "The turn ended" never counts as "it works."

**Messages are durable.** Agents talk through the app's message queue, not by typing into each other's terminals. Every message is saved before it is acknowledged, and an idle recipient wakes the moment one arrives. After a restart, each agent resumes its exact provider session, and the app never silently retries work that might have had side effects.

## Reviews

**You decide how thorough a review is.** A review level is a named set of testers and reviewers, with a line telling the coordinator when to use it. A full review can be a ticket's only review. A re-check, such as the suggested "Light", runs only on a ticket whose last review passed, for example after a rebase or a small fix. You also cap the rounds in one review and the full reviews per ticket.

**Findings stay on the ticket.** Each tester and reviewer, a verifier, reports structured findings with a location, a trigger and evidence. A blocking finding goes back to the implementer, and only the verifiers that failed check again in the next round. Every finding is kept in the ticket's decision ledger, which you can read in the Tickets panel and which the next review receives. The coordinator triages what is left open. When a ticket reaches the cap on full reviews, the coordinator is told to read whatever no review checked and then judge the ticket itself, with a waiver.

## UI evaluators

**A coordinator can start a blind UI evaluator.** It writes a prompt to `prompt.md` in a run folder of its own and calls `start_evaluation` with the exact provider, model and effort. The evaluator is a fresh session that gets that prompt and nothing else: no shell, web, repository, brain, memory or workspace tools, and none of your CLAUDE.md, AGENTS.md, settings, skills or MCP servers. Claude and Codex themselves hold it to reading and writing its run folder, and no Wiffletree variable reaches it. Codex runs from a home of Wiffletree's that holds only a link to your sign-in, because `--ignore-user-config` alone still loads `~/.codex/AGENTS.md`.

**It runs on the model it was given, or not at all.** A model the provider does not offer, an effort the model does not offer or a provider that is not signed in is refused at start. Give a full model ID, such as `claude-opus-5-5`, to pin one model: if the provider names another when the run starts, the run fails. An alias such as `opus` can move to a newer model, so the run records which model it got. At a usage limit an app-only run waits for the reset (a full-desktop run ends instead, below); it never moves to another model, and Who runs what does not apply.

**You allow evaluators per project.** They are off until you choose. The first run in a project puts a card in your Inbox, **Allow UI evaluators in this project?**, naming the models the coordinator asked for and where their folders are: App only, Full desktop or Not in this project, or Ask me later. Change it any time on the project's menu › UI evaluators. No agent can change your choice, and closing the project turns it off.

**A full-desktop run uses only the apps it names, and only after you press Start.** The coordinator names the apps by bundle ID, such as `com.apple.calculator`; nothing else is ever allowed, and the Start card calls out Wiffletree, terminals, System Settings and Finder when they are named. Runs take turns at the screen across every project. When one reaches the front, your Inbox shows **Ready to use your screen**, with the run's model, its apps and how many runs wait after it, and **Start now**, **Later** and **Skip these runs**; it has no Dismiss, since the run holds the screen. Nothing touches the screen before Start now. While it runs, a red band across the main window says **An evaluator is using this Mac**, with its model, its place among the waiting runs, the time so far and Stop. The run works through Wiffletree Evaluator, a helper app bundled with Wiffletree that alone holds the Screen Recording and Accessibility permissions, so your agents never get them. Its screenshots show only the named apps' windows; a click, scroll or drag goes through only over one of their windows, and keys and text only while one of them is frontmost. A small panel floats above every window for the whole run, top right unless you drag it to another corner: it shows the model, the allowed apps and the time, and its Stop, Esc anywhere, or Stop on the "Evaluator using this Mac" menu bar item stops the run at once. The evaluator never sees the panel or reaches it. A run whose helper lacks a permission fails before it starts, naming the System Settings pane to open. **Settings › Screen control** reads the helper's two permissions live, from the copy Wiffletree installs in its data folder, never the one inside Wiffletree.app, which macOS would check as Wiffletree. Each missing one has **Open System Settings…**, which opens its exact privacy pane. **Request access** asks macOS for both and waits up to two minutes for your answer; **Show in Finder** reveals the installed copy for the pane's + button; **Check again** reads them again. App-only runs need neither. A full-desktop run that reaches its provider's usage limit ends rather than wait, so it never takes the screen again without your Start. Claude and Codex both run it through Wiffletree's own `desktop` driver; neither provider's built-in computer use is used.

**An app-only run drives its own test copy of the app.** The coordinator names the copy: its executable, its arguments with a test data folder of its own (`--data-dir`), and the variables it needs, such as provider stubs and `GH_CONFIG_DIR`. It creates the data folder first. Wiffletree starts it for the run with `--automation-socket` on a socket of the run's own, from a clean environment with no Wiffletree session variable or token, and with `WORKSPACE_SKIP_LOGIN_ENV` set so the copy's host keeps the given `PATH` and stubs instead of the login shell's. A run fails, saying why, if the copy's socket does not answer. When the run ends or is stopped, the copy and everything it started stop. Two runs that have not ended cannot share a data folder, and none may use Wiffletree's own. The evaluator's only MCP server is the app driver: screenshot, click, double-click, right-click, move, type, key, scroll, drag, resize and window size, in window points that match its screenshots, and sample pixels. Sample pixels, which the full-desktop driver has too, reads up to 64 points of a screenshot the evaluator saved and returns each one's exact sRGB hex and luminance, and the WCAG contrast ratio of up to 64 pairs with whether each passes AA; it reads only that file in the run folder. It reaches that copy's window and no other app. The app captures its own window at one pixel per point or at the display's scale, which needs no Screen Recording permission, and the driver saves each screenshot in the run folder under the name the evaluator gives.

**The coordinator sees only that a run ended.** When a run ends, its coordinator gets one message with the run's id, state, model, folder and duration, and reads the report from the folder. It never sees the transcript, which Wiffletree keeps for you. `list_evaluations` shows the project's runs and `stop_evaluation` stops one.

**You watch runs beside the tickets.** The Agents panel lists a project's runs in its Evaluations group, apart from every ticket: each with its mode, pinned model and state (Queued, Waiting, Running, Finished, Failed or Stopped), and how long it has run, what it waits for, its place in line for the screen, or when it ended and why. The sidebar says "Evaluating · 1 running" under the project. A run's page shows its pinned model, its mode with the app copy or the apps it may use, its folder with Show in Finder, who started it and what it has, and its latest steps from the stored transcript, a screenshot's thumbnail beside each screenshot it took. Only you see them. Stop is on the page, and on the quiet band each app-only run shows across the main window with Open run.

## Spaces

**Every project belongs to a Space.** A Space, such as Sage, Vyttle or Personal, answers "where does this go?". It has a description, additions to every role's instructions, the code repositories it covers and its own rows in Who runs what. New project starts in the Space you used last, with that Space's repositories ticked; a repository the Space lists that is not cloned on this Mac is shown as not cloned here. The Repositories page groups repositories by Space, with one chip per Space on each row, and a repository may be in several Spaces or none. Adding a repository suggests a Space from its GitHub owner, which only suggests. A Space's page chooses its repositories from a tree of the folders that hold them, and a Space can follow root folders, so a repository found there later joins it by itself. You create, edit and remove Spaces on the Spaces page in the sidebar, which is Settings › Spaces, and only you change which repositories a Space lists or which folders it follows: no agent tool can.

**Repositories have an app and a layer.** On a Space's page, each code repository has an App and a Layer menu of the Space's own values, with None and a field to type a new value, which every repository in the Space can then use. Removing a value says which repositories have it first, and clears it from them. Adding a repository suggests the tags of the one whose name starts with the most of the same hyphen-separated words, such as `palette-api` for `palette-cli`, and tags it only when you choose Use; a repository a followed folder adds stays untagged. Each Space keeps its own tags, saved in its `space.yaml` with Save. A project's apps and layers are those of the repositories its tickets work in, open or finished: a project with tickets but no app is "no app", and one with no tickets is "not started". Its coordinator sees them too.

**A coordinator asks for a repository by name.** When a project needs a repository it does not use, its coordinator asks with the reason, and you answer one card in the Inbox, which shows the Spaces that list it and this project's Space. **Add to this project** adds it to that one project, and a folder the coordinator just cloned to the workspace as well. No Space's list changes, the project stays in its Space, and the coordinator can use the repository at once.

**One repository holds what a Space shares.** Each Space names one repository and a folder in it, `wiffletree/` unless you choose another. The folder holds the Space's definition in `spaces/<space>/space.yaml`, its issues in `issues/` with `wiffletree-issues.yaml`, one prefix such as SAGE, and its brain in `second-brain/`. Every Space has issues, logs and a wiki; there is nothing to turn on. Spaces in one repository share its folder, issues and brain. Files outside the folder are the repository's own, and Wiffletree never commits them.

**New Space.** One form takes the name, the description, the repository and the prefix. A local repository lives in the data folder with no remote and is never pushed or scanned. For a team, name a private GitHub repository, or press Create to have `gh` make one, private. A repository that already holds a folder fixes the folder, prefix and compile time from it. The repository checks say who can read it, whether Wiffletree can push to `main` directly, which it needs, as GitHub's rulesets and branch protection say, and whether history is protected. Protect history adds a GitHub ruleset that blocks force-pushes and deleting `main`, which needs an admin; without it the page keeps its warning.

**The Repository box.** A Space's page has one Repository box: the repository and folder, the last sync, the issue count, who compiles its wiki with Compile on this Mac, and Sync now, Import from Linear…, Bring in a brain…, Move… and, for a repository whose files sit at its root, Move into `wiffletree/`, which moves them in one commit and leaves a short stub at each old file for an older Wiffletree. Move… puts the folder in another repository, from this Mac to GitHub, from GitHub to this Mac or to another GitHub repository, with every Space in it, its issues, logs and wiki (when the target is already a tracker, the logs and wiki stay behind in the old repository): you see who can read the target and what moves first, nothing is deleted, and old local storage goes to the backups folder with its Git history.

**Joining.** A teammate adds a shared Space with Add Space → From a repository: Wiffletree finds the folder, lists its Spaces, and asks only where each code repository is cloned on this Mac, or leaves it missing. Compiling the wiki on this Mac too, Also on this Mac, is off until you tick it.

**Who can read and change it.** Everyone who can read the repository can read the Space, its issues and its brain, and the Space's page says who that is. Anyone who can push to it can change the Space's instructions for everyone in it, and edit its issues, wiki and log entries; see [Safety](#safety). Edits to a shared Space are commits that sync like settings, and an edit made on two Macs, or outside Wiffletree, pauses until you choose. Before pushing anything in the folder, Wiffletree runs a personal-data and a secret scan on your Mac. A file that fails, or that a check cannot scan, for example because gitleaks is missing, stays on your Mac with a card naming the file, the check and the rule, never the text it matched.

## Second brain

A brain keeps what a team has decided and learned, so the next agent starts from it. It is the `second-brain/` folder of a Space's repository: log entries under `logs/<repository>/`, and the wiki, `STATUS.md` and `notes/`. The Brains page in the sidebar lists each wiki this Mac knows, with the Spaces that use it and the Macs that compile it. See [the scan checks' README](../gate/README.md) for the checks and the entry fixtures.

**Agents log as they work.** The coordinator, implementers and the Assistant record decisions and observations with the `log_work` tool, and each entry is one file under `logs/<repository>/`, or `logs/assistant/` for the Assistant's. Testers, reviewers, the PR keeper, issue threads and loop runs do not log. When an implementer reports ready for testing, or a ticket is accepted or published, an agent that has not logged since its last milestone is asked for one short entry.

**Entries land straight in.** Each entry is scanned on your Mac and pushed to `main` a couple of seconds after the last one, several in one commit; in a local repository it is committed at once. An entry offline waits and lands when GitHub is back. An entry that fails a scan is held on your Mac and never pushed, with a card on the project, or on the Brains page, that names the check and rule but never the text: Edit it scans it again, Discard drops it, and Not sensitive, for a personal-data finding only, lands it with a marker that says why.

**Anyone can read it.** Agents ask the brain with the read-only `query_brain` tool, which walks `STATUS.md`, the note index, the top notes and then the log entries. A project's Memory panel shows its brain, entries held on this Mac, open conflicts and recent entries. The brain browser has four views, for a project or for the whole brain: Status, Wiki, Logs and Conflicts. Wiki shows each note with its sources and backlinks, and an issue ID the tracker knows, such as VYT-42, opens the issue. ⌘K searches one brain.

**Compile turns logs into the wiki.** Any Mac can volunteer to compile a wiki, on the Brains page or when it creates or joins a Space. Every volunteer is due at the wiki's compile time, set in `wiffletree-issues.yaml`, or when you press Run now. The first awake claims the run on a `wiffletree-compile-claim` branch, the others stand by, and a claim a crashed Mac left expires after an hour. A Mac out of quota, or with no model on the Brain compiler row, claims nothing. A run first checks each pending entry's commit or pull request, through GitHub when the repository is not cloned there, and marks the entry verified, claimed or unverified. A run with nothing pending makes no model call. The model then folds entries into a page per product and into `STATUS.md`, and it can change only `notes/**` and `STATUS.md`. What conflicts with an existing note becomes a card in the Inbox, on the Brains page or in the Conflicts view, with a recommended ruling; your ruling is written back as a decision entry, and the next compile folds it in. Wiffletree checks and scans the run's changes and lands them on `main` as one commit. With no volunteer, entries keep landing but the wiki stops changing, and the Brains page says so.

**Each Mac scans what it pulls.** A slip made outside Wiffletree, such as an edit on GitHub, reaches `main` without a scan. Each Mac scans every commit it pulls into the folder and raises one Inbox card per file and rule, naming who pushed it and never the text, with Open the file, Not sensitive and [How to clean history](clean-history.md). The card closes by itself when the text is gone from the file on `main`.

**Bring in a brain.** A brain kept elsewhere by an earlier release, or by hand, comes into a Space's folder with Bring in a brain… on its Repository box. It reads the brain's clone on this Mac, so entries never pushed come too, and writes nothing there. It brings every entry and wiki page, lists what it skips, keeps what was already compiled as compiled, and running it again adds nothing.

## Issues

**Issues are your team's shared backlog.** The Issues page, in the sidebar before Repositories, lists the issues of every Space as a list grouped by state or as a board, with filters for Space, open, assignee, priority, label and repository, and a search over titles, descriptions and comments. Drag a card to move it; open an issue to read its description and timeline, comment, and change its state, priority or assignee. An issue changed since you last opened it carries a dot, and the sidebar counts them. Unread marks and filters stay on your Mac. Each issue is a folder of plain files in its Space's repository: a private GitHub repository your team chooses, or a local one that stays on your Mac. Choosing the GitHub repository is what lets Wiffletree push issues to it. A new issue there has a temporary ID until it is pushed and numbered. Issue text is scanned for personal data and secrets before it is pushed, but know the limits: issues stay in Git history for good, even after you delete or edit them; everyone who can read the repository can read them, including, for an organization's repository, its members; anyone who can push can edit any issue; and an agent's shell can still push to the repository with your credentials, though sync does not spread an edit it did not make. Teammates without Wiffletree can add and edit issues through GitHub, and an issue file Wiffletree cannot read is shown as written. Tickets, agents, projects and conversations are never written to a tracker: an issue is not a ticket.

**Issues connect to work.** Start project from issue creates a project named after the issue, in its Space, and links the two. A Space's Repository box also offers Import from Linear…, which copies a Linear team's issues into the tracker and changes nothing in Linear.

**Ask the assistant about issues; you apply what it suggests.** Ask the assistant on an issue opens that issue's thread beside it, and on the Issues page a thread with the tracker's list attached, in the Space the page is filtered to, or the one you last used for a new project. A tracker two Spaces share has a separate thread in each, and a thread never changes its Space. An issue thread reads only its Space's tracker, and its Space's repositories on this Mac at their base branch, read-only and bounded. Because issue text is written by others, it has no web search or fetch and none of its Space's sources, so it has no way to send what it read off your Mac, and a notice names who wrote what it reads. It cannot link an issue to work, create a ticket or log to the brain. Every change it suggests is a card: an edit as a diff, a comment, a split, a duplicate link or a new issue, which any thread may propose in its own Space. Nothing reaches the tracker until you choose Apply, which writes as you; Edit changes the proposal's text first, and Discard writes nothing. A card whose issue changed since says who changed it and shows the change against the current version. A comment you apply reads "Assistant for ‹you›" on every Mac, and an issue you file from a card says the assistant filed it for you.

## Assistant, loops and Boards

**One conversation for everything.** The Assistant, pinned above Projects in the sidebar under the name you give it in Settings, is one conversation across every Space, in one chat with no tabs. It is one Claude or Codex session that this Mac owns, started on your first message and resumed after, on the model this Mac's Assistant row in Who runs what picks, or the one you choose in the composer, which applies from the next turn and keeps the session's provider. It runs one turn at a time: whatever arrives during a turn, your messages first and then reports from its work, reaches it together at the next. Stop ends a running turn, and a turn that has run 30 minutes shows "Working 30 min" with Stop in the chat and on the sidebar row, with nothing in the Inbox. The Assistant decides which Space each request belongs to, and asks with one button per likely Space only when it cannot tell. The composer's Space chip reads "Space · auto" until you pick one; a message sent with a Space picked holds that turn's tools to it. The conversation stays in this Mac's database and never syncs. Threads from before the one conversation are listed read-only under History, searchable and filterable by Space; deleting one asks first, and a message the old router held unsent waits in the composer as your draft.

**It acts on this Mac; code changes go through work.** The line under the composer says so: "Can act on this Mac · repositories change through work". The Assistant runs in its provider's YOLO mode, as a coordinator does, in `assistant/workspace/` in the data folder. It runs commands, reads and writes files anywhere you can, searches and fetches the web, and reads, builds and tests every repository, ticket worktree and project folder. A change to a repository added to Wiffletree lands through work instead, reviewed and published as a pull request, because edits from two places collide with the implementer's and reviewed pull requests are what Wiffletree guarantees. The Assistant's instructions say so; the host does not enforce it.

**Work starts without project upkeep.** When a request needs code, the Assistant starts work in the Space at once, with no brief for you to confirm: a project whose coordinator reports to the Assistant. The chat shows a work card with its title, Space, stage and pull requests, with Stop and Open details, which opens the project's own view with Back to chat. A small, clear change takes the fast path: one implementer and the lightest review the Space allows. Assistant work is not listed under Projects. When you write about running work, the Assistant passes your message on and the chat tags it "→ ‹work›" with Change, which sends it to other running work or to just the Assistant and tells the first work it was moved. Stop on a card stops every turn of that work and moves it to Done recently as Stopped. The Assistant reads its work's plan, tickets, reviews, findings, reports and worktrees directly, so "why isn't it done?" gets an answer without waiting for a report.

**Coordinators ask the Assistant; it asks you only what is yours.** Reports, questions and check-ins from its work's coordinators go to the Assistant, never to the Inbox. It answers what it can and brings you real decisions as cards: the question, its recommendation, one button per option and a free answer. Approvals only you can give, such as publishing outside the allowed owners, a merge after a blocked review or a protected branch, stay in the Inbox and also show in the chat; answering in either place settles both. A rail beside the chat lists Needs you (decision, approval and action cards, failed or unstarted loop runs and outputs waiting for approval), Running, Loops and Done recently (work of the last 7 days, with its pull requests), and the sidebar row shows a working mark and the Needs you count.

**It keeps issues, outputs and notes for you.** The Assistant reads every Space's tracker and files, edits and comments at once, as you, marked "Assistant for ‹you›", and the chat links to what it wrote. It saves files to Boards in a Space, kept only on this Mac; suggests a new Space as a card, which you create yourself; and reads a Space's brain with `query_brain` and, when you ask it to remember something, logs one entry there under `logs/assistant/`.

**Other apps through Space sources.** The Assistant reaches mail, calendars, trackers and other apps only through the sources a Space lists: MCP servers configured for Claude or Codex, command-line tools you installed and signed in to, and, on Claude, claude.ai connectors you connected, such as `claude.ai Gmail`. Wiffletree builds no connector and runs no app sign-in. Each source lists read tools or commands, and act ones, which send, post, create, change or delete. Add source on a Space's page lists the MCP servers configured for Claude and Codex and the installed gh, linctl, sentry-cli and aws, starts the one you pick to list its tools with a suggested read or act kind for each, and, when it fails, shows the server's own sign-in instructions with Try again. It does not list claude.ai connectors yet: name one in the Space's `space.yaml` sources as `claude mcp list` shows it. Reading is free: the Assistant is offered each source's read tools and nothing else, and runs a command-line source's read commands through Wiffletree. On Codex a claude.ai connector is unavailable, and the Assistant's list of Spaces says so.

**Acting in an app shows a card first.** Anything that sends, posts, creates, changes or deletes in another app is an action card: the app, the target and the exact content, with Run and Decline, counted under Needs you. Nothing happens until you press Run, and the result or error shows on the card. Mark an act on a source Do without asking, such as creating a calendar hold, and it runs at once with a done card instead. Wiffletree calls a command-line MCP server's act tool itself. An act on a server reached by URL, or on a claude.ai connector, whose sign-in only Claude holds, runs through a short Claude run offered only that one tool, with every built-in tool off and none of your Claude settings: a hook refuses every call but the card's exact one, which goes through at most once; Wiffletree stops the run at any other call and fails the card, and keeps only the tool's result. Such acts need the Assistant on Claude; on Codex they are refused. A run cut off after its call went through says so and asks you to check the app.

**Text written by others never acts.** Emails, invites, issues, web pages, files and reports from work are context, not instructions. A turn is held when you did not start it with a message, when a report, a loop's result or a Wiffletree notice arrived beside your message, or when, before acting, it read a source, an issue, a brain, a work item's status, the web or a report. In a held turn every act, Do without asking included, waits on a card that names what the turn read, and every loop change waits on a loop card with Apply. Two rules are instructions only, because the Assistant has a shell: it never runs a source's command-line tool or calls an app itself instead of asking with a card, and it never edits a repository added to Wiffletree instead of starting work. An MCP source's act tools are held by Wiffletree itself, since the Assistant's provider is never offered them.

**Recurring work is a loop.** Ask for something recurring, such as a brief every weekday at 7, and the Assistant saves a loop at once and shows a card: what it made or changed, the schedule in words with its next run, and each source with its read tools or commands, with Undo, Edit and Run now. Undo restores the loop as it was before that change, until it changes again. In a held turn the change waits on a loop card for your Apply, so a brain note, an email or a report cannot create a schedule. A loop only reads: a command-line source can be only gh, linctl, sentry-cli or aws, and only their read commands on Wiffletree's short list; an MCP source offers only its read tools; a server reached by URL is refused; and a loop never acts, whatever a source's Do without asking marks say. The Loops page, opened from the rail, lists every Space's loops, and each loop's page is where you pause, resume, run, edit or delete one. Each run is a fresh read-only run in the loop's Space, on the Job row, offered only its recipe's sources, and saves its result as a file kept at the same place each time, as a new version. Before a run, Wiffletree checks each source is installed and signed in, and a run with one missing does not start and says how to fix it. A loop with a command-line source or a claude.ai connector runs only on Claude, which can hold it to its listed reads; Codex cannot yet. Loops run only while Wiffletree runs and never wake your Mac: missed runs come back as one catch-up run, and the Loops page offers Start Wiffletree at login. A run that has gone 30 minutes shows on the Assistant's row and on its loop's page with Stop, and one that failed or did not start counts under Needs you until you open its loop.

**Boards keeps what the Assistant and loops save.** Boards, pinned under the Assistant, lists every output with its Space, the loop that wrote it or "From a thread" for one the Assistant or an issue thread saved, when it last changed, a preview and where it is kept: "Shared in ‹Space›", or "Only on this Mac". A loop's output says Stale when two of its scheduled runs passed without a new version, and a shared loop's names the Mac that runs it. Filter by Space and loop, or search titles; its Jobs button opens the Loops page. Markdown opens in Wiffletree; HTML opens in an embedded web view that runs its scripts but cannot reach the network, other files, or navigate away, and a link offers Open in browser instead; images and PDFs open in Quick Look; anything else opens in its default app. The picker lists the latest first, then the history, a Git commit for each push and, for a shared loop's output, the saves replaced before a push, marked as only on this Mac; picking an earlier one shows it without changing the latest. An output only on this Mac offers Share to Space…, which copies it into that Space's repository after saying who can read it. No thread, Assistant turn or loop moves an output.

**A shared loop runs on one Mac, or on everyone's.** In a Space stored on GitHub, a loop is "One runner, shared result" unless you choose "Everyone runs their own". A one-runner loop, such as a release dashboard, runs only on its runner's Mac: the Mac that saved it, until a member chooses Take over running, which commits their Mac as the runner. Every other member's Boards shows the runner's latest output with "Runs on ‹name›'s Mac", and Stale once two of its scheduled runs pass without a new version. Nothing a loop writes is pushed until its runner approves it: its first output, and its first after anyone changes its prompt or sources, waits on the runner's Boards as "Waiting for your approval", with Share and Keep private, which leaves it only on that Mac. The approval is kept on the runner's Mac and never in the repository, and a member who takes over approves their own first output. An "Everyone runs their own" loop is a template each member's Mac runs with that member's own sign-ins, and its results stay on that Mac.

**Who can change a shared loop's instructions.** Anyone who can push to a Space's repository can change its loops' prompts and sources and the Space's instructions, for every member. The runner's approval of each changed prompt or source list is what keeps a changed loop from pushing what it read, and an edit made outside Wiffletree pauses until you choose. A loop is saved or changed only by the app or by an Assistant turn that is not held; no loop run, note or file can save, enable, take over or approve one, only the app takes over or approves, and a run's shell is held to its listed read commands. A project agent's shell is not sandboxed, though. It runs as you, so it can still write the storage clone in the data folder and push to the repository with your credentials, as it can for the settings repository. Sync does not spread an edit it did not make: such an edit waits for you on that Mac.

## Models and usage

**Any model can play any role, and you decide who runs what.** Claude can coordinate Codex implementers, and Codex can coordinate Claude. On the Models page, one table says who runs each job (the coordinator, implementers, testers, each reviewer, the PR keeper, the assistant, loop runs on the Job row and the brain compiler): a first choice, a choice for when that subscription runs low, and optionally a lighter line for small work. A Space can override any row but Brain compiler for the work in it. Wiffletree moves a job to its next choice when the first choice's subscription passes a threshold you set, 95% by default, and when every choice is past it, waits for the earliest reset; it never buys more. A reviewer's row can say skip instead, and then a review goes ahead without that reviewer and says so. By default the Claude and Codex reviewers wait rather than switch, so a second opinion stays a second opinion. The coordinator never picks models: it asks for a job, and for small work when it fits, and each agent shows why it runs where it does, just above the message box, such as "Started on Codex: Claude's weekly limit was at 96%". A running agent never switches provider. You can still change the model of any single agent yourself.

**Usage and limits stay in view.** The sidebar shows each provider's 5-hour and weekly limits, and the Usage page puts both accounts side by side. Those percentages come only from the providers' own telemetry: the Codex app server, and the rate-limit events Claude sends during live turns, so a Claude window reads **Unavailable** when Claude reports no percentage. Wiffletree never scrapes account pages or spends tokens to check. Below the limits, it charts the tokens its agents used by day and ranks them by coordinator, with project and provider filters.

**You can see what fills an agent's context.** Each agent's Overview has a Context card that shows how full its context window is and with what, measured after every turn without a model call. Claude reports its own categories; for Codex they are estimates. **Compact…** on the same card replaces a Claude or Codex agent's conversation with a summary when you choose, and for Claude you can say what to keep.

## Behaviors and skills

**You can change how agents work, not what they may do.** The Behaviors page, after Models in the sidebar, is the one place for it. A scope bar picks the Workspace, which is you on every Mac, a Space, or one of that Space's repositories. For each role it lists the Behaviors, named choices such as Review depth or Publishing, each with its switch or pick, a chip naming where its value comes from (Stock, Workspace, the Space or the repository, or "Set here") and Reset to what the scope inherits. A Behavior a scope can't set shows its value read-only, and a Space or repository is offered only stricter Review depth and Publishing. A Space and a repository each have their own additions, free text after the Behaviors for every role in the Space, or for that repository's tickets in that Space. At the Workspace, a role's additions are its skill's own rules, and Advanced holds the five skills: Coordinating, Implementing, Reviewing, Keeping a PR and Assisting, for the Assistant's conversation, issue threads and loop runs. Each is a stock text bundled with Wiffletree, and you can add your own rules after it. Agents are told that your rules win where the two disagree. A saved change applies from each agent's next turn. A Codex agent gets it from its next new session, because a resumed Codex session keeps the instructions it started with.

**You can rewrite a skill and keep updates.** You can also rewrite the stock text itself, after a confirmation: your rewrite is sent in place of it. When a release brings a new version of a skill you rewrote, Wiffletree merges the update into your rewrite on its own, paragraph by paragraph, and leaves a note on the skill's page with Review changes, which shows each change before and after, and Undo, which puts back exactly what you had. Where you also changed a passage the update changes, the PR keeper's Claude model merges just that passage; with no such model, you choose the update's wording or yours on the skill's page. You are asked only when the model finds that the two wordings want different things: the question waits at the top of every project's Inbox and on the skill's page, and answering it on one Mac settles it on all of them. With a settings repository, one Mac merges for all of them. Until a merge applies, your rewrite keeps running as written, and the skill is marked out of date, with a dot on the Behaviors row and on Advanced, and what changed line by line; you can merge it in, mark it up to date or reset it. Reset to stock removes your rules or rewrite after asking, and a skill's History lists every change, newest first, with View and Restore, so nothing you wrote is lost.

**Authority is not in the text.** Every agent also gets a fixed core that you can read there but not edit: its workspace tools, how it reports, and the rules the app enforces whatever a skill says. Each skill's page lists what the app enforces and what the text decides. An agent's shell is not sandboxed: the guard refuses its pushes and GitHub writes, but a full path to `git` or `gh` still runs with your credentials, and it can write the skills folder in the data folder, as it can write the settings file.

## Pull requests

**Humans own integration.** Agents deliver tested branches. An implementer may push its own ticket's branch to save work until its pull request is open, which that push never opens; from then on only Wiffletree pushes the branch, after a review. And a coordinator that needs a new branch on origin, such as a feature branch for its tickets, has Wiffletree create it. Once a ticket's review has ended, Wiffletree pushes its branch and opens its pull request itself: without asking for the GitHub owners you allow on the Repositories page, and only after you approve each step everywhere else. Each repository on the Repositories page has a list of protected branches: its default branch on GitHub and its base are always on it, you add names and patterns such as `release/*`, and branches GitHub protects count too. When the coordinator asks, Wiffletree merges a ticket's pull request into any other branch, such as a feature branch, in a repository whose owner you allow, but only at the reviewed commit, with passing checks or none and no conflict, and the merge accepts the ticket. After a review that ended blocked it asks you first, on an Inbox card. You merge into protected branches, including a feature branch into `main`: Wiffletree refuses whoever asks. It never approves, closes or comments on a ticket's pull request.

**The PR keeper keeps pull requests current, if you ask it to.** It is off until you tick it on the Repositories page, and it acts only in repositories that open pull requests without asking. Two rows are independent, and either can be on alone: "Keep it free of conflicts and failed checks" rebases a pull request only when it conflicts or its checks fail, then tries once to fix it, and "Keep it rebased" also rebases every time the base moves. Once a pull request's base has been quiet for a couple of minutes, Wiffletree rebases the branch itself, with no model and no review, and replaces the branch on GitHub with a lease, only when the rebased change is the same as the reviewed one. Every commit id on the pull request changes.

A rebase whose patch changed, because the base moved lines the change touches, is pushed only with "Keep it free of conflicts and failed checks" ticked, a re-check level chosen for it and a checks command on the repository's row: the command, such as `cargo test`, runs on the rebased commit, stopped after its limit (20 minutes unless you set 1–120), then the commit is reviewed at that level before it is pushed. If either fails, nothing is pushed, the branch is left as it was before the rebase and the coordinator is told.

A rebase that conflicts gets one try by the PR keeper's model at each pull request head, with the same settings and a PR keeper model in Models → Who runs what. The model works in the keeper's own checkout, never the ticket's worktree, and its result is thrown away unless it changes only the files Git could not merge, passes the checks and passes the review; only then is it pushed. A try that is thrown away leaves the branch and the ticket's review as they were, and the coordinator is told why. The pull request's line reads "keeper resolving" while the try runs and "with the coordinator" after one was thrown away.

The same setting covers failed checks: a pull request whose checks failed on GitHub gets one try the same way, once no rebase is due for it: Wiffletree first runs your checks command on its head, and if it passes here, no model runs and the coordinator is told the failure could not be reproduced. Otherwise the model's fix must add commits on top of the head, change only files the pull request already changes and pass the same checks and review; the line reads "keeper fixing" meanwhile. Without all of these, a changed patch, a conflict or failed checks are left to the coordinator.

With "Sort new comments" ticked and a Claude model in the PR keeper's row, it also sorts new comments from people who can push to the repository into needs a change, a question or no action, with a model run that has every tool and hook turned off, and sends the coordinator links to those that need something, never their text. It never replies, resolves or reacts on GitHub. It works only while Wiffletree is running.

## Settings sync

**Your settings can follow you to every Mac.** In Settings, name a private GitHub repository that you created, empty or already used by your other Mac. Wiffletree then keeps the skills with your rules, rewrites and their history, the review settings, the model notes, the switch threshold, the check-in thresholds and the PR keeper's triggers the same on every Mac that names it. It also shares the assistant's name and the PR keeper's quiet period and review level. It pulls at launch and every 5 minutes and pushes a few seconds after you change something, with no model. What belongs to one Mac stays there: who runs each job, the PR keeper's model included, the workspace folder, the owners allowed to get pull requests, the repositories and their checks, and the appearance. Passwords, tokens, the database, conversations, projects and tickets are never shared.

Choosing the repository on a Mac is what lets Wiffletree push to it, only to its default branch, only its own files and never by force; the owners you allow for pull requests neither grant nor need that. Skills are part of every agent's instructions, so whoever can push to the repository can change how your agents work on every Mac, and an organization's members may be able to read a private repository it owns: Settings says who can before you choose. When two Macs change the same setting, or something other than Wiffletree changes one, that setting pauses until you choose, with a note at the top of every project's Inbox and a comparison of both versions. An agent's shell can still write the shared folder and push to the repository with your credentials. Sync does not prevent that, but it does not spread an edit it did not make: such an edit waits for you on that Mac.

## Remote access

**Another Mac can drive this one.** Settings › Remote access › "Let other devices use this Mac's Wiffletree" is off by default, and while it is off the host listens on no network port. While it is on, the host accepts TLS 1.3 connections. You pair a device at the host with a one-time 4-digit code that lasts 2 minutes. A paired device has Control, which can do anything the host's human can in the app, or View only, which reads and changes nothing. Agents run with permission prompts off, so Control is the same as running commands on the host. Neither level can change remote access, pairing or devices. Repositories, credentials and agents stay on the host. See [remote access](DEVELOPMENT.md#remote-access) for the details and [current limits](DEVELOPMENT.md#current-limits) for what is not offered yet.

## Processes panel

**You can stop what agents leave running.** A dev server or watcher an agent starts keeps running between its turns. The Processes panel lists what each agent has running, or every agent's from the coordinator, with how long it has run and its CPU, and stops one or all of them. Wiffletree also stops them when an agent is stopped or archived and when the app quits.

## Performance

**It should feel instant.** Wiffletree is a native Rust app built on [GPUI](https://github.com/zed-industries/zed/tree/main/crates/gpui), not a web view, and it stays light when idle.
