## Safety

Agents run with their provider's permission prompts bypassed so they can work unattended. Add only repositories you are comfortable letting them change.

Wiffletree itself pushes a ticket's branch and opens its pull request only through its own checked operation: without asking in repositories whose GitHub owner you allow, and after your approval everywhere else. It merges a ticket's pull request only through its own checked merge, which the coordinator asks for, only in those repositories and only into a branch that is not protected. It never merges into a protected branch and never approves, closes or comments on a ticket's pull request.

For a brain you name in a Space, it also pushes its own `wiffletree/brain/` branches, opens their pull requests and turns on auto-merge, so GitHub merges each once the brain gate's required checks pass, except Set up's and Update gate's, which wait for the code owner's review; it closes one only when you choose Discard.

If you turn on the PR keeper, Wiffletree also rebases a ticket's open pull request and replaces the branch on GitHub, which changes every commit id on the pull request: whenever its base moves with "Keep it rebased" ticked, or, with only "Keep it free of conflicts and failed checks" ticked, only when the pull request conflicts or its checks fail.

Agents can still run any command on your Mac, including a push or a merge with your credentials, which Wiffletree does not prevent. That includes the PR keeper's model, which gets one try at a conflict or at failed checks when "Keep it free of conflicts and failed checks" is ticked: Wiffletree checks only what the try leaves behind, which files changed and whether your checks command passes, and has that reviewed before pushing it. Your checks command runs as you wrote it.

## Projects and the coordinator

**Projects are outcomes, not repositories.** A project is a feature, a bug or any goal you want reached. Repositories are attached to it, and one repository can serve many projects at once.

**You talk to one coordinator.** Each project has a coordinator that owns the goal and the conversation with you. It plans, asks you the questions that matter and reports the result. You do not have to manage the agents underneath it.

**Blocked is not the same as needs-you.** Workers report blockers to the coordinator, which resolves most of them. Only the coordinator escalates to you, and it gathers its questions in one Inbox so you answer them once.

**Software does the routine work; models do the thinking.** Git state, status, polling and usage tracking are ordinary deterministic code. Models are woken only for decisions that need reasoning, so coordinators sleep between events instead of polling.

**You can see how far along the work is.** The app derives the progress bars from each agent's checklist, each ticket's stage and its review results. The coordinator's strip shows the project's phase, one segment per ticket and how many tickets are accepted. The Agents panel, opened from any of the project's conversations, lists every ticket with its agents, their models and their progress, and marks an agent that is stuck.

## Tickets

**Each ticket is its own workspace.** The coordinator breaks the work into tickets, one repository each, with its own branch and worktree. It assigns an implementer, then verifies with one call that runs every tester and reviewer in the chosen review level at once on the same commit, and accepts the result.

**Tickets are small, isolated and tested by someone else.** Every ticket gets its own Git worktree and branch. An implementer builds it, and a separate tester checks it against the acceptance criteria. "The turn ended" never counts as "it works."

**Messages are durable.** Agents talk through the app's message queue, not by typing into each other's terminals. Every message is saved before it is acknowledged, and an idle recipient wakes the moment one arrives. After a restart, each agent resumes its exact provider session, and the app never silently retries work that might have had side effects.

## Reviews

**You decide how thorough a review is.** A review level is a named set of testers and reviewers, with a line telling the coordinator when to use it. A full review can be a ticket's only review. A re-check, such as the suggested "Light", runs only on a ticket whose last review passed, for example after a rebase or a small fix. You also cap the rounds in one review and the full reviews per ticket.

**Findings stay on the ticket.** Each tester and reviewer, a verifier, reports structured findings with a location, a trigger and evidence. A blocking finding goes back to the implementer, and only the verifiers that failed check again in the next round. Every finding is kept in the ticket's decision ledger, which you can read in the Tickets panel and which the next review receives. The coordinator triages what is left open. When a ticket reaches the cap on full reviews, the coordinator is told to read whatever no review checked and then judge the ticket itself, with a waiver.

## Spaces

**Every project belongs to a Space.** A Space, such as Sage, Vyttle or Personal, answers "where does this go?". It has a description, additions to every role's instructions, a brain the project's coordinator logs to, the code repositories it covers and its own rows in Who runs what. New project starts in the Space you used last, with that Space's repositories ticked, and says which brain the project will log to; a repository the Space lists that is not cloned on this Mac is shown as not cloned here. The Repositories page groups repositories by Space, with one chip per Space on each row, and a repository may be in several Spaces or none. Adding a repository suggests a Space from its GitHub owner, which only suggests. You create, edit and remove Spaces on the Spaces page in the sidebar, which is Settings › Spaces, and only you change which repositories a Space lists: no agent tool can.

**A Space's storage repository is also its tracker.** Each Space keeps its definition in a Git repository, in `spaces/<space>/space.yaml`, and that repository's `issues/` folder and `wiffletree-issues.yaml` are the Space's issues, with one prefix such as SAGE. A new Space gets a local repository in the data folder with no remote, which is a private tracker that is never pushed. A team shares a Space by storing it in a private GitHub repository; a teammate adds it with Add Space → From a repository and says where its brain and each code repository are cloned on their Mac, or leaves them missing. Spaces stored in one repository share its issues and prefix. Everyone who can read that repository can read the Space and its issues, and the Space's page says who that is. Anyone who can push to it can change the Space's instructions for everyone in it and can read and edit its issues, so the page says that too. Edits to a shared Space are commits that sync like settings, and an edit made on two Macs, or outside Wiffletree, pauses until you choose. Before pushing `spaces/` or `issues/`, Wiffletree runs the brain gate's personal-data and secret scans on your Mac. A file that fails, or that a check cannot scan, for example because gitleaks is missing, stays on your Mac with a note naming the file, the check and the rule, never the text it matched.

## Second brain

A brain is a Git repository of Markdown that keeps what a team has decided and learned, so the next agent starts from it. A Space names its brain in its settings, and the Brains page in the sidebar lists every brain this Mac knows. See [the brain gate's README](../gate/README.md) for the entry format and the checks.

**Agents log as they work.** The coordinator, implementers and assistant threads record decisions and observations with the `log_work` tool, and each entry is one file under `logs/<repository>/`. Testers, reviewers, the PR keeper and job runs do not log. When an implementer reports ready for testing, or a ticket is accepted or published, an agent that has not logged since its last milestone is asked for one short entry.

**Entries reach the brain in batches.** Entries wait on your Mac in a batch, per ticket for an implementer, per coordinator, or per thread. A batch closes when its ticket is accepted or closed, when its agent is archived or its thread deleted, 24 hours after its first entry, or when you press Send now. Wiffletree keeps its own checkout of each brain and sends each batch as a pull request from a `wiffletree/brain/` branch. Naming a brain in a Space is what lets it push there, and it can push only those branches.

**Anyone can read it.** Agents ask the brain with the read-only `query_brain` tool, which walks `STATUS.md`, the note index, the top notes and then the log entries. A project's Memory panel shows its brain, its waiting batches, open conflicts and recent entries. The brain browser has four views, for a project or for the whole brain: Status, Wiki, Logs and Conflicts. Wiki shows each note with its sources and backlinks. ⌘K searches one brain.

**Compile turns logs into notes.** One Mac is a brain's compiler, and it compiles at the time set in the brain's `wiffletree-brain.json`, on Run now, or after a ruling merges. It first checks each pending entry's commit or pull request and marks the entry verified, claimed or unverified. A run with nothing pending makes no model call. The model on the Brain compiler row in Who runs what then folds entries into notes and `STATUS.md`, and it can change only those files. With no model on that row, entries wait. What conflicts with an existing note becomes a card in the Inbox, on the Brains page or in the Conflicts view, with a recommended ruling, and your ruling is written back as a decision entry. Compile's result reaches `main` through a pull request like any other.

**The brain gate guards `main`.** Every pull request to a brain runs seven deterministic checks: `secret-scan`, `sensitive-info`, `markdown-lint`, `wikilinks`, `log-schema`, `path-ownership` and `gate-tests`. No check calls a model, and none prints a matched value. Wiffletree ships the gate as a GitHub Action, and each brain pins it with a thin caller. Set up on the Brains page opens the pull request that installs the gate, and Update gate moves its pin; both wait for the code owner's review. Batches auto-merge once the required checks pass. If a brain's gate would reject its logs, they wait on your Mac.

## Issues

**Issues are your team's shared backlog.** The Issues page, in the sidebar before Repositories, lists the issues of every Space as a list grouped by state or as a board, with filters for Space, open, assignee, priority, label and repository, and a search over titles, descriptions and comments. Drag a card to move it; open an issue to read its description and timeline, comment, and change its state, priority or assignee. An issue changed since you last opened it carries a dot, and the sidebar counts them. Unread marks and filters stay on your Mac. Each issue is a folder of plain files in its Space's storage repository: a private GitHub repository your team chooses, or a local one that stays on your Mac. Choosing the GitHub repository is what lets Wiffletree push issues to it. A new issue there has a temporary ID until it is pushed and numbered. Issue text is scanned for personal data and secrets before it is pushed, but know the limits: issues stay in Git history for good, even after you delete or edit them; everyone who can read the repository can read them, including, for an organization's repository, its members; anyone who can push can edit any issue; and an agent's shell can still push to the repository with your credentials, though sync does not spread an edit it did not make. Teammates without Wiffletree can add and edit issues through GitHub, and an issue file Wiffletree cannot read is shown as written. Tickets, agents, projects and conversations are never written to a tracker: an issue is not a ticket.

**Issues connect to work.** Start project from issue creates a project named after the issue, in its Space, and links the two. A Space's Storage and issues box also offers Import from Linear…, which copies a Linear team's issues into the tracker and changes nothing in Linear.

**Ask the assistant about issues; you apply what it suggests.** Ask the assistant on an issue opens that issue's thread beside it, and on the Issues page a thread with the tracker's list attached, in the Space the page is filtered to, or the one you last used for a new project. A tracker two Spaces share has a separate thread in each, and a thread never changes its Space. An issue thread reads only its Space's tracker, and its Space's repositories on this Mac at their base branch, read-only and bounded. Because issue text is written by others, it has no web search or fetch and none of its Space's sources, so it has no way to send what it read off your Mac, and a notice names who wrote what it reads. It cannot link an issue to work, create a ticket or log to the brain. Every change it suggests is a card: an edit as a diff, a comment, a split, a duplicate link or a new issue, which any thread may propose in its own Space. Nothing reaches the tracker until you choose Apply, which writes as you; Edit changes the proposal's text first, and Discard writes nothing. A card whose issue changed since says who changed it and shows the change against the current version. A comment you apply reads "Assistant for ‹you›" on every Mac, and an issue you file from a card says the assistant filed it for you.

## Assistant, recurring jobs and Boards

**Quick questions go to the assistant, not a project.** The assistant, pinned above Projects in the sidebar under the name you give it in Settings, holds many threads in tabs. Each thread is its own small Claude or Codex session in one Space, which never changes. Before each message a router, a small Claude model on the Router row with every tool off (Codex cannot yet run with every tool off, so a Router row on Codex always asks), answers which thread and which Space it belongs to: it continues the thread, switches to another open one or opens a new tab, and a message that went elsewhere leaves a line saying where, with Change. When it is less sure than the threshold in Settings (0.8 at first), when it fails or when its row is spent, it asks with one-click choices and holds your message, unsent, until you answer, even across a restart; picking a Space with the chip in the composer skips it. A thread starts on the model the Assistant row in Who runs what picks, or the Space's own Assistant row when it has one that this Mac can run. A thread is read-only plus its own scratch folder in the data folder, and the provider enforces it: Claude runs in a permission mode that denies, without asking, everything but reading, web search and fetch, writes under the scratch folder, the thread's own tools and its Space's sources, with none of your Claude settings files; Codex runs in its workspace-write sandbox rooted at the scratch folder, with no temporary folders, no shell network and approvals never asked. A run that starts with a tool or MCP server it was not given is stopped, and says so. A thread has no coordination tool and cannot edit a repository, commit, push, change a Space or a setting, or start agents. It can save a scratch file to Boards, kept only on this Mac; suggest a new Space, which you create yourself; and offer Make this a project, which, once you confirm its brief, starts a project in the thread's Space and leaves the thread read-only. Threads stay on this Mac, never sync, leave the tab strip a day after their last message and stay searchable. A thread reads its Space's whole brain with `query_brain`, and when you ask it to remember something it logs one entry there with `log_work`, under the brain's `logs/assistant/` folder, sent in a batch pull request like an agent's; deleting the thread closes its batch and keeps its entries. ⌘K in a thread searches its Space's brain.

**Recurring work is a job only you can save.** Ask the assistant for something recurring, such as a brief every weekday at 7, and its thread shows a recipe card: the prompt, the schedule in words with its next three runs, the model, and every source a run may read, each checked now, such as `gh pr list` and `gh pr view` or a Linear MCP server's read tools. A command-line source can be only gh, linctl, sentry-cli or aws, and only their read commands on Wiffletree's short list; a write such as `gh pr comment` is refused. Before a run, each MCP server is started and must answer and list its tools. Nothing is scheduled until you press Save job; no thread, run, note or file can save, change or enable a job, and the assistant's Jobs list and each job's page are where you pause, resume, run, edit or delete one. Each run is a fresh read-only thread in the job's Space, offered only its recipe's sources, and saves its result as a file kept at the same place each time, as a new version. Before a run, Wiffletree checks each source is installed and signed in, and a run with one missing does not start and says how to fix it. A job with a command-line source runs only on Claude, which can hold the CLI to its listed commands; Codex cannot yet. Jobs run only while Wiffletree runs and never wake your Mac: missed runs come back as one catch-up run, and the Jobs list offers Start Wiffletree at login. A run that has gone 30 minutes shows on the assistant's row and on its job's page with Stop, and one that failed or did not start counts there until you open its job.

**Boards keeps what threads and jobs save.** Boards, pinned under the assistant, lists every output with its Space, the job that wrote it or "From a thread", when it last changed, a preview and where it is kept: "Shared in ‹Space›", or "Only on this Mac". A job's output says Stale when two of its scheduled runs passed without a new version, and a shared job's names the Mac that runs it. Filter by Space and job, or search titles; its Jobs button opens the assistant's Jobs list. Markdown opens in Wiffletree; HTML opens in an embedded web view that runs its scripts but cannot reach the network, other files, or navigate away, and a link offers Open in browser instead; images and PDFs open in Quick Look; anything else opens in its default app. The picker lists the latest first, then the history, a Git commit for each push and, for a shared job's output, the saves replaced before a push, marked as only on this Mac; picking an earlier one shows it without changing the latest. An output only on this Mac offers Share to Space…, which copies it into that Space's storage after saying who can read it. No thread or job moves an output.

**A shared job runs on one Mac, or on everyone's.** In a Space stored on GitHub, a job is "One runner, shared result" unless you choose "Everyone runs their own". A one-runner job, such as a release dashboard, runs only on its runner's Mac: the Mac that saved it, until a member chooses Take over running, which commits their Mac as the runner. Every other member's Boards shows the runner's latest output with "Runs on ‹name›'s Mac", and Stale once two of its scheduled runs pass without a new version. Nothing a job writes is pushed until its runner approves it: its first output, and its first after anyone changes its prompt or sources, waits on the runner's Boards as "Waiting for your approval", with Share and Keep private, which leaves it only on that Mac. The approval is kept on the runner's Mac and never in the repository, and a member who takes over approves their own first output. An "Everyone runs their own" job is a template each member's Mac runs with that member's own sign-ins, and its results stay on that Mac.

**Who can change a shared job's instructions.** Anyone who can push to a Space's storage repository can change its jobs' prompts and sources and the Space's instructions, for every member. The runner's approval of each changed prompt or source list is what keeps a changed job from pushing what it read, and an edit made outside Wiffletree pauses until you choose. No thread, job run, note or file can save, enable, take over or approve a job: only the Wiffletree app sends those commands, and a run's shell is held to its listed read commands. A project agent's shell is not sandboxed, though. It runs as you, so it can still write the storage clone in the data folder and push to the repository with your credentials, as it can for the settings repository. Sync does not spread an edit it did not make: such an edit waits for you on that Mac.

## Models and usage

**Any model can play any role, and you decide who runs what.** Claude can coordinate Codex implementers, and Codex can coordinate Claude. On the Models page, one table says who runs each job (the coordinator, implementers, testers, each reviewer, the PR keeper, the assistant, its router, scheduled jobs and the brain compiler): a first choice, a choice for when that subscription runs low, and optionally a lighter line for small work. A Space can override any row but Router and Brain compiler for the work in it. Wiffletree moves a job to its next choice when the first choice's subscription passes a threshold you set, 95% by default, and when every choice is past it, waits for the earliest reset; it never buys more. A reviewer's row can say skip instead, and then a review goes ahead without that reviewer and says so. By default the Claude and Codex reviewers wait rather than switch, so a second opinion stays a second opinion. The coordinator never picks models: it asks for a job, and for small work when it fits, and each agent shows why it runs where it does, just above the message box, such as "Started on Codex: Claude's weekly limit was at 96%". A running agent never switches provider. You can still change the model of any single agent yourself.

**Usage and limits stay in view.** The sidebar shows each provider's 5-hour and weekly limits, and the Usage page puts both accounts side by side. Those percentages come only from the providers' own telemetry: the Codex app server, and the rate-limit events Claude sends during live turns, so a Claude window reads **Unavailable** when Claude reports no percentage. Wiffletree never scrapes account pages or spends tokens to check. Below the limits, it charts the tokens its agents used by day and ranks them by coordinator, with project and provider filters.

**You can see what fills an agent's context.** Each agent's Overview has a Context card that shows how full its context window is and with what, measured after every turn without a model call. Claude reports its own categories; for Codex they are estimates. **Compact…** on the same card replaces a Claude or Codex agent's conversation with a summary when you choose, and for Claude you can say what to keep.

## Behaviors and skills

**You can change how agents work, not what they may do.** The Behaviors page, after Models in the sidebar, is the one place for it. A scope bar picks the Workspace, which is you on every Mac, a Space, or one of that Space's repositories. For each role it lists the Behaviors, named choices such as Review depth or Publishing, each with its switch or pick, a chip naming where its value comes from (Stock, Workspace, the Space or the repository, or "Set here") and Reset to what the scope inherits. A Behavior a scope can't set shows its value read-only, and a Space or repository is offered only stricter Review depth and Publishing. A Space and a repository each have their own additions, free text after the Behaviors for every role in the Space, or for that repository's tickets in that Space. At the Workspace, a role's additions are its skill's own rules, and Advanced holds the five skills: Coordinating, Implementing, Reviewing, Keeping a PR and Assisting, for the assistant's threads. Each is a stock text bundled with Wiffletree, and you can add your own rules after it. Agents are told that your rules win where the two disagree. A saved change applies from each agent's next turn. A Codex agent gets it from its next new session, because a resumed Codex session keeps the instructions it started with.

**You can rewrite a skill and keep updates.** You can also rewrite the stock text itself, after a confirmation: your rewrite is sent in place of it. When a release brings a new version of a skill you rewrote, Wiffletree merges the update into your rewrite on its own, paragraph by paragraph, and leaves a note on the skill's page with Review changes, which shows each change before and after, and Undo, which puts back exactly what you had. Where you also changed a passage the update changes, the PR keeper's Claude model merges just that passage; with no such model, you choose the update's wording or yours on the skill's page. You are asked only when the model finds that the two wordings want different things: the question waits at the top of every project's Inbox and on the skill's page, and answering it on one Mac settles it on all of them. With a settings repository, one Mac merges for all of them. Until a merge applies, your rewrite keeps running as written, and the skill is marked out of date, with a dot on the Behaviors row and on Advanced, and what changed line by line; you can merge it in, mark it up to date or reset it. Reset to stock removes your rules or rewrite after asking, and a skill's History lists every change, newest first, with View and Restore, so nothing you wrote is lost.

**Authority is not in the text.** Every agent also gets a fixed core that you can read there but not edit: its workspace tools, how it reports, and the rules the app enforces whatever a skill says. Each skill's page lists what the app enforces and what the text decides. An agent's shell is not sandboxed, so it can still run `git push` with your credentials, and it can write the skills folder in the data folder, as it can write the settings file.

## Pull requests

**Humans own integration.** Agents deliver tested branches. Once a ticket's review has ended, Wiffletree pushes its branch and opens its pull request itself: without asking for the GitHub owners you allow on the Repositories page, and only after you approve each step everywhere else. Each repository on the Repositories page has a list of protected branches: its default branch on GitHub and its base are always on it, you add names and patterns such as `release/*`, and branches GitHub protects count too. When the coordinator asks, Wiffletree merges a ticket's pull request into any other branch, such as a feature branch, in a repository whose owner you allow, but only at the reviewed commit, with passing checks or none and no conflict, and the merge accepts the ticket. After a review that ended blocked it asks you first, on an Inbox card. You merge into protected branches, including a feature branch into `main`: Wiffletree refuses whoever asks. It never approves, closes or comments on a ticket's pull request. A brain's batch pull requests auto-merge once the brain gate's required checks pass, except Set up's and Update gate's, which wait for the code owner's review, and Wiffletree closes one only when you choose Discard.

**The PR keeper keeps pull requests current, if you ask it to.** It is off until you tick it on the Repositories page, and it acts only in repositories that open pull requests without asking. Two rows are independent, and either can be on alone: "Keep it free of conflicts and failed checks" rebases a pull request only when it conflicts or its checks fail, then tries once to fix it, and "Keep it rebased" also rebases every time the base moves. Once a pull request's base has been quiet for a couple of minutes, Wiffletree rebases the branch itself, with no model and no review, and replaces the branch on GitHub with a lease, only when the rebased change is the same as the reviewed one. Every commit id on the pull request changes.

A rebase whose patch changed, because the base moved lines the change touches, is pushed only with "Keep it free of conflicts and failed checks" ticked, a re-check level chosen for it and a checks command on the repository's row: the command, such as `cargo test`, runs on the rebased commit, stopped after its limit (20 minutes unless you set 1–120), then the commit is reviewed at that level before it is pushed. If either fails, nothing is pushed, the branch is left as it was before the rebase and the coordinator is told.

A rebase that conflicts gets one try by the PR keeper's model at each pull request head, with the same settings and a PR keeper model in Models → Who runs what. The model works in the keeper's own checkout, never the ticket's worktree, and its result is thrown away unless it changes only the files Git could not merge, passes the checks and passes the review; only then is it pushed. A try that is thrown away leaves the branch and the ticket's review as they were, and the coordinator is told why. The pull request's line reads "keeper resolving" while the try runs and "with the coordinator" after one was thrown away.

The same setting covers failed checks: a pull request whose checks failed on GitHub gets one try the same way, once no rebase is due for it: Wiffletree first runs your checks command on its head, and if it passes here, no model runs and the coordinator is told the failure could not be reproduced. Otherwise the model's fix must add commits on top of the head, change only files the pull request already changes and pass the same checks and review; the line reads "keeper fixing" meanwhile. Without all of these, a changed patch, a conflict or failed checks are left to the coordinator.

With "Sort new comments" ticked and a Claude model in the PR keeper's row, it also sorts new comments from people who can push to the repository into needs a change, a question or no action, with a model run that has every tool and hook turned off, and sends the coordinator links to those that need something, never their text. It never replies, resolves or reacts on GitHub. It works only while Wiffletree is running.

## Settings sync

**Your settings can follow you to every Mac.** In Settings, name a private GitHub repository that you created, empty or already used by your other Mac. Wiffletree then keeps the skills with your rules, rewrites and their history, the review settings, the model notes, the switch threshold, the check-in thresholds and the PR keeper's triggers the same on every Mac that names it. It pulls at launch and every 5 minutes and pushes a few seconds after you change something, with no model. What belongs to one Mac stays there: who runs each job, the PR keeper's model included, the workspace folder, the owners allowed to get pull requests, the repositories and their checks, and the appearance. Passwords, tokens, the database, conversations, projects and tickets are never shared.

Choosing the repository on a Mac is what lets Wiffletree push to it, only to its default branch, only its own files and never by force; the owners you allow for pull requests neither grant nor need that. Skills are part of every agent's instructions, so whoever can push to the repository can change how your agents work on every Mac, and an organization's members may be able to read a private repository it owns: Settings says who can before you choose. When two Macs change the same setting, or something other than Wiffletree changes one, that setting pauses until you choose, with a note at the top of every project's Inbox and a comparison of both versions. An agent's shell can still write the shared folder and push to the repository with your credentials. Sync does not prevent that, but it does not spread an edit it did not make: such an edit waits for you on that Mac.

## Remote access

**Another Mac can drive this one.** Settings › Remote access › "Let other devices use this Mac's Wiffletree" is off by default, and while it is off the host listens on no network port. While it is on, the host accepts TLS 1.3 connections. You pair a device at the host with a one-time 4-digit code that lasts 2 minutes. A paired device has Control, which can do anything the host's human can in the app, or View only, which reads and changes nothing. Agents run with permission prompts off, so Control is the same as running commands on the host. Neither level can change remote access, pairing or devices. Repositories, credentials and agents stay on the host. See [remote access](DEVELOPMENT.md#remote-access) for the details and [current limits](DEVELOPMENT.md#current-limits) for what is not offered yet.

## Processes panel

**You can stop what agents leave running.** A dev server or watcher an agent starts keeps running between its turns. The Processes panel lists what each agent has running, or every agent's from the coordinator, with how long it has run and its CPU, and stops one or all of them. Wiffletree also stops them when an agent is stopped or archived and when the app quits.

## Performance

**It should feel instant.** Wiffletree is a native Rust app built on [GPUI](https://github.com/zed-industries/zed/tree/main/crates/gpui), not a web view, and it stays light when idle.
