# Local development build

Wiffletree is the product name, selected October 5, 2026. This is a working local trial, not the completed PRD release.

## Build and open

On macOS with Rust, Xcode and its Metal toolchain:

```sh
bash scripts/package_macos.sh
open "target/Wiffletree.app"
```

The bundle includes both the GPUI client and `workspace-host`, the host it runs (see [the host process](#the-host-process)), plus the Interlock macOS app icon. Packaging builds the standard and Retina icon representations from the canonical brand-kit PNGs using the macOS `sips` and `iconutil` tools. It is ad-hoc signed for local development and never updates itself; see [releases and updates](#releases-and-updates) for distributed builds. The default store is `~/Library/Application Support/Wiffletree`, outside your repositories. Existing installations automatically reuse `~/Library/Application Support/Agent Workspace` when no Wiffletree data directory exists. This preserves stored sessions and absolute ticket-worktree paths without moving live data. An explicit `--data-dir` still takes precedence. A new store starts empty. Only one host can own a store.

The settings meant to follow the human to every machine live in the shared folder, through `shared::SharedStore` (`crates/workspace-host/src/shared.rs`): the settings repository's clone at `repos/github.com/<owner>/<name>/` when one is chosen, and the store's `shared/` folder otherwise (`shared::folder`). It holds `wiffletree.json` (`{"format": 1}`), `settings/review.json` (the verifiers, review levels and both caps), `settings/model-guide.md`, `settings/models.json` (the switch threshold), `settings/check-ins.json`, `settings/pr-keeper.json` (the keeper's triggers, quiet period and review level) and the skills in `skills/`. JSON files are written atomically, pretty-printed with sorted keys, keeping fields this release does not know, and a missing or unreadable file means that setting's default. Everything else stays in `settings.json` (the workspace folder and the allowed owners) and the database (the Who runs what table, the PR keeper's row among it). At start, after the model selection's own migration and before anything reads a shared setting, the host copies each shared setting that has no file yet from where an earlier release saved it, exactly as saved, and renames `skills/` into `shared/`, writing `wiffletree.json` last: a move cut short finishes at the next start, and once `wiffletree.json` exists nothing is copied again. The old fields stay in `settings.json` and the database row, unread and never written again, so an older release starts with the values it had.

A settings repository makes the shared folder a Git clone (`crates/workspace-host/src/sync.rs`). How the host reaches GitHub, the URLs it tries, gh's login and the read-only check of who can read a repository, is in `github_access.rs`, for every repository the host syncs. `CheckSettingsRepository` takes `owner/name` or a `github.com` URL. It reads the repository's visibility, owner kind and default branch with `gh api repos/…`, and an organization's base permission with `gh api orgs/…`; both are GETs, and `Readers` says who can read the repository; an internal repository is readable by every member of its enterprise. It checks access with `git ls-remote` and refuses a public repository. For `owner/name` it tries the URL of gh's Git protocol (`gh config get git_protocol -h github.com`, `https` when unset) and then the other, and keeps the first `ls-remote` can read as the push URL; a URL the human names is the only one tried. Every Git command that reaches an HTTPS `github.com` URL (`ls-remote`, clone, a pass's fetch, push) gets `-c credential.https://github.com.helper= -c 'credential.https://github.com.helper=!gh auth git-credential'`, so it uses gh's login for that command only; no token is stored, logged or put on a command line, and Git's own config is unchanged. When no URL can be read, the error names each URL and Git's reason. Clone and `ls-remote` get the push's longer time limit. Then it clones the branch into a temporary `shared-staging-*` folder of the data folder, removed when the check ends. A symbolic link at or under `wiffletree.json`, `settings/` or `skills/` refuses the repository, and copying never follows one. When the clone has `wiffletree.json`, the answer carries `joining`: each shared setting as the repository and this machine hold it, and the machine and time of the last commit. The comparison is in the check's answer, not on the snapshot, because only the client that asked needs it. `SetUpSettingsRepository` (no `wiffletree.json` yet) adds this machine's `wiffletree.json`, `settings/` and `skills/` beside the clone's files and refuses to overwrite one. `JoinSettingsRepository` with `with: this_machine` replaces the clone's three with this machine's. `with: repository` only adds this machine's skill history entries that the clone lacks; an entry whose name the clone already uses for another entry is kept as `<name>-2.json`. Each makes at most one commit with the human's Git identity, named for the change and the computer (`scutil --get ComputerName`), and refuses to commit when Git has no name and email. It pushes. Then, with another settings repository chosen, its `wiffletree.json`, `settings/` and `skills/` are first copied to `shared/`, as `StopSettingsSync` does, and its clone stays where it is. The prepared clone moves to `repos/github.com/<owner>/<name>/`; when the repository already has a clone there, that clone is reused instead: it fetches the prepared commit, takes the other files as that commit holds them and the three settings paths as the prepared clone holds them. `settings_repository` (name, push URL, branch and who can read it) is saved in `settings.json`, where it is never synced, which makes that clone the shared folder, and only then do the three settings paths of `shared/` move to `backups/shared-<time>/`. No clone is ever moved to `backups/`. One folder per owner keeps `a-b/c` and `a/b-c` apart, which the `repos/<owner>-<name>/` folders of stage 2 did not; at start, before the settings clone moves, `repos::migrate_clone_folders` renames each such clone by the name this Mac recorded for the repository it holds (the settings repository or storage), or else by the repository its `origin` names, and then sets a recorded repository's `origin` to its name, recording the rename in `repo_moves` before making it so a start cut short finishes it. A clone is set up with `origin` naming its repository as GitHub does, and a clone found under `repos/` is used only when its `origin` names the chosen repository, by GitHub's name or as its recorded push URL does, which an older release left as `origin` for a URL GitHub redirects (`repos::holds`): otherwise set-up and join are refused before anything is pushed, the first start's move is skipped with a log line, and `shared::folder` stays `shared/`. A `shared-staging-*` folder left by a host that stopped mid-way is removed at the next start. If a shared setting was saved after the clone was prepared, the clone is refused and the folder stays as saved. If saving the choice fails, a clone moved into `repos/` is moved back and the shared folder in use is unchanged. At start, before anything reads a shared setting, a machine whose settings repository is chosen and whose clone is still in `shared/` (a release before `repos/`) renames it to `repos/github.com/<owner>/<name>/`; the rename is the move, so a start cut short before it moves it at the next start. Without a settings repository, `shared/` stays a plain folder. The push (`sync::push`, through `repos::push`) sends only the clone's HEAD, to the recorded default branch at the recorded push URL, with `--no-follow-tags --recurse-submodules=no` and never forced. It refuses a commit that does not contain GitHub's head, and any commit changing a path outside those three. The check, the clone, the commit and the push run off the host thread; only the last swap runs on it. The allowed owners neither allow this push nor are needed for it. The snapshot's `still_needs` lists, once a repository is chosen, what this machine lacks to run the shared settings, each with the main window's page that provides it: a keeper trigger's PR keeper model or re-check level, and a verifier with no row in Who runs what here. No agent tool names the shared folder or the repository.

Sync keeps the clone and the repository's branch in step. Every clone the host writes to lives under `repos/`, with one sync engine per repository (`crates/workspace-host/src/repos.rs`): it fetches, lets each of the repository's rule sets compare the files it claims by path (`repos::RuleSet`), brings the files no rule set claims to GitHub's version without ever committing them, makes one commit per rule set, and pushes them together; `repos::push` refuses a commit holding two rule sets' files. A rule set whose compare fails (`RuleSet::failed`) commits nothing that pass and keeps its files, while the others commit and push. A repository is fetched at the shortest cadence of its rule sets (`repos::Pace`). The settings repository's only rule set so far is settings (`sync::Settings`), over `wiffletree.json`, `settings/` and `skills/`. Its record is the `sync_record` table, keyed by repository (`repos::key`, lower-case `owner/name`; the empty key for `shared/` with no repository, and the rows of a store from before keys became the settings repository's, once): per shared file, the content last synced and the content the host last wrote, which `SharedStore` and `SkillStore` note on every write (a skill's files and history entry once its whole change holds, so a change put back notes nothing); the row with an empty path holds the commit last synced. Choosing a repository starts the record afresh from the clone, as does the first pass on a repository chosen before the record existed: each file at the clone's head is synced, and as the folder holds it written. A pushed file is recorded as the pushed commit holds it, which can be a save made during the pass. A pass runs off the host thread: it fetches the branch, compares each file under `wiffletree.json`, `settings/` and `skills/` (hidden files aside) whole with its last synced version and GitHub's, resets the index to GitHub's head, brings other files such as `README.md` to GitHub's version, commits the files changed only here, named by setting and computer, and pushes with `sync::push`. A file changed on both sides is left out of the commit and kept here. Files changed only on GitHub go back to the host thread, which writes each one unless it was saved meanwhile, and records the pass. A push GitHub refuses leaves the pulled files applied and the changes waiting for the next pass. `repos::Pace` runs a pass at start, every 5 minutes, at once on `SyncNow`, and 5 seconds after the last shared write; while passes fail to read GitHub it backs off to 10, 20 and then every 30 minutes, and saves wait for the next try. The snapshot's `settings_sync` carries the repository, the last pass's time, files pulled and pushed and error, the next pass, and the settings the host wrote since they were last synced, each named once.

A pass pauses what it should not decide alone, recorded in `sync_paused` with why and GitHub's content: a file both sides changed to different content since it was last synced, a file whose content here is neither what the host last wrote nor what it last synced (changed outside Wiffletree, such as by an agent's shell), and a pulled file the host would refuse to save (`shared::check`), which is not applied. A skill's `additions.md`, `rewrite.md` and `base.md` pause together, as one unit named by the skill's folder; its history entries keep syncing. A paused file is neither pushed nor overwritten, and this machine keeps using its own; a newer version on GitHub replaces the one compared against, and the pause ends when both sides become equal. The host never pushes a file it would refuse to read. When `wiffletree.json` names a format this release does not know, sync stops and pulls and pushes nothing. The snapshot's `workspace_notes` has one note per paused unit, with no file contents. The window lists them at the top of every project's Inbox with a "Workspace" label, counted in the Inbox's badge, and in the Settings repository section with why. `ComparePausedFile` answers, read-only, with the line diff from this machine's version to GitHub's, or to the last synced one for an edit made outside Wiffletree; for a skill it compares the rewrite, or else the rules. `SettlePausedFile` takes the note's choices: Keep this Mac's and Use the other machine's for two machines, Sync this version (checked first) and Put back the synced version for an outside edit, and Keep this Mac's for a file that cannot be read. The next pass pushes or pulls what the choice leaves, and the note closes in every Inbox. `StopSettingsSync` copies `wiffletree.json`, `settings/` and `skills/` from the clone to `shared/`, exactly as they are, which is the shared folder from then on, forgets the repository and its settings files' pauses, leaves the clone where it is, syncing on as storage when a Space is stored there, and changes nothing on GitHub. The sidebar footer's sync mark, shown only while a repository is chosen, opens the Settings window at the section; the section's cards about what this machine still needs open Models or Repositories in the main window. No agent tool reaches a note, its comparison or its choices.

A Space's definition and its tracker live in its storage repository (`crates/workspace-host/src/storage.rs`); the store keeps each Space as the host uses it, and the files are what travel. `space.yaml` (at `spaces/<folder>/`) and `wiffletree-issues.yaml` (at the root) are YAML. The keys this release does not know are kept where they were read, in an `extra` map on the Space, its brain and brain repository (local or on GitHub), its models and each default model (`SpaceModel`), each source and the tracker config (`workspace_core::Extra`), so a write only serializes the value: each list item keeps its own, and clearing a field drops what was under it. A `space.yaml` naming a `storage`, which only the store holds, is refused. A GitHub tracker's prefix change is refused while its clone, or GitHub's tree at the commit last synced, holds an issue. Local storage is a Git repository at `repos/local-<id>/` with no remote: creating a Space makes it, with `space.yaml` and the tracker's config in its first commit, every change to the Space is committed at once with the human's Git identity (Wiffletree's when Git has none), and nothing is ever pushed or scanned. At start, `ensure_local_storage` gives a Space from the upgrade, or one whose first commit was cut short, its repository. A GitHub storage repository is checked as a settings repository is and cloned into a `shared-staging-*` folder off the host thread (`CheckStorageRepository`, which lists its Spaces and prefix; `CreateSpace` with `storage`; `JoinSpaces`), then placed at its clone folder, or the clone already there is kept, as for a repository that is also the settings repository, whose record then gains the Space files it lacks. A new Space in a repository with no commit first pushes an empty commit (`start_if_empty`), only after every refusal has run (`Host::precheck_stored_space`, then the clone's folder and GitHub's name for the repository). Storage passes, the settings pass, adopting a clone and putting a Space in one all take the one `sync_passes` lock, so no two work in a clone at once. A rule set whose compare fails keeps its pauses and holds. A pulled tracker config whose prefix another storage repository here uses, or a pulled Space whose GitHub brain has another use here, is paused as one this Mac cannot use; joining refuses such a brain. Restarting the settings record touches only settings files, so a Space's pauses and holds survive choosing its storage as the settings repository. Its engine runs two rule sets: Spaces, over the folders of the Spaces this Mac added, comparing whole files as settings does, and issues (`issues_sync::IssueRules`), over `wiffletree-issues.yaml` and `issues/`, described below. A pulled `space.yaml` or tracker config updates the store. A storage repository that is also the settings repository runs them in the settings pass; any other has its own pace, every minute once it has a tracker, and a repository that gains one, by Set up issues or a pulled config, has its next fetch brought forward at once (`Pace::set_every`). Each storage pass's time and error are kept in memory for the Space page's Storage and issues box (`SpaceStorage`, human-only because it names the clone's folder), which counts the tracker's issues from the issue index. Paused storage files are workspace notes whose `repository` names the storage repository, and `ComparePausedFile` and `SettlePausedFile` take it. A tracker's prefix is 2 to 5 capitals, unique among this Mac's storage repositories (`SetTrackerPrefix`): a local one renames its `issues/<OLD>-<n>/` folders and every whole `<OLD>-<n>` in its issues, and commits; a GitHub one changes only while its clone has no issue. `SetUpIssues` adds the config to joined storage that has none. Joining takes, for each Space, where its brain is and the folders here that are clones of its code repositories (`JoinSpace.clones`); each must have an `origin` the Space lists, and they join the workspace's repositories with the Spaces, or nothing is written. A repository has one use here (`Host::refuse_second_use`): a Space's GitHub brain is refused as storage or settings, and storage or settings as a brain, before anything is pushed.

Shared issues (OpenSpec change `shared-issues`) are files in the tracker: `issues/<ID>/issue.md`, `comments/` and `events.jsonl` (`crates/workspace-host/src/tracker.rs`). The issue rule set (`issues_sync.rs`) syncs them against what this Mac last synced: a file changed on GitHub by anyone is pulled, one that does not parse included, and one changed here that Wiffletree did not write is paused whole, its paused parts kept as they were. An `issue.md` changed on both sides, or with a paused part, merges three-way per part, each front matter field and the description (`issues_sync::merge_issue`): a part changed on both sides to different values keeps this Mac's value here and pushes GitHub's, and is kept in `issues.sql`'s `issue_parts` with GitHub's value and the last author there, until the human settles it or both sides agree. A merged file is written here and recorded as last synced in GitHub's version, so this Mac's own part changes push and a paused one does not. `events.jsonl` changed on both sides merges as the union of its lines ordered by `at`; a comment changed on both sides pauses whole. Merged content is scanned before it is pushed like any other. Paused parts are notes at paths such as `issues/CEL-148/issue.md#description`, which `ComparePausedFile` and `SettlePausedFile` take (Keep mine, Use theirs). A new issue in a GitHub tracker has a temporary ID (`CEL-new-qxvb`) until a pass numbers it on top of GitHub's head, in the content it commits, and the host renames it here once pushed; a local tracker numbers it when filed and commits each write at once. When a scan holds a new issue's `issue.md`, the issue stays here whole and unnumbered, with every file naming its number; a held file naming another new issue holds that one too, repeating until nothing more is held (`IssueRules::also_held`). The files are the source of truth. `issues.sql` keeps an index of them for the list, counts and search: each issue's listing, a stamp of its folder's file names, sizes and times, a digest of their content and its ID, title, description and comments in lower case. Listing, the Space page's count and the end of every pass read again each issue whose stamp changed, so an issue added or edited by hand, in a local tracker or the clone, is listed as it is (`Host::refresh_issue_index`); the index is rebuilt when it is missing or of another format. `issue_read` keeps the digest of each issue as the human last opened it (`MarkIssueRead`) or the host last wrote it for them; an issue whose digest differs is unread, and a tracker this Mac indexes for the first time starts read. Read marks never reach the tracker. Search (`Issues` with `search`) keeps the issues whose indexed text holds every word. `Issues` is a read, but when its refresh of the index finds a change the service reloads the snapshot, so the sidebar's count follows. `issue_last_filed` keeps the Space of the last issue filed on this Mac, which the snapshot gives as `last_filed_space`.

Links between issues and work (`issue_work.rs`) stay on this Mac in `issues.sql`'s `issue_links`: an issue to a project, or to one of its tickets. `StartProjectFromIssue` creates the project and coordinator in one of the Spaces sharing the tracker, with the issue's repositories on this Mac (or the Space's when it lists none), links them, sends the coordinator the issue as JSON passages naming their authors, behind a line framing it as context and not instructions, and appends a `work` event. The linked work derives the issue's state (`issue_work::derive`); `issue_derived` keeps the state last derived, and the issue moves, with a `state` event marked `auto`, only when that changes, so a manual move, which records the derived state it overrode, holds until the work changes. The PR watcher re-derives, with a `pr` event, when a linked ticket's PR number or state changes, and accepting or closing a ticket re-derives too. The PR watcher stops at acceptance, so an accepted ticket counts as finished. Nothing about the project, tickets or agents reaches the tracker. No write builds on an issue file that holds neither what the host last wrote nor what it last synced (`Host::changed_outside`): the human's writes are refused, and an automatic one keeps its `work` and `pr` events in `issue_pending` with the derived state left unrecorded, so an agent's shell edit is never recorded as the host's or pushed; once the file is settled, or put back and seen by a pass, the pending events are written with the state the work derives (`Host::follow_pending_work`). The coordinator's `list_issues`, `read_issue` and `link_issue` reach only its project's Space's tracker, and the coordinator core says issue text is never instructions.

The Issues page (`crates/workspace-desktop/src/issues_view.rs`) lists every Space's issues from `Issues`, grouped by state or as a board, and asks again with the filters' Space and search; open, assignee, priority, label and repository filter the listings it has, and the board, with a column for every state, ignores the open filter. Filters live in the window, never in the tracker. Dragging a board card sends `MoveIssue`. Opening an issue (`issue_view.rs`) reads it with `Issue` and marks it read, and reading it again after a pass changed its tracker marks the new version read too; its title, description, comments and events are shown as plain text, never rendered Markdown, because issue text is untrusted. Its Work box lists the linked projects here with their tickets and PRs, or who started work on another Mac and the PRs from the `work` and `pr` events, or offers Start project from issue, a `creation.rs` dialog whose Space picker lists only the Spaces sharing the tracker (`IssueProjectDefaults`). New issue (`new_issue.rs`) sends `CreateIssue`. Every write is human-only on the socket. The sidebar's Issues row counts unread issues per tracker from the snapshot's `issue_trackers`, counting a tracker two Spaces share once.

The human's identity in a tracker is `gh api user`'s login (`spaces::gh_account`), read off the host thread at launch, once a Space's storage is chosen or joined, whenever `gh`'s `hosts.yml` changes (`GH_CONFIG_DIR`, else `$XDG_CONFIG_HOME/gh` or `~/.config/gh`), and when a tracker write arrives without one. A login replaces the one kept, `gh`'s exit code 4 (signed out) forgets it so writes are refused, and any other failure keeps it, so issues can still be filed offline. The issue page's assignee picker asks `IssuePeople`: the logins the index's `people` column names, the storage repository's collaborators and the profiles' names, which the service reads through `gh` at most once an hour per tracker (`issue_inbox::read_people`, only for logins GitHub could have given). Inbox issue notes (`issue_inbox.rs`, `WorkspaceNote::Issue`) are listed under an "Issues" label at the top of every project's Inbox and counted in each: paused parts and paused issue files, with Compare and Keep mine and Use theirs, or Sync this version and Put back the synced version for an edit made outside Wiffletree; and news in `issue_notes`, noted at the end of a pass by comparing each touched issue before and after it: a new Urgent issue naming a repository on this Mac, an assignment to the human, a mention of `@login` in a description or comment, a new comment on an issue the human follows, and, from `follow_work`, a linked issue's automatic move. Nothing is noted of the human's own changes. Opening the issue (`MarkIssueRead`) settles its news for every project. The human follows what they filed, are assigned or commented on, unless they chose otherwise with Follow on the issue page (`FollowIssue`, kept in `issue_follows`). Follows, notes and names never reach the tracker.

Before a storage repository's commits are made, each file under `spaces/`, `issues/` or `wiffletree-issues.yaml` with content is scanned (`crates/workspace-host/src/scan.rs`) by the brain gate's `sensitive_scan.py` and `secret_scan.py`, bundled with `include_str!` and written once per version to `<data folder>/gate/<hash>/`. They run with `python3` from the host's `PATH` in a scratch repository of two commits, GitHub's version and this Mac's, with `GATE_BASE` at the first, so only added lines are scanned and inline `gate:allow` markers work. A file a check fails (exit 1, each finding matched to a file it was given), or that a check cannot scan (exit 2, such as gitleaks missing; Python not starting; or an exit 1 whose findings do not all name given files, as a traceback's), is held, and a check that cannot scan holds every file of the pass: left out of the commit, kept here, and listed in `sync_held` as a `WorkspaceNote::Held` that names the file, the check and its rule or the check's own error line, never the matched text. The next pass scans it again.

A release's new stock version of a skill is merged into the human's rewrite (`crates/workspace-host/src/skills.rs`, `skills/merge.rs`, `skills/model.rs`; the history and merge types are `workspace_core::skills`). A rewrite is due a merge when its base's version is older than this release's stock version, its files can be read, are not paused and were not changed outside Wiffletree, no Undo or restore from before a merge stops that version, and no question waits about it. The host checks at start after the "New stock version" entries, after a pass that pulled a skill's files, and on `MergeSkillUpdate`; with a settings repository, the start's merges wait for the launch's first pass. `merge::merge` splits base, stock and rewrite into paragraphs, merges the title line on its own and diffs the paragraph lists with `similar`; changes from both sides that share, touch or insert at one place are one overlapping passage. With none, `SkillStore::change` saves the merged rewrite, the stock text as its base and one `merged` history entry, which keeps the rewrite and base from before, each change's source, the model and tokens and the machine; `UndoSkillMerge` writes the before bytes back with an `undid_merge` entry. Overlapping passages go to the PR keeper row's Claude choice (`ModelSelection::sorting_model`): a run of its own off the host thread (`provider::merge_run`), `claude -p --tools "" --strict-mcp-config --no-session-persistence` with hooks off, the bundled `skills/merging.md` as system prompt and a schema, in an empty temporary folder with no workspace socket or token and a 5-minute limit, sent the skill's name, the three texts and the passages, never the fixed core. Its answer gives each passage a merged text or a one-sentence question and is checked before anything changes; an answer is dropped when the skill's files changed while it ran. A failed try is kept in memory until Try again or the next start. A question writes an `asked` entry holding the merge so far (its parts and each passage's answer) and the stock text it merges into, and changes nothing else. While it is the newest entry about this release and the skill still holds what it asked about, no run starts, the skill's `SkillState.question` and a `WorkspaceNote::SkillQuestion` carry it, and `AnswerSkillQuestion` builds the merge from the entry with no model. A machine whose stock text differs neither shows it nor answers it. With no Claude choice in the PR keeper's row, `AnswerSkillQuestion` takes a wording for each overlapping passage instead. Dismissed merge notes are kept per machine in `skill_merges_dismissed`.

To try unreleased work without interrupting the installed app, build the beta:

```sh
bash scripts/package_macos.sh --beta
open "target/Wiffletree Beta.app"
```

**Wiffletree Beta** has its own bundle ID (`com.vyttle.wiffletree.beta`), a BETA badge beside the wordmark and its own store at `~/Library/Application Support/Wiffletree Beta`. It runs beside the release app and never opens, migrates or locks the store that live sessions use, so a newer schema in the beta cannot strand the release app. The two stores do not share projects; do not point the beta at the release store with `--data-dir`.

For an isolated trial:

```sh
cargo build --locked --release -p workspace-desktop -p workspace-host
./target/release/workspace-desktop --data-dir /tmp/wiffletree-trial \
  --demo-repository "$PWD"
```

The optional demo argument creates one project and attaches the supplied repository at `HEAD`, once a model setup is saved (see First project, step 3): on a fresh data directory, save the suggested setup on the Models page and relaunch. It does not start inference. Use a persistent data directory for actual work: ticket worktrees live inside that directory, so deleting it would delete their working files.

## The host process

The app and its host are separate processes. The desktop reaches the host only over `<data folder>/host.sock`, as [docs/host-protocol.md](host-protocol.md) describes, and the host owns the store alone.

- **A signed app on its default data folder** runs the host as the LaunchAgent `com.vyttle.wiffletree.host` (`com.vyttle.wiffletree.beta.host` for the beta). When no host answers, the app copies its bundle's `workspace-host` to `<data folder>/host/<version>/workspace-host`, writes `<data folder>/host/<label>.plist` and loads it with `launchctl bootstrap gui/<uid>`. The plist is deliberately not in `~/Library/LaunchAgents`, so the host **does not start at login**: after a restart or logout nothing runs until the app is opened. launchd restarts the host only after an unsuccessful exit. The host starts its agents' helpers from its copy, so replacing the app bundle never touches a running host, and at each start it removes the copies of other versions.
- **`--data-dir`, and every unsigned or ad-hoc-signed build**, start `workspace-host serve --data-dir <dir> --child` as the app's own child, straight from the bundle (or `target/`). There is no plist, no versioned copy and no launchd job, and the child stops when the app exits, stopping its turns. Only a Developer ID signature counts as signed here (`workspace_core::developer_id_signed`).
- **Its log** is `<data folder>/logs/host.log` for the launchd host. A child host writes to the app's standard error.
- **To stop it**, choose **Stop agents and quit** from the menu bar icon: the host stops every turn as a quit does, records them as interrupted, and exits cleanly, so launchd leaves it stopped. From a shell, `launchctl bootout gui/$(id -u)/com.vyttle.wiffletree.host` stops it the same way. **To remove it**, boot it out and delete `<data folder>/host/`. Its client credential is the login keychain item `com.vyttle.wiffletree.client-credential` whose account is the data folder; delete it in Keychain Access, or with `security delete-generic-password -s com.vyttle.wiffletree.client-credential -a "<data folder>"`.
- **The host key** for remote access is the login keychain item `com.vyttle.wiffletree.host-key` whose account is the data folder, created the first time remote access is turned on, with the same access list as the client credential. A child host keeps one too. An unsigned development build cannot read it again after a rebuild, since its access list names that build alone; delete it with `security delete-generic-password -s com.vyttle.wiffletree.host-key -a "<data folder>"` and turn remote access on again.
- **The client credential** guards the commands only the human should give: a message from the human, answering the Inbox, and granting publish or push authority. The launchd host creates it at its first start, in a login keychain item that only the signed app and the host's copies read without a dialog. Any other program, an agent's shell among them, gets a dialog asking for the login keychain password. A child host gets a fresh one on its standard input each launch, never in its environment or a file. This raises the bar for an agent that tries to answer its own questions; **it is not a sandbox**. Agents run as you, can open the socket, and can run any command you can.

Quitting follows the host:

- With a launchd host and agents working, ⌘Q asks **Quit Wiffletree?**, with **Keep them running** (the default) and **Stop agents and quit**. Keeping them, or quitting with nothing working, closes the windows and leaves the Dock. Closing the last window does the same. The app then runs in the background with an icon in the menu bar, quiet while no agent works and showing the count while any does, turns started later by a timer included. Its menu has **Open Wiffletree**, **Stop agents and quit** and **Quit Wiffletree**, which ends the app and leaves the host and its turns running.
- With a child host, ⌘Q quits at once, as before, and the child stops with its turns.
- A quit from the Dock decides as ⌘Q does. Every other quit ends the app at once: a logout, restart or shutdown, and a quit a script or installer sends, as `scripts/install.sh` does before it replaces the app (`crates/workspace-desktop/src/native_quit.rs`). A launchd host keeps running through it; a child host stops with its turns.
- A downloaded update installs only when the app process exits: on Quit Wiffletree, on Stop agents and quit, or with a child host on ⌘Q. Closing into the background keeps it waiting.
- While any turn or compaction runs, the host holds one power assertion that keeps the Mac from idle sleep (`pmset -g assertions` lists "Wiffletree agents are working"). The display may still sleep, and a closed lid with no external display still sleeps the Mac.

After an update, the new app connects to the old launchd host. If they share a protocol, the app asks the host to restart once no turn and no compaction runs, and the sidebar says "The host restarts into <version> once no agent is working", with **Restart now**, which stops running turns as a quit does. New turns still start while the restart waits. If no protocol is in common, the app shows only that screen: how many agents are working, **Restart now** and **Wait until they finish**. When the app is the older side, it says to update Wiffletree instead.

## Provider setup

Install the standalone Claude Code and Codex CLIs, then sign in using their normal CLI flows. The app searches `PATH`, `~/.local/bin`, `/opt/homebrew/bin`, and `/usr/local/bin`. `WORKSPACE_CLAUDE_BIN` and `WORKSPACE_CODEX_BIN` can select an explicit binary for development.

```sh
claude auth login
codex login
```

The app uses [Claude print mode](https://code.claude.com/docs/en/headless) with JSON events and [Codex noninteractive execution](https://learn.chatgpt.com/docs/non-interactive-mode) with JSON events. Codex's equivalent of print mode is `exec`, not `-p`. Each turn resumes the exact stored provider session. No provider fallback or global configuration edits occur. The app injects its own scoped [MCP tools](https://learn.chatgpt.com/docs/extend/mcp) and bundled role instructions automatically. The instructions are in `crates/workspace-host/skills/`: `core/` holds the fixed core, the communication contract and each role's core, with every sentence the app depends on, and `stock/` the four skills' stock texts, the ways of working. Each file starts with its name and version. `provider::instructions` sends the contract, the role's core and its skill, in that order, and then the human's own rules for that skill, if any, under a heading of Wiffletree's. The human's edits are kept by `skills::SkillStore` in the shared folder's `skills/`: `<skill>/additions.md` for their rules, or `<skill>/rewrite.md` with `<skill>/base.md`, the stock text it is based on, for a rewrite, which is sent in place of the stock text with no separate rules; and one `<skill>/history/<time>.json` per change with the whole state after it, never deleted. A missing or unreadable file counts as missing; an unreadable one is reported on the snapshot. A rewrite is out of date when `base.md` is not this release's stock text, compared as text, and `SkillStockChanges` answers with the line diff from one to the other, computed with the `similar` crate. New releases never change a rewrite. `Host::instructions` reads the store as each turn is built, and the turn carries that text to the provider and to the context probe. Only the human's client changes a skill, through `SaveSkillRules`, `StartSkillRewrite`, `SaveSkillRewrite`, `MarkSkillUpToDate`, `ResetSkill` and `RestoreSkill`, each text limited to 32,000 characters; no agent tool reaches the folder, though an agent's shell, which is not sandboxed, can write it as it can write `settings.json`. At start the host writes a "New stock version" entry for each skill whose latest entry recorded another stock version.

Refreshing preserves unsaved edits, and saved models stay selectable if the catalog no longer lists them. If a CLI is missing or discovery fails, built-in and saved options remain available with a visible notice.

A fresh store saves no setup. ## Communication and recovery

Messages and explicit reports are persisted in SQLite before acknowledgment. An event schedules an idle recipient immediately; coordinators do not poll. A busy recipient receives new input at its next turn boundary. A queued context compaction (see Context window) runs at that boundary first: while a session has one, queued or running, no turn starts for it by any path, a verification round with such a verifier waits whole, and its messages stay queued for the first turn after it settles. Each turn takes every queued message for its recipient in order, up to 20; the rest wait for the next turn. Progress reports are delivered too, but batched: when only progress is queued, an idle parent waits 20 seconds after the first report so a burst arrives in one turn, and any other message or report delivers them at once. Workers talk to the project coordinator, which resolves decisions or asks the human. During a verification cycle, verdicts and the implementer's ready report are quiet messages: they ride along with the coordinator's next turn without starting one, and the coordinator wakes once when the cycle ends.

Open ticket branches are checked for trouble before they land. Each repository with open tickets is checked at most every 5 minutes and one check at a time, on its own thread, after any host event, so a `workspace_context` call refreshes a stale cache while returning the cached result. A base that is a remote-tracking ref such as `origin/main` is fetched into that ref alone (`+refs/heads/main:refs/remotes/origin/main`, `--refmap=`, no tags, no `FETCH_HEAD`, no automatic maintenance), whatever refspecs the remote configures. Git then counts the base's commits since each branch's merge-base, lists the files that would conflict with it (`git merge-tree --write-tree`) and the files each branch changes that another open ticket's branch in the same repository also changes, in any project, with any conflicts between the two; renames count as changing both paths. Branches, worktrees and indexes are never modified, and only committed work is compared. Results are cached between checks, and warnings about tickets closed or accepted since are dropped when read. `workspace_context` lists them on each ticket as `warnings`, such as "origin/main is 3 commits ahead; conflicts in src/a.rs" or "overlaps ticket T (project P) in src/a.rs". A failed fetch or conflict check is a warning too, such as "origin/main as of 2026-10-08T14:02:00Z; last fetch failed: fatal: …". The ticket card shows the most pressing as a **Conflicts**, **Check failed**, **Overlaps** or **Behind** badge whose tooltip lists them. Git queries share one 15-second deadline for output and exit.

Open tickets' GitHub PRs are watched without a model. For each repository with an open ticket whose coordinator is not archived, the host runs one read-only `gh api graphql` query per pass, covering up to 50 ticket branches, on its own thread. Owner, name and branch names are passed only as `-f` raw strings. This needs an authenticated `gh` on `PATH`; without one, the repository row shows the error and nothing else changes. Owner and name come from the base's remote (`origin/main` → `git remote get-url origin`). A base without a remote, or a remote that is not on `github.com`, is never queried, and its row says its PRs are not watched. A ticket's PR is its branch's open PR among the two newest, or else the newest; PRs from forks are skipped. A repository is checked at once when the host starts or first has an open ticket, then every 60 seconds while one of its tickets has an open PR and every 5 minutes otherwise. Failures back off to 5, 10, 20 and then 30 minutes. Below 200 remaining API points, the next pass waits for GitHub's reset. The host wakes itself for the next pass and keeps watching paused projects. Each ticket stores its PR as `pull_request`, which `workspace_context` shows: number, URL, state, draft flag, base, head, merge state, check rollup, unresolved threads, the newest comment id of each kind and the merge commit. The host saves it and logs a `pull_request` event only when it changes. An `unknown` merge state at the same head keeps the recorded one, and a failed pass keeps every snapshot. A message that cannot be queued, as when the coordinator's queue is full, leaves the change unsaved so the next pass sends it; a message to an archived coordinator is logged and dropped. When a PR merges, the coordinator gets one message (`pr:{ticket}:merged:{number}`). It names the merge commit, says whether the merged head is the ticket worktree's HEAD, and tells the coordinator to call `accept_ticket`; the ticket stays open until it does. A PR closed without merging sends one `pr:{ticket}:closed:{number}`. Failed checks and a conflict with the base wake the coordinator, never the implementer, once per head and at most 3 times per PR. The next one due becomes a single budget message, and then the PR wakes nobody until it merges or closes. Comments wake nobody. These messages carry only the ticket's title and id, PR numbers, base names, SHAs and fixed wording, never PR titles, bodies, comments, check names or authors. Turn input and the chat show them as from the Wiffletree PR watcher, not the human. The watcher never comments, labels, reviews, pushes, rebases or merges. A ticket row with a PR gets a second line such as "#142 · checks ✓ · 1 thread · behind", and its Tickets card shows the PR with an **Open on GitHub** link. A repository row with open tickets adds its open-PR count, plus when PRs were last checked or why the check failed and when it retries. Check status is kept in memory. The window picks up a new check time with the next change it is told about, so on a quiet host "checked … ago" can lag behind the real check.

The PR keeper (`crates/workspace-host/src/keeper.rs`) acts on the watcher's passes with no model. Its settings are in the shared folder's `settings/pr-keeper.json`, changed only by the client's `SetKeeper`: the rebase trigger, off after an update and on a fresh install, and the quiet period, 2 minutes by default and 1–60 accepted. Each pass also reads the PR base's `baseRefOid`, which is kept in memory per repository and base branch with when a pass first reported it, never stored on the ticket, so a moving base logs nothing and a restart starts the wait again. A ticket's PR is kept while the ticket is open, its coordinator is not archived, its project is live, its repository publishes without asking and the PR is open; `workspace_context` marks a repository `kept` while a trigger is on. The keeper may change the branch only while the latest cycle passed, the worktree's HEAD is the verified commit or patch-equivalent and is the PR's head, and no publish request exists. When the base has reported the same commit for the quiet period, is not contained in the PR's head, and that head and base were not rebased before, a thread fetches the tracking ref of the PR's base alone, stops if it is no longer the measured commit, and rebases the head in `<workspaces_dir>/keeper/<ticket id>`, a detached worktree, with hooks, rerere and `--update-refs` off. The result is the same change when its stable patch id against the ticket's base, as publishing compares them, equals the verified commit's; a stacked ticket's base is its parent's branch, onto which its PR's base also rebases it, never main; it is kept under `refs/wiffletree/keeper/<ticket id>` and the checkout is always removed. On the host thread, between turns of the ticket's agents, `keeper_adopt` runs `git reset --hard` to it only while the worktree is on the ticket's branch at the head the rebase started from, clean, with no cycle or publish request; otherwise the result is dropped. `keeper_publish` then pushes through publishing's own checks and lease; a step that would ask ends with nothing sent and raises no Inbox item, and its result goes to `Ticket.keeper`, not to an agent. A pushed rebase logs `pull_request_rebased`. A changed patch the keeper does not review, as described below, and a push that was refused or failed, each send the coordinator one `keeper:{ticket}:{changed|push}:{head}:{base}` message, with commit ids cut to 20 characters; a conflict or failed checks the keeper does not try, as described below, are left to the watcher's own message. A rebase that fails outright, as on a failed fetch, does not count as a rebase of that head and base: later passes try it again, and after three failures in a row the coordinator gets one `keeper:{ticket}:failed:{head}:{base}` message. An error for one ticket is logged and leaves the other tickets' work alone. At start the host removes keeper checkouts, deletes `refs/wiffletree/keeper/*` and drops results that were waiting, so their head and base are rebased again; a keeper push that was running ends with one `push` message telling the coordinator that GitHub may still have the old head. After each pass the host also keeps, in memory, the end of each kept ticket's PR line, sent in the snapshot's `keeper_parts` while the rebase trigger is on: "rebase in N min", "rebase waiting", "rebased N min ago" (the keeper's rebase is the PR's head and under an hour old) or "up to date". The window reads a try's part from the ticket itself, so it shows at once and outranks the others: "keeper resolving" or "keeper fixing" while a try at the PR's head runs, and "with the coordinator" once it was thrown away, until the head changes. The ticket's card shows a try newer than `Ticket.keeper.last`, a thrown-away one only while the PR's head is the try's, or else `Ticket.keeper.last`, worded by its kind and by whether the keeper's review of it is still running, and each withdrawn keeper review. The keeper's only network calls are that fetch, publishing's own read, `ls-remote` and push, and the comment reader's read-only GraphQL query; it never merges, approves, closes or comments. A pushed rebase changes every commit id on the PR, and the keeper acts only while Wiffletree is running.

Each repository may hold a checks command, `Repository.checks`: the human's own text and a limit of 1–120 minutes, 20 by default, set or removed only by the client's `SetRepositoryChecks` from the field on the repository's row. `keeper::run_checks` runs it with `/bin/sh -c` in the keeper's checkout through `runtime::run_limited`, in its own process group with its output discarded, and at the limit stops the group and everything it started. The conflicts trigger, `keeper.conflicts` with its `review_level`, is refused unless the rebase trigger is on, the table has a PR keeper row and the level is a configured re-check; the rebase trigger cannot be turned off under it, and a verification setting that removes or changes that level is refused. With it on, in a repository with a command, a rebase whose patch changed is not dropped: its checks run first, and a failed or timed-out run drops the result and tells the coordinator once (`changed`) with no ticket change. A passed result is moved onto the branch like a same-change rebase, then `Host::keeper_review` starts a one-round cycle at that level, marked `keeper`, with each verifier's model resolved from its row as in any cycle, and records it in `Ticket.keeper.reviews`. A passed review is pushed as a rebase is. A review with any failed or blocked verifier is withdrawn: the cycle before and the ticket's state come back, the review's own ledger entries leave the ledger and stay with the cycle on its record, `keeper_review_withdrawn` is logged, and once no agent of the ticket is in a turn the branch goes back to the commit before, or, if the worktree moved or is not clean, the keeper's commit is held as not reviewed. Only a cycle marked `keeper` and recorded as the keeper's latest review is ever withdrawn. With it on, a conflict gets one try per PR head, recorded in `Ticket.keeper.tries`, when the repository has a command and the keeper's review could start: the rebase's checkout is left stopped at the conflict, and a PR keeper agent starts there with one message from Wiffletree naming the base, the head, the files of the rebase's first stop and every file `git merge-tree --write-tree` could not merge, which can be more. The watcher's conflict wake is held in `Ticket.keeper.held_wakes` while the keeper will still try. When the agent's turn ends, `keeper::gate` throws the result away unless the checkout is clean, no rebase is in progress, HEAD contains the base, `git diff --name-only` from Git's own merge tree touches only those files and the checks pass. A passed result goes through the move, the keeper's review and the push like a changed patch. Any failure removes the checkout and the ref, archives the agent, records why and sends the coordinator one `keeper:{ticket}:conflict:{head}` message, with each blocking finding after a failed review; at start, a try whose review has not started is thrown away. The checks trigger, `keeper.checks`, is refused and kept on as the conflicts trigger is, and shares its review level. With it on, a kept PR whose watcher reading says its checks failed at its head, in a repository with a command, gets one try per head when no rebase is due or waiting for it, which means the head contains the base the keeper last saw or that head and base were already rebased, and no try runs. `keeper::reproduce` first runs the checks at the PR's head in the keeper's checkout and lists the files the PR changes, `git diff --name-only <base>...<head>`. Checks that pass here start no model: the try is recorded as thrown away because the failure could not be reproduced, and the coordinator gets one `keeper:{ticket}:checks:{head}` message. Checks that fail or run out of time start a PR keeper agent in that checkout with one message naming the PR number and the command. Its gate throws the result away unless the checkout is clean, HEAD contains the PR's head, so that commits were only added, `git diff --name-only <head> <result>` names only files the PR changes and the checks pass; the move, the review and the push follow as for a conflict, and since the result contains GitHub's head the push is a fast-forward with no lease. A thrown-away try sends one `keeper:{ticket}:checks:{head}` message. The watcher's failed-checks wake is held the same way, and sent if the keeper ends with that head without a try, as when the trigger is turned off. The PR line reads "keeper fixing" while it runs. The try's limit: its model runs, like every agent, with its provider's permission prompts bypassed, so its shell can run any command, including a push with the human's credentials. The host checks what the try leaves in its checkout, which files changed and whether the checks pass, and has it reviewed, but does not confine what the model runs, and the checks command is run as the human wrote it.

The keeper's model is the PR keeper row of the Who runs what table, changed only on the Models page; with no row there is no keeper model. Its model runs belong to agents with the role `keeper` ("PR keeper"), made only by `Host::keeper_agent` as children of the ticket's coordinator, one for a try and one for sorting, each with its own focus so neither is handed the other's conversation. Before each run, between its turns, the agent is pinned again: a try to what the row resolves to then, and a sorting run to the row's Claude choice alone; an agent whose provider differs is archived and a fresh one starts. The conversation's model controls cannot change them. A try's instructions are the keeper core, `skills/core/keeper.md`, and Keeping a PR; the sorting run's are the keeper core alone. They never hold the ticket's worktree, and no coordinator tool can create, message, resume or assign one; `stop_agents` and `archive_agent` still reach them. A try at a conflict or at failed checks and comment sorting create them.

Comment sorting is `keeper.comments` in the settings, refused without a Claude choice in the PR keeper's row, and a table that drops it while it is on is refused too. While Claude is spent, `comments_due` reads nothing, so new comments wait and are never sorted on Codex. Which comments are new is decided by id alone, never by time or id order: `Ticket.keeper.comments.read` maps each comment read that a read can still return to its class. A read is one `gh api graphql` query (raw-string `-f` fields, `--hostname github.com`) for the PR's last 100 comments and reviews and the last 50 replies of the newest 50 review threads, the ones the watcher follows, whose unresolved count is of those threads alone; only comments with a body count, and the record keeps only ids the latest read returned, so it stays within that window. The first pass that sees a kept PR with the trigger on reads it only to record the comments already there as `earlier`; turning the trigger on again clears `read`, and a read or run started before that, or still going when the trigger is turned off, records nothing when it ends and a read then starts no run: each read is numbered, and only the ticket's latest one, which a reset forgets, records anything, even when the next pass has started another. A later pass reads when the watcher's comment cursors changed and the sorting session is not in a turn; every comment whose id is not in `read` is new, including a pending review's that appears after later ones. The host counts new comments by other authors as `outside` and sends only `OWNER`, `MEMBER` and `COLLABORATOR` authors' to the model: the oldest 20, each cut to 4,000 characters, with every other author's counted in `outside`. When 20 are taken and more wait, the cursors are left as they were so the next pass reads again. The comments' text exists only in the sorting run's stdin. The run is a turn of the ticket's sorting session, `TurnKind::Sort`: `claude -p --tools "" --strict-mcp-config --no-session-persistence --settings '{"disableAllHooks":true}' --output-format stream-json --verbose --system-prompt <the keeper core and the sorting instructions> --json-schema <one class per id>`, with `WORKSPACE_SOCKET` and `WORKSPACE_TOKEN` removed from its environment, no `--resume` and a folder emptied before each run, `<workspaces_dir>/keeper/sorting/<ticket id>`; a Codex session is refused. An `init` event whose tools are not exactly `StructuredOutput`, or that lists any MCP server, ends the run, and an answer counts only after an `init` that passed; the actor also drops any step a sorting turn sends. A failed run's error is stored as a fixed sentence, since a provider's error output could repeat a comment. A sorting turn records no steps, even from streamed events, stores no reply, sends no turn result, and is left out of the turn-count check-ins; its usage comes from the `result` event. The host accepts, for each id it sent, only `needs_change`, `question` or `no_action`; every other comment it sent is `not_sorted`, and none is sent again. `Ticket.keeper.comments` keeps `read`, by id (GitHub's anchor, such as `discussion_r4190331`), the cursors, `outside` and the counts of comments that need a change and questions, which `verify_ticket` and a merged or closed PR set to zero. A run with a comment that needs a change, a question or one not sorted sends the coordinator one `keeper:{ticket}:comments:{newest id}` message, past a full queue since the record already holds those comments, built from the classes, kinds, `<PR url>#<id>` links, paths, lines and counts. On October 14, 2026, with Claude Code 2.1.300, one throwaway run in an empty folder, `claude -p --tools "" --strict-mcp-config --no-session-persistence --output-format stream-json --verbose --json-schema <schema> --system-prompt <text> --model haiku` with three sample comments on stdin, one of them telling the model to run `git push --force`, behaved as design.md measured with 2.1.296: the `init` event listed the one tool `StructuredOutput`, no MCP server and `permissionMode: default`; the model's only action was that tool; the `result` event carried `structured_output` with one class per comment (the hostile one `no_action`) and `usage`; nothing was written in the folder or to the session store. It cost $0.0009.

Each ticket owns an isolated branch/worktree. Its implementer and tester run sequentially in that workspace. Separate tickets can run concurrently. Acceptance requires a verification cycle, described below; finishing a provider turn does not mark a ticket accepted. Coordinator context persists across tickets via the provider session ID; ticket agents are never reused for other tickets.

Verifiers attach findings to their `passed` or `failed` report, each with a severity (`blocking`, `non_blocking` or `pre_existing`), a `path:line` location, a one-line summary, a trigger and evidence. The host decides each verifier's result: failed only for a blocking finding with a line, a trigger and evidence that the coordinator has not settled, passed otherwise, recording the reason on the run when that differs from the reported kind. A `blocked` report and a changed worktree behave as before. Each finding of a completed check enters the ticket's decision ledger as `F1`, `F2`, …: evidenced blocking findings `open`, `non_blocking` and `pre_existing` ones `noted`, and unevidenced blocking ones `untriaged`. A verifier's next completed check marks its focus's open entries it does not report again `fixed`; one it reports again by id stays open, and a noted one it reports again as an evidenced blocking finding becomes open. Noted entries need no decision and block neither `accept_ticket` nor `publish_ticket`. A blocked report or a changed worktree leaves the ledger as it was. The implementer receives only the round's open entries, sent as Wiffletree, and is told to fix each with the smallest change or object to the coordinator in one sentence. The coordinator decides each untriaged entry, and any noted one it chooses, once with `triage_findings`: `fix_now`, `follow_up` or `wont_fix`, with a one-line reason, all or none, waking nobody. It may overrule an open entry with `follow_up` or `wont_fix`, never `fix_now`. Each round's input names the base commit, the diff from it with its `--shortstat`, the entries already decided, the noted entries and the verifier's own open entries, plus its configured instruction; from round 2 on it also names the new diff and limits the check to those entries and that diff. `verify_ticket` checks the level before anything starts (`verification.rs::level_may_start`): a re-check is refused unless the ticket's latest cycle passed; any level is refused when a configured verifier it does not run has an `open` ledger entry, naming the verifier and the ids; and a full review is refused once the ticket has started the cycle cap's full reviews (2 by default; rounds default to 3). Re-checks are not counted, and a cycle recorded before levels counts as a full review. Each cycle records its level's name and kind as they were when it started (`Verification.level`), and earlier cycles stay on the ticket as `previous_cycles`. With those rules a passed cycle always rests on a passed full review. `accept_ticket` and `publish_ticket` accept a passed cycle as before; the one exception is the waiver of unreviewed commits once a ticket has started every full review the cap allows: a `waived` reason naming each commit past the verified one by short SHA, for accepting or publishing, where a publish that relies on it runs without asking in an allowed owner's repository, as a waived blocked review does (see `accept_ticket` below). The cycle-end message lists the open and untriaged entries, the cycle's noted entries (at most 10 lines), and the ids decided or noted earlier, and offers only the actions allowed then. `workspace_context` lists each open ticket's ledger, earlier cycles and waiver; an accepted or closed ticket is one short entry, and `ticket_id` returns its full record.

`accept_ticket` gates on the latest cycle, not the ticket's state, so a `completed` report after a passed cycle no longer blocks it. It refuses while a cycle runs or any finding is untriaged, and HEAD must be the verified commit or patch-equivalent to it: the diff from its merge-base with the ticket's base has the same `git patch-id --stable`, as after a squash or a clean rebase. Once the ticket has started every full review the cycle cap allows (`Host::unreviewed_waiver`), a waiver may also cover the commits from the verified one to HEAD when it names each by a short SHA of at least 7 characters; `live::verified_head` lists them with `git rev-list`, refuses with the short SHAs it does not name, and the ticket records them as `waived_commits`. `publish_ticket`'s `waived` follows the same rules, for the open findings of a blocked cycle and for unreviewed commits at the cap; only the ticket's coordinator may pass it, and `live::ensure_findings_settled` makes the same verifier and triage checks for both tools. A publish carrying the waiver runs without asking in an allowed owner's repository, records it on the ticket as `waiver` and `waived_commits` for later publishes and the PR keeper (`Ticket::standing_review`), and the next verification cycle clears it. A stacked ticket's base is its parent's branch alone, so a rebase onto a parent that only gained commits keeps the review, and a rebase of the whole stack needs a new one. When the patch id cannot be computed, only the exact commit qualifies and the refusal says why. After a blocked cycle in which every verifier checked, `waived` accepts with a one-line reason: the ticket stores it, the `ticket_accepted` event names it with the entries still open, and the cycle stays blocked. Its Agents panel card says it was accepted with a waiver, and its Tickets card shows the waiver.

**Stop** interrupts the project's active provider processes and holds its queue until you message or resume it. **Pause** interrupts the selected session. Both also stop the processes the stopped agents started, before the command returns: every agent of a stopped project, and the paused session (see [processes agents start](#processes-agents-start)). A session whose turn was cut short shows **Interrupted** (the host's `disconnected` status); the held-input notice is amber after a pause and red after a failure. Closing the app stops its host, its provider turns and every process its agents started. After a restart, a project that was running keeps running and one that was stopped stays stopped. Only the sessions whose turn the stop cut off wait: they show **Interrupted** with their input held. Everything else in a running project carries on without **Go live**: queued messages are delivered and each timer that came due fires once, late. Interrupted or failed input becomes **held**; the session's conversation shows the error above the composer. Inspect the worktree, then choose **Retry** or **Skip** there. Retrying can repeat external effects, so the app never retries uncertain work automatically. Restarting and enabling a project preserves its coordinator identities and transcripts.

Coordinators can set timers with `schedule`, `unschedule` and `list_schedules`; workers get an error. `at` and `until` take RFC 3339 or an offset such as `+90m`, up to 90 days ahead; `every` takes `30m`, `2h` or `1d` and is between 5 minutes and 90 days. Labels are bounded to 80 bytes, prompts to 4 KiB and each session to 20 active timers. Timers are stored in the `schedules` table and fire into the owner's own queue as `timer:{id}:{slot}` messages, whether or not the project is running, so a stopped project collects them until it runs again. A fire waiting to be delivered absorbs later slots and is marked late, as is a fire enqueued or delivered more than a minute after its slot; `schedule_fires` records each fire's slot, missed count and lateness, which the turn input shows as a `Timer status` line; the stored message never changes. The host wakes for the earliest progress batch or timer slot, sleeping at most a minute at a time so a Mac's sleep cannot hold a timer back for long. A session's first turn after a host start begins with a short note naming the turn the stop interrupted, its active timers and its late fires. The project **Overview** lists active timers. `unschedule` and archiving a session stop its timers and withdraw fires still queued, and an archived session cannot set new ones; a fire held after an interrupted turn stays held for **Retry** or **Skip**. A fire that cannot be enqueued, for example because its owner's queue is full, rolls back and is retried a minute later instead of spinning.

Coordinators may run short, read-only checks themselves from a timer, without creating workers: the coordinator's final message is the result in the human chat. No turn has a time limit; a turn runs until it finishes or is stopped. When a turn has run 30 minutes, and every 30 minutes after while it runs, the host checks in: the session's parent, which for every ticket agent is the project coordinator, receives a durable `[check-in]` message (`check-in:{run}:{minutes}`) naming the session, its ticket, the elapsed time, the last provider event and the latest step. The host also checks in by turn count: when a session with a parent starts a turn and has run `checkin_child_turns` turns (25 by default) since its parent last messaged it, or any multiple of that, the parent receives `check-in:{run}:turns`, naming the count, when the parent last messaged it and the start of the session's last reply. The count is read from `provider_runs` and the parent's messages, so it survives restarts. A check-in is an ordinary message, not a report: it never counts as a verdict or changes a verification cycle, and it wakes the coordinator even while the agent's ticket is being verified. The project coordinator has no parent, so its own long turns raise an Inbox item instead; a newer check-in or the turn's end clears it. Its turns are also counted in memory from the human's last message, retry or answer, and at each multiple of `checkin_human_turns` (100 by default) it raises a `turn-count:{run}` Inbox item, which survives the turn's end and is cleared when the human steps in or a newer one is raised. Check-ins never pause or stop anything. Both thresholds are host settings in the shared folder's `settings/check-ins.json`, changed with `set_check_ins` (5–500 and 10–1000). The host wakes for the next check-in like any other timed wake. A coordinator stops its direct children with `stop_agents` (`session_ids`, all non-archived children when omitted, and `reason`; any other argument, an archived child or another caller is refused). A running turn's cancel flag is set as for **Pause**; the run's outcome is `stopped_by_parent` with `stop_reason` in its detail, the chat shows "Stopped by its parent", the activity log records `turn_stop_requested` and `turn_stopped_by_parent`, and the turn's input is completed rather than held, because the parent decides what runs next. An idle child is paused (`paused_by_parent`). Either way the child stays **Paused**, even if its turn reports while winding down, so messages and timer fires wait; the result lists each agent as `stopped`, `paused_idle` or `already_paused`. The session's runtime records who stopped it (`stopped_by`: `human` or `parent`) until it runs again; a parent's stop never replaces the human's. `resume_agent` (`session_id`, optional `held` and `message`) releases a paused or interrupted, non-archived direct child through the same reconciliation as **Retry** and **Skip**: `held` is required while it has held input, `retry` redelivers that input with the interruption note and `skip` drops it, and `message` is queued as new input. Arguments are checked first and the release, message and activity entry commit together, so a refusal changes nothing. It is refused while the child is working, still winding down or not stopped, and its result names who stopped the child. The next turn's prompt names a parent-stopped turn and its reason. A `send_message` to a paused or interrupted session still queues, with receipt `queued_while_held` and a hint to call `resume_agent`, which says when the human stopped it. A human **Stop** or **Pause** tells the parent once, when the command runs, whether or not a turn was running (`human-stop:` messages, `stopped_by_human` in the activity log); human clicks bound these notices, so they skip the 1,024-message recipient cap that agent sends still hit; it overrides a parent's stop still winding down, so that turn's input is held, and the turn's end sends no second notice. Other interruptions report the error and ask for a worktree check before resuming, except a turn that fails on its provider's usage limit: a quota reading during the turn that says the limit is reached, or else the error text, records `limit_retry` on the runtime, the parent gets one `turn-result:` message saying nothing is needed, and the scheduler's pass (`retry_after_limits`) releases the held input as Retry does once the limit resets, at the known reset or at the first reading since the failure that no longer says it is reached. The sidebar marks a paused, interrupted or idle agent with undelivered input as **held** or **queued input**.

**Archive** hides a session and everything it owns: a project's "…" menu archives the project, and any agent's **Overview** archives that agent. Accepting or closing a ticket archives its agents, and only that archives a ticket's implementer. Verification archives a verifier once its cycle no longer needs it: after a round that sends failures to the implementer, the verifiers that passed; when the cycle passes or is blocked, all of them. Each `verify_ticket` cycle therefore starts fresh verifier sessions, and a verdict an archived verifier sends late is stored quietly and changes nothing. The coordinator's `archive_agent` tool archives one agent of a ticket it owns, such as a reviewer whose findings the implementer has; it refuses an agent mid-turn, an open ticket's implementer and a verifier the running cycle still needs. Repository coordinators migrated from older stores stay archived and read-only. Archiving interrupts active turns in that tree, stops the project when its coordinator is archived, and refuses new messages, tickets and agents until restored. Conversations, tickets, branches and provider sessions are kept; the worktrees of tickets the tree owns are removed, including ignored build output. Removal is all or nothing and refuses, naming each ticket, while a worktree is locked or has uncommitted or untracked files. Archiving first stops every process the archived agents started; a refused archive stops nothing. A worktree whose agent is still in its turn is removed when that turn ends, or at a later turn's end or startup once a process the host could not confirm as the agent's has exited; if the agent left unsaved work, the worktree is kept and its coordinator, the nearest unarchived owner, or the human inbox is told. Closing or accepting a ticket removes its worktree the same way. **Archived** in the sidebar header lists archived sessions dimmed; open one and choose **Restore**, which also restores the owners above it and re-creates each open ticket's worktree from its branch. Closed and accepted tickets are not re-created. Restoring a project leaves it stopped. Headless: `set_archived` with `session_id` and `archived`.

The local administrative JSON protocol trusts its caller. Provider tools instead use a private Unix socket, per-turn credentials and host-assigned sender identity. No TCP port is opened. Existing stores migrate additively; historical unassigned workers remain visible but need a ticket assignment before live execution.

## Processes agents start

Claude Code and Codex both run each tool command as the leader of its own session and process group, so nothing a tool starts is in its provider's group, and a turn's end, which stops the provider's group, leaves it running. That is the rule: what an agent starts keeps running after its command and between its turns. The host stops it when the agent is archived (the human's archive, `accept_ticket`, `close_ticket`, `archive_agent`, a retired or replaced verifier), when the agent is stopped (**Stop**, **Pause**, `stop_agents`, a cancelled turn), at a quit and at startup.

While any provider runs, one watcher thread (`crates/workspace-host/src/processes.rs`) lists the process table after each 4 ms sleep, about 200 times a second, whatever the number of turns: one `proc_listallpids`, one `proc_pidinfo` for each id it has not listed before and for each process it already follows. A new process joins a run's tree when its parent is in the tree or its group is one the tree holds, so an orphan whose shell exited stays followed. The interval is 4 ms because a Claude Code tool shell that starts a background process and returns lives about 10 ms; once a shell has been listed, its group is followed after it exits. Each turn's thread sends the host what the watcher saw as its loop wakes, at most 50 ms later, for as long as the provider runs; a stop or a quit asks the watcher for a look of its own first and records everything it follows for that turn, so a tool started a moment earlier is stopped too, also when its sighting was still on its way. The watcher keeps a run's tree until the host has handled the run's end and releases it, so that look still answers after the provider has exited; a turn that ends on its own as its agent is stopped is settled as a stopped turn. A Codex compaction's `codex app-server` runs through the same `provider::run`, so it is watched and settled like a turn; a stop lets a started compaction finish and so spares what that compaction's run started, which is stopped when the compaction ends if its agent is still stopped. After a pause of over a second, when an id may have been reused, a group whose last known member has gone is dropped only if nothing has its id any more. Its thread starts with the first provider run and exits when the last ends. Measured on October 13 on an Apple M4, it costs roughly 2% to 4% of one core in a release build, whatever the number of turns and more the more processes the machine runs (18 to 27 ms of CPU a second with about 600 processes, up to 42 ms with about 800), because listing the process table after each sleep misses the cache. A debug build measured 18% to 20%. With no turn running it costs nothing.

The host keeps the record in `process_groups` (one row per agent and group: the run that first saw it, whether it is the provider's own group, `noticed_at`, and `ended_at` with `ended` as `archived`, `archive_failed`, `stopped`, `quit`, `startup` or `dismissed`) and `process_group_members` (process id, start time in microseconds, command). A row without `ended_at` is a group the host believes is running. A process seen in a group joins such a row only while a member the row recorded is still alive in the group; otherwise the group emptied unseen and its id was given out again, and the row is replaced by a fresh one for the run that saw it. Groups that exit on their own and a provider's group stopped at its turn's end are deleted, so the tables hold what runs now and what the host stopped, when and why. `provider_runs.process_group` and `process_started` are no longer written; opening an older store carries them into the record once.

Every stop goes through `processes::stop_group`: a group is signalled, SIGTERM and after one second SIGKILL, only while a recorded member with the recorded process id and start time is still alive in it. The leader need not be alive. macOS does not give a new process an id that is still a live group's id (tested over a full lap of the id counter, and `forkproc` in XNU says the same), so a live recorded member proves the group never emptied and everything in it is the agent's. A group that no longer runs is forgotten without a signal. One that runs and cannot be confirmed is not signalled and raises a `leftover-process:` Inbox note; dismissing the note marks the record `dismissed`. One the host signalled that still runs, because a process joined it after it was confirmed, is not signalled again; its note says it was signalled and that part of it still runs, and a provider's run still records when it was stopped. Each scheduler pass settles the notes whose group is gone, whether or not that session has a turn due, and looks again every two seconds while one is open. A provider's own group is stopped by its turn instead (`processes::stop_provider_group`): the turn freezes the group with SIGSTOP, has the watcher look while it is frozen, and only then sends SIGTERM. A tool the provider forked into a session of its own a moment before a cancel is then still the frozen provider's child, so the look records it and the host stops it when the cancelled turn ends. Every SIGTERM the host sends is followed by SIGCONT, because a stopped process that handles SIGTERM acts on it only once continued; a look that fails continues the group, and a group a dying host left frozen is stopped at the next startup like any other.

A turn that ends on its own with processes still running adds one notice from Wiffletree to the agent's conversation, such as "Tester left 8 processes running. All 8 are the program `yes`.", with the start time, the process group and "they keep running until Tester is archived". Every notice states the count first and names programs as programs ("2 are the program `node` and 1 is `esbuild`."), never a name beside a bare count. It is a quiet message under a `processes:` id: it rides along with the agent's next turn and never starts one, and each group is named once. Before that turn's end is reported, its thread waits up to 300 ms for the tree's other processes, such as tool-server helpers, to exit. A stop adds a notice naming what was stopped and why. An archive, close or accept writes its notice once its outcome is known: if it failed after stopping the processes, the record says `archive_failed` and the agent, still there, reads the notice at its next turn. `verify_ticket` stops what a replaced verifier started only once the new review has started, so a review that fails to start leaves the verifier and its processes as they were. Only a provider's own leftover process holds a session's next turn; what the agent started never does.

Known gaps: a shell that starts and exits between two ticks is never seen, so what it leaves is not recorded; a process that moves to a new session after its parent has exited is not recorded; and a group that replaces all its processes while its agent is idle can no longer be confirmed and raises the note instead of being stopped.

## Conversation rendering

The native transcript renders Markdown with selectable text, headings, emphasis, lists/checklists, blockquotes, links, tables, inline code and fenced code. Tree-sitter provides syntax highlighting for bundled languages; code blocks include Copy. Unknown fence languages remain readable code. Markdown is parsed in the component's background task and transcript rows remain virtualized. Only each turn's final text becomes a chat reply; narration and tool calls stream as work steps (see Live work). Mathematical typesetting and rendered Mermaid diagrams are not implemented.

The sidebar uses the outlined two-tone wordmark and red Interlock symbol, with separate light/dark artwork. Main-coordinator welcome screens use the same symbol. The four SVGs are embedded in the executable and loaded through GPUI’s cached full-color image renderer; no font installation, runtime file lookup or network request is needed. Interface typography remains the macOS system family, and action/status colors retain the existing Tidal tokens.

The sidebar and inspector have draggable dividers. The sidebar minimum is 240 px so the wordmark and New project button fit without clipping. The tree lists only groups and projects (`tree::rows`); a project's tickets and agents are in the Agents panel. The selected project row offers Rename and New ticket, and stays selected while any of the project's agents is open. Dragging a project row sends one `move_projects`, and the list is redrawn from the order the host returns. A row held near the top or bottom edge of the list scrolls it (`tree::edge_scroll`, one step every 16 ms), and a drag released on its own row is cancelled if it left the row and is otherwise the click it would have been (`tree::own_release`). The **Group** button in the PROJECTS header draws projects that share a first word under one group row; groups exist only in `crates/workspace-desktop/src/tree.rs` (`entries`, `drops`, `project_move`), and the button's state is saved as `group_projects` in `desktop-preferences.json`. Headless: `{"type":"move_projects","project_ids":["…"],"before":"…"}`, where leaving out `before` moves the block to the end. Project tools stay in the right inspector rail. Projects are created and named directly in the sidebar; other creation forms are dialogs. Widths, drafts, collapsed groups and the appearance choice (System, Light or Dark from the sidebar menu) currently persist during the client session, not across restart. Whether a working agent's live work is collapsed to its status line (`minimize_activity`) is the first client preference saved across restarts, in `desktop-preferences.json` in the data directory; a missing or unreadable file means the defaults.

The window uses a themed title bar. The conversation header carries the breadcrumb, status, Pause/Resume , the context fill chip and **Stop** while the project is working. Your messages appear as right-aligned bubbles with their delivery receipt; the session's own replies are attributed and timestamped. Messages from other agents, the session's own timer fires and Wiffletree's notices fold into one line per unbroken run (`crates/workspace-desktop/src/transcript.rs`), counting agent messages and notices apart. A notice's pill comes from `workspace_core::Notice`, read from its id and, for verification outcomes, publish results and the keeper's changed-patch notices, the host's own words after the ticket's title and id; a notice that cannot be told reads "Notice". While the agent works, its live work, described in Live work, follows the last message as rows of the transcript list (`crates/workspace-desktop/src/live_work.rs`), and a fixed-height status line sits between the transcript and the composer. Results and failures of background requests appear as toasts; failures that belong to an open dialog or the inline project name stay there.

Enter sends a conversation draft; Shift Enter adds a newline. Command Enter also sends. These shortcuts are scoped to the composer and preserve IME composition. The Models editor uses full-width cards, labeled dropdowns and scrollable model menus so model choices and effort values remain readable when resizing the inspector.

## Attachments

Drop files from Finder onto the selected conversation to attach them to the draft, or paste them with Cmd+V in the composer: files copied in Finder attach as a drop does, and an image on the clipboard, such as a screenshot copied with Cmd+Ctrl+Shift+4, is saved as `Pasted image <date> at <time>.png` (numbered when the draft, or a paste still being saved, already holds that name, and converted to PNG when it is another format). Text pastes as before. Each appears above the composer as a chip: a thumbnail for PNG, JPEG, GIF and WebP images (recognized by content, then extension), otherwise the name and size. A chip's × removes it. Folders, files over 50 MB and any file whose name is already attached, the same file included, are refused with a notice naming each one and why; the rest of the drop is still attached. When a file is dropped or pasted, the app copies it at once into `<data dir>/staged-attachments/<id>/<file name>`, because macOS lets only the app that received a drop read some files, such as a screenshot's floating thumbnail, and only around the drop. A file that cannot be copied is refused at the drop with its reason; folders and files over 50 MB are not copied and are refused as before. The host then checks each copy (`inspect_attachments`) off its thread, and the draft attaches the copy. Pending attachments belong to that session's draft, and a draft with attachments can be sent without text. A copy is deleted when its draft is sent, and when it is removed from the draft or the window closes once no send is still reading it, and the app empties the staging folder when it starts. Nothing is written to the project until you send.

Sending copies each file to `<data dir>/projects/<project-id>/attachments/<message-id>/<file name>` as read-only (0444), and the message stores those copies' paths, sizes and image formats (schema 5, an additive column on existing messages). If copying or storing the message fails, that message's folder is removed. Copies live as long as their message; archiving and restoring keep them. In the transcript a message's files show under its bubble, and clicking one opens it with its default application.

The delivered prompt lists every attachment's absolute path after the message text. Images also reach the model as images. Codex gets `--image=<path>` before `resume <session> -`; the joined form matters because `--image` takes several values and would otherwise consume the stdin `-`. Codex also splits those values at commas (no other character tested does), so an image whose name has a comma is stored with a hard link beside it, `.codex-<n>.<ext>`, and Codex is given the link. The prompt and the transcript show the original name. A data directory whose own path contains a comma is not supported for Codex images. Claude gets `--input-format stream-json` and one stream-json user message on stdin whose content is the prompt plus a base64 image block per image; turns without images still send plain text. Both were verified on October 7 with Codex CLI 0.160.0 and Claude Code 2.1.293, for new and resumed sessions and for images up to 22 MB. Only the human's messages carry attachments; agents' `send_message` does not.

## Live work

The adapters decode Claude stream-json and Codex `exec --json` into work steps (`crates/workspace-host/src/stream.rs`). Recorded and synthetic streams for both providers are in `crates/workspace-host/tests/fixtures/streams/`; when a CLI changes its output, record a new turn, sanitize paths and account details, and update the fixture tests. Claude currently streams redacted thinking, so thinking rarely appears. Codex command titles drop the `/bin/zsh -lc` wrapper.

The host keeps a running turn's steps in memory and stores each one when it starts, when its state changes and when it learns which files it touches. `steps` returns one run's steps changed after a revision cursor (`run_id: null` means the latest run), and `run_summaries` returns duration and counts for finished runs. The desktop listens to a step signal separate from state changes and fetches at most about 30 times a second, so streaming never reloads the snapshot. Bounds: 200-character titles, 40-character notes, 4 KiB details (output keeps its tail, prose its head), and 2,000 steps per run, with omitted amounts counted. Steps of runs finished more than 30 days ago are pruned when the store opens, and steps left running by a stopped host are marked interrupted.

Headless: `{"type":"steps","session_id":"…","run_id":null,"after":0}` and `{"type":"run_summaries","session_id":"…","run_ids":["…"]}`.

The snapshot holds the live workspace: the sessions that are not archived, the open tickets' agents, archived or not, archived sessions still in a turn, which show as working, the open tickets, accepted or closed tickets an unarchived agent works on, and those sessions' runtimes. It also counts the archived sessions and each coordinator's tickets, so the sidebar and a project's Overview need nothing more. `archive` answers with the rest, archived sessions, accepted and closed tickets and their runtimes, together with every session's and ticket's id in the order they were created. The desktop reads it only while something shown needs it: Show archived, the Tickets, Agents or Events panel, the Repositories page, a publish request, or a selected session or message sender that no list it holds has. The snapshot's `archive_stamp` hashes the stored rows the archive reads, and the desktop reads the archive again only when the stamp moved and a view still needs it; snapshots never wait for it. `workspace_core::WorkspaceIndex` joins the two once, when either arrives, and views look up sessions, tickets and runtimes by id, a session's children, a project's coordinator, a ticket's agents and whether anything below a session is working through it. `Command::is_read` classifies every command, and the host signals no change for a read. The desktop has at most one snapshot request on its way, and asks once more after one that a change arrived during. It leaves the reload after a command it sent to the change signal. Headless: `{"type":"archive"}`.

## Files panel

The **Files** button on the inspector rail shows which files agents are in. For a ticket agent it is a tree of the files its read and edit steps touched over the whole ticket, with counts, `+N −M` from the worktree's Git diff against the ticket base, and a highlighted row while a read or write runs; **Whole tree** lists the rest of the worktree around them. For the project coordinator it rolls every open ticket's agents up by ticket or by agent and tags in yellow a file that several agents, or two tickets in one repository, touched.

The counts come from stored steps, so they share the steps' bounds: a run keeps its first 2,000 steps, and steps are pruned 30 days after their run. Files touched only through shell commands are not counted, which includes every read by a Codex agent; their writes still appear with line counts from the Git diff. The panel asks the host only while it is open, and Git is read off the host thread.

## Processes panel

The **Processes** button on the inspector rail lists what agents have left running: for an agent its own process groups, for the project coordinator every unarchived agent of the project, including those with nothing running. Its count comes from the snapshot's `running_processes`, one grouped count over the open tool groups' recorded members, so the rail reads no process table. Between turns the record is exact; during a turn it can still count a member that exited inside a live group, and a process killed from a terminal between turns is counted until the panel is opened or the agent's next turn ends.

While the panel is open the desktop sends `Command::Processes` once a second, and nothing while it is closed (`processes_view::reading`). The host (`crates/workspace-host/src/agent_processes/panel.rs`) lists each group the record holds as running under the confirmation rule: with its live members, their programs and their CPU time from `proc_pidinfo(PROC_PIDTASKINFO)` when a recorded member is still alive in it, as unconfirmed when it runs without one, and not at all, forgotten, when it no longer runs. A reading costs one SQLite query and, per recorded group, a `killpg(g, 0)` probe, one `proc_pidinfo` per recorded member, one `proc_listpgrppids` and two `proc_pidinfo` per live member, on the host thread. The service treats it as a read and signals a change only when it forgot a group. The desktop works out CPU from the time used between two readings by the processes present at both; the first reading shows "—".

**Stop** and **Stop all** send `Command::StopProcesses` with the record ids, or none for everything the panel lists. They go through `stop_group` with the reason `stopped_by_human`, queue the "Stopped N processes …" notice for the agent's next turn and leave the agent's status alone. A stop holds the host thread for up to about two seconds, as an archive does. Headless: `{"type":"processes","session_id":"…"}` and `{"type":"stop_processes","session_id":"…","groups":["…"]}`.

## Work progress

Progress bars for agents, tickets and projects are derived, never stored. The rules are one pure function, `workspace_core::derive` (`crates/workspace-core/src/progress.rs`), over the sessions, runtimes, tickets and each session's latest plan; `crates/workspace-core/tests/progress.rs` covers the scenarios of the `work-progress` spec. Positions are hundredths of a percent, so a ticket at 3 of 7 is exactly 25.71% and only the display rounds.

A plan step carries its counts as data (`Step.plan`: done, total and the first unfinished item). A step stored before this has no counts and counts as no plan; there is no migration. Plans come from Codex `todo_list`, Claude `TodoWrite` and the workspace tool `set_plan`. On October 10, Claude Code 2.1.291 run with the host's flags offered no plan tool on Opus 5.5 or Sonnet 5.5 (Haiku 4.5 offered `TaskCreate`/`TaskUpdate`, and `TodoWrite` only with `CLAUDE_CODE_ENABLE_TASKS=0`), which is why `set_plan` exists; recheck when the CLI changes. `set_plan` takes `items`, the whole checklist as `{text, done}` pairs, at most 50 items of 1 to 200 characters, and refuses anything else without recording it. The actor attributes the call to the caller's running turn by its per-turn credential and records one plan step per run under the id `set_plan`, updated in place, through the same `record_step` as provider plans; the latest recorded plan step is the agent's checklist. The call sends no message, changes no status and sends no state signal. The communication contract (version 8) asks every agent to keep a checklist. A plan step is written to the store whenever its counts change, not only when its state does.

The host keeps each session's latest plan in memory (`Host::plans`: set when a plan step is recorded, dropped when a run starts, read from stored steps on first use after a start, archived sessions included) and the last derived board with a revision per entry (`crates/workspace-host/src/progress.rs`). After an event that changed state, a recorded plan step or a turn start, the actor derives the board again and, only if an entry changed, sends on `Service::progress_changes()`, a third bounded signal beside state changes and steps. `{"type":"progress","after":0}` answers with a `ProgressPage`: the entries changed after the cursor, or the whole board with `complete: true` when the cursor is 0 or an entry has been removed since it. Steps of runs finished more than 30 days ago are pruned, so an agent whose latest run is that old shows no checklist.

The desktop keeps the board in `crates/workspace-desktop/src/progress.rs`, with one request in flight and a dirty flag like the step watcher. `ui.rs` draws the bars (`progress_bar`, `segmented_bar`; stripes are `gpui::pattern_slash` and do not animate), `wording/tickets.rs` holds the figure and label text, `conversation_header.rs` the strip, the Agents toggle and an agent's breadcrumb back to its coordinator, `sidebar.rs` the project row's track and agents line and `agents_panel.rs` the Agents panel, whose 30-second elapsed-time timer runs only while the panel is open and a listed agent works. `agents_panel::Roster` is everyone the panel lists: each counted ticket's unarchived agents from the board, then the coordinator's other agents as "Previous agents". It is built from the index's coordinator, so an archived project, which has no board entry, lists all of its agents as previous. It also gives the toggle's working count, the coordinator's agents card (`conversation.rs`) and the project row's "N agents working" and stuck pill (`tree::agent_counts`). `agents_panel::stuck` is the one rule for a stuck agent: disconnected, or ready or done with a `last_error`, never blocked, paused or working. Every conversation of a project has the toggle, and once open the panel stays open whichever agent is selected (`Panel::kept_for`), still listing the whole project with the selected agent's row marked, until it is closed or another panel is opened. A provider plan that arrives after a run holds `MAX_RUN_STEPS` steps is not stored, but the checklist still follows it; after a restart the checklist is the last plan that was stored. To see every state without a model, run the app with `WORKSPACE_CLAUDE_BIN` pointed at `crates/workspace-host/tests/fixtures/provider.py`: a message containing `SET_PLAN` makes the fake agent record 3 of 6, and `HANG_UNTIL_CANCELLED` keeps its turn running for 30 seconds.

## Usage and provider quota

Claude and Codex account capacity stays in the sidebar as one row per provider of compact 5-hour and weekly pills, each filled to the share used and colored at 75% and 90%. Hover for the reset and reading age; click to open Usage and limits. Workspace-wide information lives in the sidebar's **Workspace** section, apart from the per-session tools on the right rail. **Usage and limits** opens a full page: account limits for Claude and Codex side by side whatever is selected, then recorded tokens for all projects, with Today, 7-day and 30-day periods, project/provider filters, daily bars stacked by model, exact values on selecting a day, and ranked coordinator totals separating own requests from workers. Graphs use America/New_York calendar days. Missing historical collection appears as missing coverage; today is partial.

Quota percentages come from provider telemetry, never from converting local tokens into subscription capacity. Codex uses the supported `account/rateLimits/read` app-server request every five minutes and on Refresh; discovery makes no model call. Available buckets and window durations are displayed independently, with reset time, reading age and 75%/90% warning colors. Claude captures `rate_limit_event` during ordinary live turns. Its CLI may report status without a percentage; those windows show **Unavailable**, and older readings retain their age. Refresh cannot force Claude to emit quota data without a response. No account-page scraping, credential extraction or dummy inference is used. Account consumption includes other applications and machines. Metadata-only Codex `account/read` and Claude `auth status --json` identify the signed-in account when available; histories remain separate by account.

The host stores request counters in an indexed SQLite ledger. Claude partial stream events provide request identities and input/cache/output counts; resumed-session cumulative result totals are retained in run metadata but never added as fresh usage. A context compaction streams no request events and its result record's `usage` is zero, so its tokens come from that record's `modelUsage`. `modelUsage` counts the session's whole life by model, so the host keeps each Claude result record's reading per session (`usage_counters`, scope `claude:<session>`) and records for a compaction only what each model rose by since the reading before it, as one request `compact:<run>:<model>`; a turn's reading adds no request. A reading counts as the baseline only when the session's run just before the compaction took it: a turn that was cut off reports no totals though Claude counted its requests, so a compaction after it, like one with no earlier reading, records none rather than count that turn twice. The reading and its requests are stored as one unit. The totals and cost Claude reported are kept in the run's metadata as they are, so they are the session's, not the run's. Codex 0.160 completion usage is cumulative across the conversation. Persistent per-thread checkpoints subtract the previous reading to record each turn once; missing resumed baselines and decreasing counters are withheld rather than invented. An interval spanning an unreported turn is marked partial. A Codex compaction is recorded another way, because no notification reports its tokens and that cumulative usage leaves it out (on 0.160 the next turn's total rose by that turn alone). Codex writes a `token_usage_record` entry in the thread's session record for the compaction's one model request, carrying the id of its turn, which `turn/completed` names. Once the server is stopped the host reads that entry's own `usage`, never its running sums, and records it as one request `compact:<run>` in the unit that settles the run (`record_codex_compaction`). It is the request's own counts, not a reading, so it neither reads nor moves the thread's checkpoint, and the checkpoint's "run just before" check skips compaction runs: the turn after one is counted whole and is not partial. Only exactly one readable entry for that turn is recorded. With none, more than one, unreadable counts, no turn id or no session record, no request is written, the compaction is still compacted, and the run's `detail.result.unrecorded` says why. A failed or interrupted compaction records nothing. Replayed events, stream updates and restarts do not duplicate requests. Interrupted requests retain reported input and output with a partial marker. Cache tokens are included in input and reasoning tokens in output when reported. Native subagents are included only when their request events are visible, attributed to the managing agent; independently identifying every native subagent is not yet supported.

Existing Codex run totals are normalized as cumulative checkpoints once, preserving observed differences. Legacy Claude totals cannot reliably distinguish new usage from resumed-session totals and remain unreported. No historical token counts or missing account percentages are fabricated. Daily quota graphs sum observed increases within the same reset window and calendar day; unknown intervals remain unmeasured. The recent consumption rate needs two readings within fifteen minutes and is hidden when stale. Account quota remains global even with a project filter.

The additive database migration advances the store to version 3. Model/role/custom-date filters, weekday patterns, worker drilldown, account daily usage import, configurable thresholds and exhaustion-based scheduling remain PRD follow-up work. Graph-query performance at the million-request target is not yet measured.

Headless commands: `usage` accepts `days` (1–30), optional `project_id`/`provider`, and an IANA `timezone`; `quotas` returns the latest persisted readings, and `refresh_codex_quota` reads Codex's limits off the host thread, records them and returns every reading. `workspace-host probe-quota` performs a metadata-only Codex quota read.

## Context window

Each session's **Overview** shows how full its context window is and with what, and the conversation header shows the fill level. The app measures after each turn finishes and on **Refresh**; a measurement makes no model call and does not change the provider's session. The client sends `measure_context` with the session and the model it shows, and the host builds the probe from the session's last run and role instructions and runs it off its thread.

- **Claude** reports its own categories. The app runs `claude -p "/context" --resume <session> --no-session-persistence` from the session's directory with the turn's model, role instructions and strict MCP configuration. Deferred tools are listed by Claude but not loaded, so they are left out; the autocompact buffer gives the compaction point. The workspace's own tool server needs a live turn's credentials and is not counted.
- **Codex** reports only the last request's total and the model's window, which the app reads from the session record under `~/.codex/sessions` (or `CODEX_HOME`). Categories are estimated: content sizes in that record at four characters per token, scaled down to the reported total after compaction, with the unaccounted remainder shown as tools and overhead. A `compacted` entry resets the conversation categories to what it kept, the retained messages and the summary item in its `replacement_history`, so a compacted context still shows Messages. The panel labels them as estimates. Codex does not state a compaction point. Right after a compaction Codex's total leaves out its fixed system prompt and tools, about 13k tokens on the threads observed, so the card reads low until the agent's next turn.

A session measured before this change shows the bar after its next turn, because the directory it runs in is recorded from then on. Headless, with the skills that data folder stores: `workspace-host --data-dir <directory> probe-context <claude|codex> <role> <model> <provider-session> <directory>`.

The same card has **Compact…** for an agent with a provider session, Claude or Codex; an agent that has not run yet shows it disabled with the reason. A Codex request takes no note, because `thread/compact/start` has no field for one: the form has no "What to keep" field, and the host refuses a Codex request that carries instructions rather than drop them. The request is stored on the session's runtime (`SessionRuntime.compaction`, one per session, `queued` then `running`), so it survives a restart and reaches the card in the snapshot. Only a client command creates one (`compact_context`, `cancel_compaction`, `dismiss_compaction`); no agent tool does.

A compaction is a run but not a turn (`start_compaction` in `service.rs`, tracked in `compacting` beside `active`). The host resumes a Claude session with a turn's arguments and exactly `/compact` or `/compact <note>` on stdin, with no wrapper; a Codex thread is compacted through `codex app-server`, as below. A compaction's `provider_runs` row has `detail.kind` `"compaction"` and no messages; every query that means "this session's turns" excludes it with the shared `IS_TURN_RUN` condition, so it counts toward no check-in and never hides a stopped or interrupted turn's note. It delivers no input, appends no reply, tells the parent nothing and leaves the session's stored status alone; the desktop draws "Compacting" from the request. Pause, Stop and `stop_agents` set the status and let a started compaction finish.

A Codex agent is compacted through `codex app-server`, one process per compaction, because `codex exec` has no compact command (`provider/codex_compaction.rs`). The host starts it in the agent's directory with a turn's three `-c` overrides, so the summary request shares the turns' prompt cache, and with a workspace token no turn holds. It writes four lines at once, `initialize`, the `initialized` notification, `thread/resume` and `thread/compact/start`, and nothing after them. `thread/resume` carries what `exec`'s flags say for a turn: the profile's model, sandbox `danger-full-access`, approval policy `never`, and `excludeTurns`; the server writes those settings into the thread's record. The server exits when its input closes and never on its own, so the host keeps the input open until the outcome is read. It then closes the input and gives the server up to a second (`EXIT_MARGIN`) to exit by itself before it stops the process group as it ends any run. Codex 0.160 writes the last entries of the thread's record a few milliseconds before it reports the outcome and exits within 0.02 seconds of its input closing, but no interface promises that order, so the margin is what lets a server that writes them later finish. The limit, a cancellation and a quit stop the group at once.

A Claude compaction's outcome is read from Claude's `status` record, never the exit code, which is 0 either way: `compact_result` `success` is compacted, with `pre_tokens` and `post_tokens` from the `compact_boundary` record; `failed` with "Not enough messages to compact" is nothing to compact; anything else, a missing record included, is failed.

A Codex compaction's outcome is read from the app-server's messages. `turn/completed` with `turn.status` exactly `completed` is compacted. Everything else is failed with a reason, and nothing is ever nothing to compact: a `failed` turn gives its `turn.error.message`; any other status is named; an error reply to one of the three requests names the request, and the first decides; a request the server sends is not answered and is named; a server that exits first ends as any run that exits without a result, its exit and error output held to one line as the reason; and one whose outcome has not been read after `CODEX_COMPACTION_LIMIT`, 10 minutes, is stopped, also when it has closed its output and stays alive. A `failed` turn whose message is empty or starts with a line break is named by its status. Every reason is one line of at most 200 characters (`compaction::REASON_LIMIT`, which the card also cuts at). The run's `detail.result.reported` keeps, whole, what the run ended with: Codex's own text for a failure it reported, or the host's words for a quit, the limit or a process that exited first. A Claude compaction's `reported` is the same, and the reason of one whose process exited without a status record is held to that one line too. A reply that says the unknown variant is the request's own method becomes "this Codex has no such method"; the same opening about a parameter's value keeps Codex's words. The line's figures are Codex's totals for the whole context: before is the context total in the thread's session record as the compaction starts, and after is `tokenUsage.last.totalTokens` from the `thread/tokenUsage/updated` that follows `turn/started`, since resuming first reports the last turn's total. Without both the line has no figures. The protocol is experimental: `codex-cli` 0.160.0 is the version these were read from.

The host stores the outcome as `SessionRuntime.last_compaction` and writes one message from the session to itself under a `compaction:<run>` id, which the conversation draws as a single line; replies are `output:` messages, so it is never taken for one. The desktop measures the card once after every outcome, also while the next turn runs, and never while a compaction runs.

A quit cancels a running compaction and waits for its process group like a turn's. At startup an unfinished compaction run goes through the same leftover handling as an unfinished turn, and is then settled as `interrupted`: never run again, the session's status and waiting messages untouched. The fake provider answers `/compact` with the recorded streams `compact-success`, `compact-nothing` and `compact-failed`; a note containing `NOTHING`, `FAIL` or `NO_STATUS` picks the outcome, and `WAIT_FOR_GATE` holds a compaction until `gate-compact` exists in `WORKSPACE_TEST_USAGE_DIR` (a turn's message with it waits for `gate-turn`). Started as `app-server`, the fake provider checks the four requests it reads and plays the server's side of a recorded exchange, `codex-compact-*.jsonl` in the streams directory, most of them recorded from Codex 0.160 and the `synthetic-` ones written by hand. `codex-compact.json` in `WORKSPACE_TEST_USAGE_DIR` picks the recording (`stream`) and changes it: `refuse` answers a request with an error, `turn` overrides fields of the completed turn, `no_figure` drops the turn's own total, `stop_before` ends the replay early, `exit` and `stderr` end the process, `close_output` closes its output and leaves it running, `gate` holds the completion until `gate-compact` exists, `usage` leaves out, repeats or spoils the usage entry it appends to the thread's session record under `CODEX_HOME`, and `record` writes that record for a turn that did not complete (`failed`) or only once the input has closed (`late`). Like the real server it stops and exits when its input closes, also mid-replay; `ignore_input_closing` makes it stay. The tests point `CODEX_HOME` at a scratch directory, and `WORKSPACE_CODEX_COMPACTION_LIMIT_MS` shortens the limit for the one test that waits it out.

## Repository owners and publishing

The **Repositories** page lists the GitHub organizations and users that own the workspace's repositories under "Open pull requests without asking". Tick an owner to allow it: in its repositories, agents may push a ticket's branch and open and update its pull request without asking, once the ticket's review has passed. Nothing is allowed until you tick it. A fork has its own tick box and is never covered by its owner's. A repository with no GitHub `origin`, one whose `origin` has more than one push URL, one whose base is not on `origin`, and one GitHub has not answered for always ask first. The list is kept in this Mac's `settings.json` as `allowed_owners` and is never synced.

The owner comes from the push URL of `origin`, read on disk. Whether a repository is a fork, whether it is public and which owner GitHub reports for it come from one read-only `gh api graphql` request for the whole workspace (one per 50 distinct repositories), made at launch, when repositories are added and when you come back to the app, for repositories whose answer is missing, a day old or for another `origin`. If `gh` is missing or signed out, owners are still listed, the page says why GitHub could not be checked, and everything without an answer asks first.

Agents publish with one tool, `publish_ticket`, which the ticket's coordinator or implementer may call and a verifier may not. The host runs the push and opens the pull request itself. On an open pull request, a title, a description or both make the host edit them with `gh pr edit` after the push, passing only the fields given; when GitHub's branch, read again before the push, is already at the commit, nothing is pushed and only the edit is sent. It refuses unless the ticket has been reviewed, no review is running, the worktree is on the ticket's branch at the reviewed commit or a patch-equivalent one, and `origin` is one checked place on GitHub that the base tracks. It freezes what it will send (repository, push URL, branch, base, commit, title and description) and the review cycle it was decided on, and checks that nothing differs before each step; a later review of the ticket ends the request, and the next call is decided on that review. `origin` and Git's URL rewrite rules are read in the ticket's worktree, where the push runs, since a worktree can carry its own configuration. Before anything is sent it asks GitHub again which owner the repository has now, and sends nothing if that differs or GitHub gives no answer. Every `gh` call names `github.com`, so `GH_HOST` cannot point them at another GitHub. The step then makes the local checks once more on its own thread, against the store and the worktree as they are at that moment, immediately before Git or `gh` sends. The push names the frozen URL and one refspec, with `--no-follow-tags --recurse-submodules=no`, so tags, other branches, submodules and a repointed `origin` are left out. GitHub's branch is replaced only when its head is the commit the host last pushed or was once this branch's tip here, as its reflog records; otherwise the push is refused.

Where the owner is not allowed, each push, each pull request and each edit of one waits for your approval on an Inbox card the host writes; approving runs exactly what the card showed. In an allowed owner's repository the host publishes without asking when the review passed, or when the coordinator waived a blocked review; a blocked review published without a waiver asks once for the commit, and the card lists the open findings. So does opening another pull request after an earlier one was closed or merged. The result reaches the calling agent as a message from Wiffletree, queued even when the agent's queue is full; a request whose result cannot be queued is kept and ended at the next start.

Requirements: the same signed-in `gh` the PR watcher uses, now also for `gh pr create`, `gh pr edit` and `gh pr merge`; and Git credentials for `origin` that work without a prompt, because the host's `git push` runs with `GIT_TERMINAL_PROMPT=0`. The push runs the repository's pre-push hooks and is stopped after 10 minutes. Only `github.com` remotes are supported, and pull requests go into the ticket's `base` branch if it has one, otherwise the repository's configured base branch, on the same repository. A stacked ticket's pull request goes into its parent's branch, and `publish_ticket` refuses until the host has pushed the parent; once the parent's pull request has merged, it goes into the parent's base branch: the parent's `base` if it has one, otherwise the repository's.

Wiffletree merges a ticket's pull request only through `merge_ticket` (`crates/workspace-host/src/merge.rs`), which only the ticket's project coordinator may call, and only into a branch that is not protected, in a repository that publishes without asking. A branch is protected when it is GitHub's default branch, the branch of `origin` the configured base tracks, matches an entry on the repository's list (`workspace_core::ProtectedBranches`, changed only by the client's `SetProtectedBranches` and stored with the repository on this machine), or GitHub's branch protection or an active ruleset applies to it. The host first makes the checks it can on this machine, the same as `accept_ticket` and `publish_ticket`, then reads the pull request, the default branch, the allowed merge methods, branch protection and rulesets from GitHub again, and refuses when any read fails. It merges with `gh pr merge <number> --<method> --match-head-commit <head>`, the method being the first of squash, merge commit and rebase that GitHub allows, never with `--auto`, `--admin` or `--delete-branch`; records the PR as merged by the host; accepts the ticket; and moves each stacked child's pull request to the merged one's base with `gh pr edit --base`. While checks run or GitHub has not worked out mergeability, the request is stored on the ticket (`Ticket.merging`) and decided again after each PR watcher pass. After a blocked review, or over commits no review checked, it waits on an Inbox card under the host-only `merge:` prefix, drawn from `workspace_core::merge_card`; every check runs again on approval and just before the merge. While it waits for the human, each watcher pass that left GitHub's rate limit above the watcher's floor also reads GitHub once for it, without merging and without starting another pass, and ends it when the base became protected, a conflict appeared or the checks failed.

Not prevented: an agent's shell can still push, merge or call GitHub with your credentials, edit `settings.json` or a repository's remotes, and nothing notices a push or a merge made outside the app. Closing that needs credentials the agents do not hold, or a sandbox.

## Remote access

Another Mac can drive this Mac's projects over the network, as `openspec/changes/archive/2026-10-20-remote-hosts/` specifies and [docs/remote-protocol.md](remote-protocol.md) describes for other clients.

- **Turning it on.** At the host, Settings (⌘,) › Remote access › **Let other devices use this Mac's Wiffletree**. It is off by default. While on, the host listens on TCP port 47821 over TLS 1.3 and advertises `_wiffletree._tcp` on the local network; the page shows the names and addresses it can be reached at. Turning it off closes the listener and every remote connection at once, and paired devices stay paired. The setting belongs to this Mac's host and is never synced.
- **Finding other Macs.** On the Mac you drive from, Settings › This Mac · the app › OTHER MACS › **Find Wiffletree on other Macs on this network** browses for `_wiffletree._tcp`. It is off by default, an older preferences file included, so the app never browses and macOS asks about the local network only when someone turns it on. Off, paired hosts still reconnect by their stored addresses, and a name or address can still be typed; a paired Mac that moves to a new LAN address is found again only while it is on. Connect a computer's **Turn it on** flips the same setting (`desktop-preferences.json`'s `find_on_network`).
- **Pairing.** At the host, **Pair a device** shows a 4-digit code for 2 minutes. On the other Mac, the sidebar's host menu › **Connect a computer…** lists hosts found on this network while finding is on; for a host on Tailscale or a VPN, type its name or address, with an optional `:port`. Choose it and type the code. The code works once, and the third wrong one closes pairing at the host. A new device gets **Control**.
- **Driving a host.** The sidebar's host menu switches between This Mac and each paired host. A connected host's row shows its network delay, the round trip less the host's own time, in its tooltip. The app's standard error logs every reply's timing, This Mac's host included, as `Latency to host <short id>, <request kind>: round trip … ms, on the host … ms, network … ms`, so local and remote figures can be compared. A host that stops answering keeps its last view under a "Reconnecting…" banner with **Try now**; messages written meanwhile are sent once it answers. A paired host is reconnected by the address it last answered at before Bonjour is asked.
- **What the levels allow.** **Control** runs every workspace command, as the human at the host could: sending messages, answering the Inbox, creating tickets, saving the host's settings and uploading attachments. Agents run with permission prompts off, so Control is the same as running commands on the host. **View only** reads, the handshake and the event subscription, and every change is refused with "View only: <host> refuses changes from this device". Neither level can change remote access, pairing or devices, or stop or restart the host's process; those are only the host's own. Change a device's level on the host's Remote access page; it applies to the device's next command and reconnects it.
- **Removing a device.** At the host, **Remove** on the device's row forgets it and closes its connections at once, even if it is offline; it must pair again. On the device, Settings › **Computers you've paired with** › **Remove** forgets a host on that Mac only; the host still lists the device until it is removed there.
- **Keys.** Each side has one P-256 key in the login Keychain: the host's `com.vyttle.wiffletree.host-key`, one per data folder (see [the host process](#the-host-process)), and the device's `com.vyttle.wiffletree.device-key`, one per user. A device keeps its paired hosts in its data folder's `desktop-preferences.json`. A host whose key changes is refused until paired again.
- **Trying it without touching the installed app.** Run both Macs from a build with their own folders, for example `target/debug/workspace-desktop --data-dir /tmp/wiffletree-remote`, so neither uses the installed app's store or its launchd host.

## Driving the app for testing

`workspace-desktop --automation-socket <path>` opens a development-only Unix socket (mode 600) that turns JSON lines into real input. Mouse events are posted to the application's own AppKit queue, so hit-testing, hover, menus and dialogs behave as they do for a person; keys and typed text go through GPUI's keystroke dispatch. The pointer, the keyboard focus of other applications and macOS Accessibility permission are not involved. Nothing listens unless the flag is passed. In this mode the app does not activate itself at launch and keeps its window out of Stage Manager's strip, so the window can be captured at full size while you work in another application.

`scripts/drive_desktop.py` is the client:

```sh
./target/release/workspace-desktop --data-dir /tmp/wiffletree-trial \
  --demo-repository "$PWD" --automation-socket /tmp/wiffletree-ui.sock &
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock click 1247 62
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock type "Ship the toolbar"
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock key enter
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock scroll 1100 500 -300
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock drag 120 180 120 320
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock drop 740 400 shot.png notes.txt
python3 scripts/drive_desktop.py --socket /tmp/wiffletree-ui.sock shot /tmp/window.png
```

Coordinates are window points from the top-left corner. `shot` saves the window at one pixel per point, so a position read from a screenshot can be passed straight back to `click`. `key` takes GPUI binding syntax such as `cmd-n`. `drag` presses at the first point, moves to the second in a few steps and releases there; `--hold` leaves the button down so a `shot` can capture the drag, and `release x y` ends it; `--count 2` makes the press the second click of a double-click. `press x y` and `release x y` take `--button right`. `drop` replays the file-drop events macOS sends for a Finder drag at that point, so the app's own drop handler receives the files. Drops hit-test against the last drawn frame, so after the window has sat covered, send a `move` first. Keep the socket path short: macOS limits Unix socket paths to about 100 bytes. Captures need Screen Recording permission for the calling terminal and fail while the screen is locked; input still works. GPUI stops drawing a window that other windows fully cover, so each step draws a frame itself and captures stay current while you work in front of the app. Use an isolated `--data-dir` and, for runs that must not call a provider, point `WORKSPACE_CLAUDE_BIN` and `WORKSPACE_CODEX_BIN` at `crates/workspace-host/tests/fixtures/provider.py`.

Each part of the window is its own view, and a cached view draws again only when it changes: the sidebar, the transcript, the conversation's header, the inspector panel and each workspace page. A step asks for a frame without discarding those caches, so what it redraws is what a person's input would. With `WIFFLETREE_RENDER_COUNTS=1` set, the app prints each view's renders per second to stderr about once a second while anything draws, which shows which views a change reaches. Once a second it also prints the timed stages of a refresh (snapshot decode, `WorkspaceIndex::new`, `share()`), how often each main view was notified, the main thread's CPU time and its longest stall; notifies count even while the window is covered and draws nothing. [Refresh cost with many agents](performance/refresh-cost.md) uses these with a fixture of 40 working agents.

## Releases and updates

Every pull request runs `.github/workflows/ci.yml`: formatting, warnings-as-errors Clippy, all Rust tests and the deterministic communication tests. The core and host tests are built once on Linux (`ubuntu-latest`) and run in four parallel shards. In parallel, macOS jobs (`macos-15`) run formatting and Clippy, and the desktop tests, the core and host tests that only build on macOS, and the communication tests. A `check` job, the one branch protection requires, passes only when every other job did, and fails if a core or host test runs in no pull-request job. A pull request must be up to date with `main` before it merges. Every push to `main` runs the workflow again with the whole suite also on macOS, and only those runs save the Rust build caches: a pull request restores the caches `main` saved but never saves its own, so a new pull request starts warm. Merging does not release anything. The Release workflow reruns the checks on the tagged commit, and there too the whole suite runs on macOS; it restores caches and saves none. Its signing and publishing run on `macos-15`.

To release, tag a commit on `main` with its version and push the tag:

```sh
git switch main && git pull
git tag v0.2.0
git push origin v0.2.0
```

The tag runs `.github/workflows/release.yml`. It rejects tags that aren't `v<major>.<minor>.<patch>` or that point outside `main`. Then it reruns the checks and builds the bundle with that version. It signs the bundle with the Developer ID and the hardened runtime, notarizes and staples it, and publishes `Wiffletree-<version>-macos-arm64.zip` as the release for the tag. Creating the release in GitHub's UI with a new tag works too; the workflow attaches the build to that release.

The app shows each update in a card at the bottom of the sidebar. The card has the release notes' opening paragraph, a **Changelog** link to the release page and **Restart to update**. So start the notes with one plain sentence about what changed, then let GitHub generate the PR list below it. In the UI, write the sentence and click **Generate release notes**. From the command line:

```sh
gh release create v0.2.0 --target main --generate-notes \
  --notes "Scheduled tasks, config sync and a sidebar status section."
```

Everything above the first heading or list item is the summary. Without one, the card just says the version is ready. Each tag must be higher than the last, because installed apps only move to a newer version.

`scripts/install.sh [tag]` is the public installer the README's `curl … | bash` line runs. It replaces `/Applications/Wiffletree.app` (or `$WIFFLETREE_INSTALL_DIR/Wiffletree.app`) with a release, the latest by default, after checking its signature and Gatekeeper assessment. It quits a running copy first. With a child host that interrupts active turns; a launchd host keeps them running, and restarts into the new version once they finish. Use it to replace a local development build with a release, which then updates itself. A tag whose release has no build yet fails with a retry hint, so expect that for the few minutes the release workflow is still publishing.

Signing and notarization use these repository secrets. The release fails without them rather than publishing an unsigned build.

| Secret | Contents |
| --- | --- |
| `MACOS_CERTIFICATE` | Base64 of the exported *Developer ID Application* certificate and key (`.p12`) |
| `MACOS_CERTIFICATE_PASSWORD` | The `.p12` export password |
| `APPLE_API_KEY` | Base64 of an App Store Connect API key (`.p8`) with Developer access |
| `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` | That key's ID and issuer ID |

Only builds with `WIFFLETREE_VERSION` embedded, meaning CI releases, update themselves; the beta never does. `scripts/package_macos.sh` sets that variable from the environment. A release build checks `releases/latest` at launch, hourly, and on demand, without authentication. To check on demand, click the version at the bottom right of the sidebar (local builds show `v<version> dev`) or choose **Check for Updates…** from the app menu. **About Wiffletree** in that menu opens the standard panel with the version and copyright. Because the checks are unauthenticated, updates need the repository to be public. When a newer version appears, the app does four things before staging it in `~/Library/Caches/com.vyttle.wiffletree/update`:

- Downloads the archive for its architecture.
- Requires the archive to match the SHA-256 digest GitHub publishes for it.
- Verifies the code signature.
- Requires the same signing team as the installed app. An ad-hoc install accepts any valid signature, which allows the move to Developer ID.

**Restart to update** then replaces the bundle in place after the app exits and reopens it. Quitting the app for good, with Quit Wiffletree from the menu bar icon or Stop agents and quit, installs it without reopening; closing into the background does not. With a launchd host the turns keep running through the app's restart, and the host restarts into the new version once no agent works (see [the host process](#the-host-process)). With a child host, restarting interrupts active turns like any quit; the sessions it cut off come back Interrupted, and the rest of each running project carries on. If the app's folder isn't writable, for example when it's run from a translocated download, the updater stays off.

`crates/workspace-host/examples/keychain_probe.rs` checks how the Keychain guards the client credential (`openspec/changes/archive/2026-10-19-standalone-host/design.md`, section 2). It creates, reads and deletes a generic-password item without printing the secret. Sign the built example, copy it, and read the item from each copy and from `security find-generic-password -w`:

```sh
cargo build --release -p workspace-host --example keychain_probe
cp target/release/examples/keychain_probe /tmp/kc/host
codesign --force --options runtime --identifier com.vyttle.wiffletree.spike.host --sign "<identity>" /tmp/kc/host
/tmp/kc/host create com.vyttle.wiffletree.spike [--trust <other binary>]
/tmp/kc/host read com.vyttle.wiffletree.spike
/tmp/kc/host delete com.vyttle.wiffletree.spike
```

`--data-protection` and `--access-group <team ID>.<group>` use the data-protection keychain instead, which needs the `keychain-access-groups` entitlement and a provisioning profile. Use only a test service name, never a real Wiffletree item.

`crates/workspace-host/examples/local_network_probe.rs` checks how Local Network privacy treats the launchd host copy (`openspec/changes/archive/2026-10-20-remote-hosts/design.md`, "Local Network privacy, checked"). It listens on a port on every interface, advertises `_wiffletree._tcp`, optionally connects to an address on the network, and prints what each step got. Sign a copy, run it as a launchd agent, and read `nehelper`'s decisions from the log:

```sh
cargo build --release -p workspace-host --example local_network_probe
mkdir -p /tmp/ln && cp target/release/examples/local_network_probe /tmp/ln/workspace-host
codesign --force --options runtime --identifier com.vyttle.wiffletree.spike.lnhost --sign "<identity>" /tmp/ln/workspace-host
# A plist labelled com.vyttle.wiffletree.spike.lnhost running: /tmp/ln/workspace-host 47831 90 <router>:80
launchctl bootstrap gui/$(id -u) /tmp/ln/lnhost.plist && launchctl kickstart gui/$(id -u)/com.vyttle.wiffletree.spike.lnhost
/usr/bin/log show --last 2m --info --style compact | grep nehelper | grep -E "prompting|response"
dns-sd -B _wiffletree._tcp   # on this Mac and on another one
launchctl bootout gui/$(id -u)/com.vyttle.wiffletree.spike.lnhost
```

Only a signed build runs its host as a launchd job, so its tests cannot cover that the host does not start at login. Before a release, check it by hand on a test account:

1. Open the signed app with its default data folder, so it loads the job from `<data folder>/host/com.vyttle.wiffletree.host.plist`.
2. Quit the app and log out, then log back in without opening Wiffletree.
3. `launchctl print gui/$(id -u)/com.vyttle.wiffletree.host` finds no job, and `pgrep -fl workspace-host` lists nothing.

### Checking the client credential on a signed build

`crates/workspace-host/src/keychain.rs` keeps a launchd host's client credential in the login keychain. Check it by hand on a signed build before a release that changes it. Each step names what to expect. The host never shows a Keychain dialog itself: where it cannot read the item silently, it stops with an error instead.

1. Build a signed bundle: `CODESIGN_IDENTITY="<identity>" scripts/package_macos.sh`, then set `APP="$PWD/target/Wiffletree.app"`, `HOST="$APP/Contents/MacOS/workspace-host"` and `SERVICE=com.vyttle.wiffletree.client-credential`.
2. Make a scratch data folder: `DATA=$(mktemp -d /tmp/wt-kc.XXXX)` and `ACCOUNT=$(cd "$DATA" && pwd -P)`, since the item's account is the resolved folder.
3. **Create.** Run `"$HOST" serve --data-dir "$DATA" --app "$APP"`. Expect no dialog, and `$DATA/host.sock` to appear. Stop it with Control-C. `security find-generic-password -s "$SERVICE" -a "$ACCOUNT"` lists the item's attributes, without its secret.
4. **Read.** Run the same `serve` again. Expect it to start with no dialog: it found the item, because a host that could not read it would fail to add a second one.
5. **A versioned copy.** Copy the host as the app will and re-sign it with the same identifier and identity:
   ```sh
   mkdir -p "$DATA/host/9.9.9" && cp "$HOST" "$DATA/host/9.9.9/workspace-host"
   ID=$(codesign -dv "$HOST" 2>&1 | sed -n 's/^Identifier=//p')
   codesign --force --options runtime --timestamp --identifier "$ID" --sign "<identity>" "$DATA/host/9.9.9/workspace-host"
   "$DATA/host/9.9.9/workspace-host" serve --data-dir "$DATA" --app "$APP"
   ```
   Expect it to start with no dialog, then stop it.
6. **Another program.** Run `security find-generic-password -s "$SERVICE" -a "$ACCOUNT" -w`. Expect a dialog asking for the login keychain password. Click **Deny**; nothing is printed.
7. **Fail closed.** With a fresh folder, `DATA2=$(mktemp -d /tmp/wt-kc.XXXX)`, run `"$HOST" serve --data-dir "$DATA2" --app /nonexistent/Wiffletree.app`. Expect it to exit with status 1 and `Limit the client credential to Wiffletree`, and `security find-generic-password -s "$SERVICE" -a "$(cd "$DATA2" && pwd -P)"` to find no item.
8. Clean up: delete the item in Keychain Access (search for `$SERVICE`), or with `security delete-generic-password -s "$SERVICE" -a "$ACCOUNT"`, then `rm -rf "$DATA" "$DATA2"`.

Step 7 needs no signature and passes on an unsigned build.

Last checked on October 19, 2026, on macOS 27.0.1 (26A434), signed with *Apple Development: Michael Hohlios (PF6B6HV656)* and the hardened runtime, not with a Developer ID and not notarized. Every step behaved as expected:

- Steps 3–5 started the host with no SecurityAgent process running. The item was in the login keychain, and the copy re-signed under `host/9.9.9/` read it silently.
- Step 6 brought up the dialog "security wants to use your confidential information stored in "com.vyttle.wiffletree.client-credential" in your keychain", asking for the login keychain password. The reader was killed without anything being clicked, and it printed nothing.
- Step 7 exited 1 with `Name "/nonexistent/Wiffletree.app" in the access list: 100002` and left no item.

Repeat the check with the Developer ID before the first launchd release.

## Current limits

- Acceptance preserves the tested branch. **Merging into a protected branch is manual**: Wiffletree pushes a ticket's branch and opens its pull request through `publish_ticket`, and merges a ticket's pull request only through `merge_ticket`, only into a branch that is not protected and only in an allowed owner's repository (see [repository owners and publishing](#repository-owners-and-publishing)). It never merges into a protected branch and never approves, closes or comments on a pull request. No dependency rebase or combined integration testing is implemented, and conflict fixing is limited to the PR keeper's one checked try. The PR watcher reads PR status and tells the coordinator when a PR merges, but accepting the ticket stays the coordinator's call.
- Publishing and merging are checked, not enforced: agents run with their provider's permission prompts bypassed, so an agent's shell can still run `git push`, `gh pr create` or `gh pr merge` with your credentials. Only the instructions stand in the way. There is no sandbox, and agents hold the same credentials you do. Tickets start from the repository attachment's configured base. Use independent tickets for the first trial; dependent tickets need an updated base and explicit integration planning.
- Remote hosts are Macs only: the `qr` pairing method for the iPhone is specified but not offered, and there are no push notifications. The Local Network check with a Developer ID and notarization is still a release check. A signed app's host keeps working after the app quits, but it does not start at login, so after a restart or logout coordinator timers wait in the store and fire late, once, when the app is next opened. A `--data-dir` or unsigned build still stops its host, and its turns, when it quits.
- Attachments only come from dropping or pasting files and images in a conversation: no attach button, folders, task or project file library, or cleanup apart from the message's own lifetime.
- No turn limits: every session with due input runs, whatever else is running, and no project stops after a number of turns. The one bound is on builds: at most "Builds at once" (Settings → Builds, default 1) compile or run tests at a time across the host, from any agent. The host links `wiffletree-build-gate` to its own binary in a temporary folder and gives agents `RUSTC_WRAPPER`, `CARGO_TARGET_<host triple>_RUNNER` and `GOFLAGS=-toolexec=…` naming it, unless your environment sets them. A build, the outermost Cargo (an external subcommand such as `cargo-nextest` included) or Go command whose subcommand builds, takes a slot at its first compile or test binary and keeps it until it exits (a `go run` only while its compiles and link run); `crates/workspace-host/src/build_gate.rs` keeps the slots in `<data>/build-gate/` and the link in `$TMPDIR/wiffletree-<hash of the data folder>/`. Every `verify_ticket` cycle starts at once. Agents run at nice 10, with `CARGO_BUILD_JOBS` and `NEXTEST_TEST_THREADS` at half the cores unless your environment sets them, so their builds and tests yield to the desktop and leave cores for your own work. Supervision replaces limits: long turns check in with their parent every 30 minutes, long runs of turns check in with the parent or the human, and the parent stops runaway work with `stop_agents`. There is no dollar-spend cap.
- Host dispatch measurements exclude model startup/reasoning, a busy recipient's current turn, Git checkout and permission waits. Worktree creation currently runs on the host's database thread; large repository checkout can delay host commands, although it does not run on the UI thread. Moving that Git preparation off the actor remains performance work.
- Full native responsiveness, long-document Markdown behavior, accessibility/IME, memory bounds under prolonged load and an eight-hour soak remain release gates. Compilation does not prove “no lag.”

The core and host tests also pass on Linux, where pull requests run most of them. CI's `check` job fails and names any core or host test that macOS builds, Linux does not, and the profile misses.
