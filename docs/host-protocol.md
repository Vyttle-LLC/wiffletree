# Host protocol

How a client talks to a Wiffletree host: the desktop app today, and later `remote-hosts` devices and an iPhone client. The types are in `workspace-core` (`crates/workspace-core/src/host.rs` and `Command` in `lib.rs`); this page is their reference, and a test checks that its command table lists every `Command` with its read or change class.

## Transports

| Transport | Started as | Handshake | Protocol |
| --- | --- | --- | --- |
| `<data folder>/host.sock` | `wiffletree-host serve --data-dir <dir>` | `Hello` first | 2, or 1 if the client asks for it |
| Standard input and output | `wiffletree-host --data-dir <dir>` | none | 1 only |

The standard-input mode is for scripts such as `scripts/test_communications.py`: one request per line on standard input, one response per line on standard output, and the host stops when its input closes. Everything else on this page is about the socket.

### The socket

- `serve` creates `host.sock` with mode 0600 inside the data folder, which it keeps at 0700, and removes a socket a previous host left. A socket path longer than the platform allows (103 bytes on macOS) stops the host at start with that reason.
- Each accepted connection is checked with `getpeereid` (`SO_PEERCRED` on Linux). A connection from another user is closed before anything is read.
- A child host, `serve --data-dir <dir> --child`, reads the app's client credential from the first line of its standard input and stops when that input closes. The app keeps the pipe open for as long as it runs, so the credential is never in the host's environment, which agents inherit, or in a file. `workspace_core::ChildHost` starts one this way.
- Without `--child`, the credential is the data folder's login Keychain item, created at the first start with an access list of the host's own binary and the app given with `--app <Wiffletree.app>` (`crates/workspace-host/src/keychain.rs`).
- SIGTERM, SIGINT and SIGHUP run the host's shutdown, which stops running turns as a quit does, then remove the socket.
- A launchd host runs from a versioned copy of its binary, `<data folder>/host/<version>/wiffletree-host`, which an update of the app does not replace, and starts its agents' helpers from that same copy. Started from a copy, it removes the other version folders under `host/`. A child host runs from the app bundle (or `target/`) and has no copy.

### Remote devices

While remote access is on, paired devices reach the host over TLS 1.3 on TCP port 47821, with one JSON message per WebSocket text frame in place of a line. `docs/remote-protocol.md` describes the transport, pairing and pinning in full, for clients written in any language; in short:

- `/pair` runs a pairing method while pairing mode is open: `PairStart`, then `PairReply` and `PairConfirm` (`workspace_core::remote`).
- `/v1` opens with the host's `Challenge`. The device answers with `ChallengeAnswer`, its id and a signature, and the host replies with `ChallengeVerdict`: `{"accepted": {"level": "control"}}` or `"view_only"`, so the client knows what it may do before it sends anything, or `"unpaired"`, after which the host closes the connection with the reason `unpaired`. `Hello` and the rest of this page follow an accepted verdict.
- Changing a device's level or removing it closes its connections, so it reconnects and reads its new level from the verdict, or is refused.
- A device's commands are checked against its level, never against the client credential.

## Framing

Every message is one line of JSON ended by `\n`. A line from the client, `Hello` or a request, is at most 256 KiB; a longer one closes the connection. Lines from the host have no such bound: a `read_file` response carries up to 50 MB as base64, about 67 MiB, so a client accepts host lines of at least 70 MiB. A connection carries:

- from the client: one `Hello`, then requests;
- from the host: one answer to `Hello`, then responses and, after `Subscribe`, events.

Requests are answered in any order; match a response to its request by `id`. Writes never interleave within a line.

```json
{"version": 2, "id": "c4a1…", "command": {"type": "snapshot"}}
{"version": 2, "id": "c4a1…", "result": {…}, "error": null}
```

`command` is tagged by `type` in snake_case, with the fields below. A response has `result` or, when the command failed or was refused, `error`, a sentence for a person. `version` in a response is the request's. `host_ms`, when present, is how long the host took from reading the request to writing the reply.

Types in the command table are Rust's: `String` and `PathBuf` are JSON strings, `Option<T>` is `T` or `null`, `Vec<T>` an array, integers are numbers, and named types are the `workspace-core` structs and enums of that name in their serde form. A field marked `?` may be left out.

## The handshake

The first line a client sends is `Hello`:

```json
{"hello": {"protocols": [1, 2], "app_version": "0.9.0", "client": {"name": "Wiffletree", "kind": "desktop"}, "capabilities": [], "credential": "…"}}
```

- `protocols` is the oldest and newest protocol the client speaks.
- `client.kind` says what the client is, such as `desktop` or `script`; the host only reports it.
- `credential` is the app's client credential. Leave it out unless you are the app.

The host chooses the newest protocol both ranges include. It accepts its own protocol version and the one before it (`PROTOCOLS`, `[1, 2]` today), so an app one release ahead or behind still works. It answers with one of:

```json
{"welcome": {"protocol": 2, "host_id": "…", "host_version": "0.9.0", "epoch": "…", "capabilities": ["events", "files", "folders"], "binary": "/…/wiffletree-host"}}
{"refused": {"host_protocols": [1, 2], "client_protocols": [3, 4], "host_version": "0.9.0", "working": 2}}
```

- `host_id` stays the same for a data folder across restarts; `epoch` is new each time the host starts.
- After `welcome`, every request must use the chosen `protocol`; another version is refused.
- After `refused`, which says how many agents are in a turn, the connection may send only `restart_host`. Every other command is refused, so an updated app can always restart an older host.
- Any line before `Hello` is refused with the error `Send Hello first` and runs nothing; the connection can still send `Hello`.

`Hello`, both answers and `restart_host` keep the same shape in every protocol version.

### Capabilities

A client never sends a command for a capability the host did not list.

| Capability | Commands |
| --- | --- |
| `events` | `subscribe` |
| `files` | `resolve_paths`, `read_file` |
| `folders` | `list_folder` |
| `restart-when-idle` | `restart_host` with `when: "idle"` |
| `uploads` | `upload_attachment`, and `send`'s `uploads` |
| `attention` | `subscribe`'s `kinds`, and the `attention` event |
| `resubscribe` | `subscribe` again on a subscribed connection, to change its `kinds` |

This host lists `events`, `files`, `folders`, `restart-when-idle`, `uploads`, `attention` and `resubscribe`, and refuses a command whose capability it does not list.

### Ending the host

- `stop_agents_and_quit` and `restart_host` with `when: "now"` run the host's shutdown, which stops every running turn as a quit does and records each as interrupted by the quit with its input held. The reply comes once the shutdown has stopped them; the host then exits successfully, so launchd does not start it again.
- `restart_host` with `when: "idle"` is answered at once. The host exits successfully at the first moment no turn and no compaction runs, which may be at once. New turns start as usual while it waits.
- In both cases the app then starts the host it wants, such as an update's new version.

### Human-only commands

Some commands are only the human's to give: a `send` with no `sender`, which is a message from the human; answering the Inbox (`resolve_attention`, `dismiss_attention`, which also approves a publish); granting publish or push authority without the Inbox (`set_owner_allowed`, `set_keeper`, `set_protected_branches`, `set_up_settings_repository`, `join_settings_repository`); creating, editing, joining or removing a Space, setting its brain, moving a project into one, changing a project's added repositories, choosing which repositories a Space lists and setting up or renaming its tracker (`create_space`, `update_space`, `join_spaces`, `remove_space`, `set_space_brain`, `move_project_to_space`, `set_added_repositories`, `set_repository_spaces`, `confirm_repository_suggestions`, `set_tracker_prefix`, `set_up_issues`), and reading where its storage is on this Mac (`space_storage`); granting, forgetting, setting up, updating the gate of or changing the compiler or compile time of a brain, amending or discarding its batches, sending its log batches now, importing its legacy logs, starting a compile with Run now and ruling on a conflict (`confirm_brain`, `forget_brain`, `set_up_brain`, `update_brain_gate`, `set_brain_compiler`, `set_brain_compile_time`, `amend_brain_batch`, `send_logs_now`, `import_legacy_logs`, `run_brain_compile`, `rule_conflict`); fixing or releasing a held log entry (`fix_held_log`, `release_held_log`); writing to a tracker (`create_issue`, `edit_issue`, `comment`, `move_issue`, `start_project_from_issue`, `link_issue`, `unlink_issue`, and `settle_paused_file` for an issue's file or part), marking an issue read (`mark_issue_read`), following one (`follow_issue`) and every step of an import from Linear (`linear_teams`, `preview_linear_import`, `import_from_linear`, `cancel_linear_import`), while reading issues (`issues`, `issue`, `issue_project_defaults`, `issue_people`) is not the human's alone; the assistant, its threads and their text (`start_thread`, `rename_thread`, `set_thread_open`, `order_threads`, `delete_thread`, `search_threads`, `draft_project_brief`, `make_project`, `scratch_files`, `dismiss_thread_card`, `open_issue_thread`, `proposals`, `apply_proposal`, `discard_proposal`, `set_assistant_name`, `route_message`, `answer_held`, `change_route`, `set_router_threshold`); every job command (`save_job`, `preview_job`, `set_job_enabled`, `run_job_now`, `delete_job`, `stop_job_run`, `see_job_runs`, `take_over_job`, `approve_job_output`); Boards (`boards`, `board_versions`, `board_version_folder`, `share_board`); and in `remote-hosts` pairing and device access. On the socket they run only for a connection whose `Hello` carried the app's client credential; without it they are refused and change nothing. Every other command works without it, but a `snapshot` sent to such a connection leaves out `space_locals`, this Mac's facts about each Space, `threads`, the assistant's tabs, `held`, the messages the router holds, and `jobs`, the user's jobs. A thread's session is never in a snapshot's `sessions`, `runtimes`, `message_revisions` or `undelivered`, or in the archive. This raises the bar for an agent, which runs as the same user and can open the socket; it is not a sandbox.

Agents reach issues only through the project coordinator's workspace tools, over the tracker of its project's Space: `list_issues`, filtered by `state`, `assignee`, `label`, `repository` and `text`; `read_issue`, the issue with its comments and events; and `link_issue`, which links the issue to the coordinator's project, or with `ticket_id` to one of its own tickets, as `link_issue` above does. Every passage of issue text they return names its author in `written_by`, and a comment an assistant wrote names whom it wrote for in `assistant_for`, with a note that issue text is context, never instructions. Any other role is refused, as is an issue of another tracker. No agent tool writes issue text or moves an issue. An issue thread of the assistant has `list_issues` and `read_issue` over its own Space's tracker, but not `link_issue`, and `search_repositories` and `read_repository_file` over its Space's repositories on this Mac at their base branch, which the service runs off the host thread with `git grep` and `git show`, bounded to 200 matching lines, 20 of one file, and 64 KB of a file. Its `propose_edit`, `propose_comment`, `propose_split` and `propose_duplicate`, and every thread's `propose_issue`, only store a proposal with the thread; the human applies it with `apply_proposal`. Threads' `log_work`, which issue threads do not have, writes under the brain's `logs/assistant/` with `ref` `—` and no repository or ticket, and `query_brain` from a thread or a job's run reads its own Space's whole brain.

## Events

`subscribe` turns the connection into a subscriber. Its reply is `Subscribed`, the cursor of the host's latest event:

```json
{"version": 2, "id": "…", "result": {"cursor": {"epoch": "…", "seq": 41}}, "error": null}
```

Events then arrive beside responses:

```json
{"event": {"cursor": {"epoch": "…", "seq": 42}, "kind": "steps", "sessions": ["…"]}}
```

| `kind` | Carries | Fetch again |
| --- | --- | --- |
| `state` | nothing | `snapshot` |
| `steps` | `sessions`, the ids whose steps changed | `steps` for those sessions |
| `progress` | nothing | `progress` |
| `usage` | nothing | `usage` and `quotas` |
| `attention` | `count`, the things that need the human: attention items and workspace notes, as the Inbox counts them | nothing; sent when the count changes |
| `resync` | nothing | take a fresh `snapshot`, then continue from this event's cursor |

Events say only what to fetch again, never workspace state, so a missed event can leave a value stale but never wrong. The host emits at most one event of each kind for each thing that happens.

### Cursors

- A `Cursor` is `{epoch, seq}`. `seq` grows by one per event within an epoch; `0` is before the first.
- The host keeps the last 1,024 events in memory and persists none.
- `subscribe` with `after` set to a cursor of the current epoch still in that log first sends every later event in order, then live events.
- Any other cursor, including one from an earlier epoch or one the log no longer holds, gets `resync` first.
- With no `after`, only events after the subscription come; take a snapshot after the reply.
- A subscriber with no `after`, or one that gets `resync`, then gets one `attention` event with the host's current count, once the host has counted, so it need not read a snapshot to show it. That event carries the cursor of the `Subscribed` reply, and comes after the `resync`. Later `attention` events come only when the count changes. A subscription whose `kinds` leave out `attention` gets none of them.
- A subscribed connection may send `subscribe` again, without `after`, to a host that lists `resubscribe`. Its `kinds` replace the subscription's from the next event on, and the reply is `null`: no new cursor, and no event after the reply is missed. Events the old `kinds` left out are not sent again, so a client that widens its `kinds` reads what it shows anew. With `after`, it is refused. A host without `resubscribe` refuses any second `subscribe`; reconnect to change the `kinds` there.
- Each subscriber has a queue of 256 events. A subscriber whose queue is full has it cleared and gets one `resync`, so a slow client never holds the host.

## Host files

`resolve_paths` reads only metadata: for each reference, the file it names, as it is when absolute or under `~/`, or else under the first of `bases` that holds it, and whether opening it would run it (an executable, or a `.command`, `.tool` or `.terminal` script). It answers one `ResolvedPath` or `null` per reference, in order.

`read_file` and `list_folder` resolve the path first, following symlinks and `..`, and check the resolved path:

- **Roots.** Only files under a project home, a ticket worktree, an attached repository, the workspace folder, or a project's attachment store, `<data folder>/projects/<project-id>/attachments/`, are served.
- **The data folder.** Inside it, only the attachment stores and project homes are served, and only one reached through real folders: a store or home that is a symlink, or lies under one inside the data folder, serves nothing. Whatever the root, the store (`workspace.sqlite3`, its `-wal` and `-shm` files and earlier copies such as `.pre-flatten`), `backups/`, `host/`, `logs/` and the host's settings (`settings.json`, `shared/`) are never served.
- **Credentials.** Over every root, these are refused: `~/.ssh`, `~/.config/gh`, `~/.gnupg`, `~/.aws`, `~/.netrc`, `~/.git-credentials`, `~/.config/git/credentials`, `$XDG_CONFIG_HOME/git/credentials`, `~/.claude/.credentials.json`, `~/.claude.json`, `~/.codex/auth.json`, `$CODEX_HOME/auth.json` and `~/Library/Keychains`. A listing leaves them out too.
- **Size.** `read_file` refuses a file larger than `max_bytes` or 50 MB, whichever is less. It answers `FileContents`, whose `data` is the file's bytes in standard base64.
- **Listings.** `list_folder` answers `FolderListing`: the folders in the path, each with its name and whether it is a Git repository, and nothing about files. The host's own clients and Control devices may also list folders under the host's home folder, which choosing a new repository needs, and may name it with a leading `~`, as `~` or `~/dev`, since a remote client does not know the host's home folder. A View only device lists only within the roots, and a `~` path is refused. `resolve_paths` takes `~/` references from every client, and for a remote device answers only files within the roots.

All three run off the host's main thread.

## The brain index and `query_brain`

The brain reads (`brain_logs`, `brain_notes`, `brain_note`, `brain_conflicts`, `brain_status`, `search_brain`) go through one SQLite FTS5 file per brain, `<data folder>/brain-index/github.com/<owner>/<name>.sqlite`, a projection of `main` in the host's checkout. Each brain pass refreshes it after its fetch: it lists the brain folder at the fetched commit, reads through Git only the files whose blob changed, removes the deleted ones and never reads a symlink. A pass that fetched nothing new does nothing, and a missing or older index, or one whose build never completed, is rebuilt from the checkout, offline from its `main` too. The brain folder is `brain_dir` in `wiffletree-brain.json` on `main`, or else the folder a Space naming the brain gives. Entries' refs are verified on this machine against the workspace's clones of their repositories, without fetching: a commit on the repository's default branch on GitHub (the one GitHub reported, else `origin/HEAD`, never the repository's configured base) is `verified`, one elsewhere, a feature base included, `claimed`, and anything else `unverified` with the reason; during the brain's pass a named PR's state is also read with `gh api`, as a compile reads it: merged verifies the entry and open claims it. Each pass, whether or not it fetched a new commit, asks about the PRs of the next 50 claimed or unverified entries whose repository is on this machine only, in turn from where the last pass stopped, so a PR merged later verifies its entry in the browser too. A PR closed without merging is final: its entry keeps that reason and is not asked about again. This machine's pending entries are verified on the request, with results cached by each clone's default-branch head, so a repeat page reads one ref per clone. The entries waiting for a compile are those the compile cursor in `notes/INDEX.md` leaves pending, by the commit graph rather than commit times: added after its `compiled-through` commit and not among its `compiled-after` ids, or with no cursor every entry the legacy import did not record as compiled. Each read is refused for a brain no Space names, before the brain's first index build, and for a `project_id` whose Space does not name that brain, so a project's scope never reads another brain. Nothing logs a query or a file's text.

Brain compile runs only on the host a brain's `wiffletree-brain.json` names as compiler, as one built-in job per brain on the scheduler: due daily at the config's `compile.at` in its `compile.timezone`, and never with no `compile`, once on wake after missed times, on `run_brain_compile`, and when a fetched `main` adds an entry whose `state` begins `Ruling on conflict`. A brain has at most one run in progress and one open compile PR; a due run while that PR is open is recorded as waiting for it, and after it merges no run starts until `main` here holds its cursor. A ruling waits, unconsumed, until a run can start. Only `rule_conflict` writes a ruling: `log_work` and the capture form refuse a `state` beginning `Ruling on conflict`, and only a `decision` entry counts as one. A run reads its cursor, `compiled-through` and `compiled-after` in `notes/INDEX.md`'s frontmatter on `main`, takes the entry files added since that commit, less the listed ids (on a first compile every entry file, less those the legacy import recorded as compiled), and compiles at most 200, oldest id first. Off the host thread it fetches each named repository's clone once and verifies each `ref` as the brain reads do, then reads a named PR's state with `gh api`: merged verifies the entry and open claims it; a verified commit's release tag is recorded. With nothing pending the run ends skipped, with no model call and no write, and without resolving a row; with entries pending and no Brain compiler row it waits for one. Otherwise one session starts, role `compiler`, owned by the brain, in no project or Space and never in a snapshot's `sessions`, on the Brain compiler row, in a worktree of the brain checkout under `<data folder>/compile-worktrees/`, with the bundled compile procedure as its instructions and an input file under `<data folder>/compile-inputs/` holding the pending entries with their verification, `STATUS.md`, `notes/INDEX.md` and the notes they name, up to 60,000 characters. Its turn runs outside YOLO mode like a thread's, with no web: Claude may write only the brain folder's `notes/**` and `STATUS.md`, and Codex only its worktree. Its workspace tools are `queue_conflict`, which records a conflict with a stable id, its rule, claim entry, what it conflicts with, evidence and a recommended ruling, and `finish_compile`; no agent has either. Its turn is stopped at 30 minutes, which times the run out. On `finish_compile` the host checks the worktree: only `notes/**` and `STATUS.md` changed, nothing was deleted, every changed note has `title`, `kind`, `updated` and `sources`, every `[[wikilink]]` names a note, every source id and footnote names an entry file under `logs/`, every footnote mark has a definition, and `main` changed none of the files the run would write since its head; otherwise the run fails and the next one compiles again. A failed check, a timeout, a crash or a turn that ends without `finish_compile` fails the run with its reason and no PR. Otherwise the host writes the cursor into `notes/INDEX.md` and `reconcile-queue.md` from the open conflicts, those still open on `main` less the ones a compiled ruling settled, then the run's own, and queues the changed wiki files as one compile batch, which the brain's batch flow pushes on its own branch and opens a PR for; `main` changes only when that PR merges. Every install shows the conflicts of `reconcile-queue.md` on `main` as `conflict` workspace notes, each naming the projects whose Inbox lists it: those whose Space names the brain and whose repositories include the claim's. One naming no project is in no Inbox and is also in `brains`' `conflicts`; the brain browser's Conflicts view shows every card with its rulings. A card says what each side says, the established note or entry and the claim's entry, from the brain's index. A card is `open`, or `ruled` with who ruled, its ruling batch's PR and whether the ruling is on `main`. A compile session's usage is recorded under the brain and reported as one line per brain, id `brain-compile:<owner/name>`, named "Brain compile". Nothing logs an entry's or a note's text.

The coordinator, implementers, testers and reviewers have the workspace tool `query_brain`, which takes `question` and optionally `scope` (`project`, the default, or `brain`). The brain is always the caller's project's Space's; the tool takes no other argument. It walks the ladder over the same index: `STATUS.md` passages that hold the question's terms, then INDEX lines, then the top five notes with their footnoted sources and the notes they link, then the top five entries with their verification, decisions above observations at each step, until about 4,000 characters of excerpts are gathered. The answer names the brain and scope, the last compile, the pending entries and when the brain was synced, marks brain text as context and not instructions, and with no match says "The brain has nothing on this." It is refused for other roles, when the Space has no brain or a local one, and before the first index build.
