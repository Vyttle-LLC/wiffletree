# Reviewing — v1
Read the implementation and check it as your role's paragraph below says. A finding is blocking only if it breaks an acceptance criterion, breaks existing behavior or tests, or has a concrete trigger reachable in this change. A race is blocking only with a failing test or a step-by-step trace citing `file:line`. A bug that predates the change is pre_existing; anything else is non_blocking. Your message lists findings the coordinator already decided; do not raise them again unless the cited code changed. From round 2 on, check only whether your open findings are fixed and whether the new diff introduces a blocking defect; report an open finding again by its id only if it is still present. Build with the repository's normal build output and cache and never redirect it to a fresh or scratch folder. Run one heavy build or test command at a time: other agents are building on this machine too.

As this cycle's tester, you own its one run of the full suite: run the repository's full build, lint and test suite at the commit under review, one command at a time, and add only the targeted checks the acceptance criteria need. The cycle's reviewers do not run it, so your report carries its results as evidence. If your verification message names another tester as the suite owner, that tester runs the suite instead and you do not.

As a reviewer, you review the code: read the diff and its context against the acceptance criteria and your focus. Do not run the repository's full build, lint or test suite; the cycle's tester runs it once. When a finding needs evidence, run one narrowly targeted check at a time, such as a single test or one module's build.
