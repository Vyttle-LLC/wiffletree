A project inherits its Space's repositories

Approved by Michael, October 31, 2026

The rule: a project uses its Space's repositories, always current, plus any you add to that project. Its open tickets keep working wherever they already are.

Today a Space's list is copied once, when New project opens, and the two lists then drift apart. Nothing here runs. Screens 1 to 5 use sample rows; the upgrade table in screen 6 uses the real figures on this Mac.

The upgrade keeps what a project named or has an open ticket in, and drops “every repository”. Everything else comes from the Space. No Space's list changes. Runs once.

How it behaves

  • A repository joins a Space: every project in that Space gets it at once, including when the change arrives from another Mac.
  • A repository leaves a Space: open tickets and their reviews carry on there; new tickets there are allowed until the last open one closes, and then it leaves the project.
  • A repository in no Space: a project reaches it only through Add to this project. On this Mac that is termic and the 8 celadon-theme repositories.
  • A repository in several Spaces: a project reads only its own Space's list, so this needs no rule.
  • A Space entry not cloned here: shown as not cloned here and unusable until it joins the workspace, when it appears by itself.
  • A Space that lists nothing here: the project uses nothing until you add to the Space or the project, and Overview says so.
  • Narrowing goes away. A project cannot use fewer repositories than its Space. It was rarely used: 24 of 26 projects use every repository.
