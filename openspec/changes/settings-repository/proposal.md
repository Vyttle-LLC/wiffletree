## Why

Everything the human has taught Wiffletree about how to work stays on the machine where they taught it: the review levels, the model guide, the check-in thresholds, the PR keeper's triggers and, once change 4 lands, their rules and rewrites for each skill. On a second machine they start again from the defaults, and an edit on one machine never reaches the other.

The human decided on October 12, 2026 that settings can name a settings repository in Git, that it holds edited skills, review levels, the model guide, check-in thresholds and the keeper's triggers, that providers, models, the workspace folder and the approved-owners list stay on each machine, that credentials, the database and conversations never go in, and that sync is fully automatic: pull at launch and periodically, push after each change, and when two machines changed the same file, pause that file, keep the local version working and put a note in the Inbox. On October 13 they described it as one repository, `wiffletree-storage`, for everything Wiffletree keeps, and raised two points to settle before real content goes in: who can read it, and keeping company and personal material apart. This is change 5 of 6 in the plan `plan-pr-keeper-and-skills.md`. It builds on skills (change 4), whose storage was laid out to move here.

## What Changes

- **Shared settings, one folder on every machine.** Skills, the review settings (verifiers, levels and the two caps), the model guide, the check-in thresholds and the PR keeper's triggers move into `<data folder>/shared/`, one file per setting. At the first start of this release they are copied there exactly as saved. The skills folder is moved there unchanged. Everything else stays where it is: providers and allowed models, the PR keeper's model, the workspace folder, the allowed owners, repositories and appearance. Without a settings repository, nothing else changes.
- **A settings repository, named in Settings on each machine.** A new Settings repository section takes a private GitHub repository and says who can read it, including an organization's base permission when GitHub reports it. **Set up** adds Wiffletree's files beside what the repository holds. **Join** makes a second machine use the repository's settings, keeps that machine's old ones in a backup, merges the skill histories, and lists what the machine still needs, such as a PR keeper model. Public repositories are refused. Wiffletree does not create repositories on GitHub.
- **A new kind of push, with its own permission.** Choosing the repository on a machine is what allows Wiffletree to push setting changes to it. The allowed owners for pull requests neither grant this nor are needed for it. Sync pushes only the repository's default branch, only commits on top of the remote head, never by force, to the recorded URL, and only Wiffletree's own files. No agent tool touches the shared folder.
- **Fully automatic sync.** Pull at launch, every 5 minutes and on **Sync now**. Push 5 seconds after the last change. Pulled changes apply where each setting is next read, such as each agent's next turn for skills. Offline, changes wait and this machine keeps using them.
- **A file changed on two machines pauses.** Files are compared whole. A file both machines changed differently stops syncing. This machine keeps using its own version, every other file keeps syncing, and a workspace note in the Inbox offers Compare, Keep this Mac's and Use the other machine's. The version not kept stays in Git's history.
- **A file changed outside Wiffletree pauses too**, so an edit made in an editor or by an agent's shell does not reach every machine's agents unseen. This settles change 4's open question 10.
- **What a machine cannot use is held, not refused.** A pulled file this machine cannot read is not applied. A newer format stops sync until an update. Keeper triggers that need a model this machine lacks are off here, and the page says why.
- **Sync status** in the Settings section, with the last sync, what moved, the last error and the paused files, and a small mark in the sidebar footer.
- **Not included:** second-brain logs, tickets or anything else in the repository (the layout leaves `logs/` and `tickets/` free); merging two machines' edits of one file; sharing between people; repositories outside GitHub or public ones; creating repositories or changing who can read them; merging stock updates into a rewrite (change 6).

### New Capabilities
- `settings-repository`: which settings are shared and which stay; the shared folder; choosing, setting up and joining a repository; what sync may push and how that relates to the allowed owners; when sync runs; how files merge; paused files from two machines, from outside edits and from what this machine cannot use; sync status; stopping; the documented limits.

- `native-workspace`: "Check-in thresholds in Settings" names the shared file in its hand-edited scenario.

- `skills` (change 4, once its slice 2 has synced them): "Skills are stored in a folder that can move" names the shared folder, and "Every skill has a history" writes a "New stock version" entry only for a newer stock version.

## Decided questions

The human approved the recommended answer to each question on October 16, 2026.

1. **One repository for everything, or one per company?** The human sees this as one repository, `wiffletree-storage`, for settings, skills, second-brain logs and later tickets. Their machine layout keeps company and personal material apart ("Vyttle IP only in vyttle-docs, work IP only in sagehaven-docs"), and each machine is personal plus exactly one company: this one is `sage`, a personal laptop is `vyttle`. Wiffletree is a Vyttle-LLC project, and on this machine it also runs Sage-Social and personal repositories, so logs of this machine's work would hold all three. Decided: (a) settings and skills, all this change syncs, go in a private repository under the human's own GitHub account, such as `MHohlios/wiffletree-storage`, shared by every machine. Company material, such as logs and tickets, goes later into one repository per company, chosen by the owner of the project's repositories rather than by the machine's profile, and is decided when that change is proposed. Not chosen: (b) one repository per company, chosen by the machine's profile, as the plan suggests: the two laptops would then share no settings, and this machine's Vyttle and personal work would still be logged in the Sage one; (c) one repository for everything in Sage-Social, as now: simplest, and it crosses the line. *Why (a):* settings and skills are how the human works, like `personal-brain`, which is the one brain on both machines. They hold no company's work, provided company-specific rules stay in each repository's own instructions, which agents already read. Choosing by project rather than by machine is the only split that keeps this machine's mixed work apart.
2. **Who can read the repository?** Sage-Social's base permission for members is Read, so every member can read `Sage-Social/wiffletree-storage`, and organization owners can write it. Writing it changes every machine's agents' instructions. Decided: (a) as in question 1, use a repository under the human's own account, where only they and people they invite can read or write it, and leave `Sage-Social/wiffletree-storage` unused for now; Wiffletree shows who can read any repository before it is chosen. Not chosen: (b) keep the Sage-Social repository and accept that members can read the human's settings and skills, which hold no credentials; (c) ask a Sage-Social owner to set the base permission to No permission and grant access by team, which changes access to every Sage-Social repository for every member. *Why (a):* it needs no change to the organization, and it limits who can change the agents' instructions to the human.
3. **Does choosing the repository allow pushes to it, or must its owner be allowed too?** Decided: (a) choosing it on a machine, with a confirmation that names the repository, its branch and who can read it, is the permission. The allowed owners neither grant it nor are needed. Not chosen: (b) also require the repository's owner to be on the allowed list; (c) ask in the Inbox before each push. *Why (a):* the allowed owners are about opening pull requests in code repositories; a settings push is a different act on one repository the human named. (b) would make allowing an owner for pull requests mean two things, and (c) defeats the fully automatic sync the human chose.
4. **Where does the note about a paused file go?** Inbox items belong to a project today, and a paused setting belongs to none. Decided: (a) one workspace note, shown at the top of every project's Inbox with a "Workspace" label and counted in each, settled once for all of them; the sidebar's sync mark and the Settings section show it too. Not chosen: (b) no Inbox note, only the sync mark and the Settings section; (c) a new Inbox for the whole workspace, opened from the sidebar. *Why (a):* the human asked for a note in the Inbox, and it should be seen whichever project they are in.
5. **When a second machine joins, whose settings win?** Decided: (a) the repository's; this machine's shared folder is kept in `backups/`, its skill history entries are added to the repository's, and **Replace the repository's settings with this Mac's** is offered, asking first. Not chosen: (b) choose per setting while joining; (c) this machine's win. *Why (a):* the repository holds what the human has been using, and a new machine usually has defaults. Nothing is lost either way.
6. **How often does sync pull?** Decided: (a) at launch, every 5 minutes, and on **Sync now**; push 5 seconds after the last change. Not chosen: (b) every minute; (c) every 15 minutes; (d) also whenever the app comes to the front. *Why (a):* settings change rarely, a pull is one `git fetch`, and Sync now covers the moment it matters.
7. **Edits made outside Wiffletree.** Change 4 left this here. Decided: (a) pause the file with a note offering **Sync this version** or **Put back the synced version**. Not chosen: (b) sync whatever the folder holds; (c) put back the synced version without asking. *Why (a):* a skill is part of every agent's instructions on every machine, so an edit made by an agent's shell or a script should not spread unseen, and a hand edit by the human should not be thrown away.
8. **Order against the skills build.** Slice 1 moves `SkillStore`'s root, which skills slice 2 adds. Slice 4 changes when skills slice 2 writes "New stock version" entries, pauses a skill's `rewrite.md` and `base.md` with its rules, and completes "Every skill has a history", whose restoring of a rewrite skills slice 5 adds. Decided: (a) start slice 1 after skills slice 2 merges and slice 4 after skills slice 5 merges, and run the other slices alongside skills slices 3 to 6. Not chosen: (b) start after all of skills merges; (c) start slice 1 now and move the skills folder when it exists. *Why (a):* each slice waits only for what it changes.
