## Context

Wiffletree already runs sessions the provider holds to what they are given: assistant threads, job runs and brain compiles (`provider/restricted.rs`). Each is a session with a role, a pinned model and a restricted launch, and the scheduler runs its turns, records its steps and waits at a usage limit. A brain compile shows how to keep such a session out of every project's agent tree: its session has no project and no parent, and a run record ties it to what owns it.

## Goals / Non-Goals

**Goals:** a coordinator starts a blind evaluator on an exact model and is woken when it ends; the human decides per project whether evaluators may use the screen; nothing the evaluator reads, writes or says reaches the coordinator except through the run folder.

**Non-Goals:** messaging a running evaluator; an editable deny-list of apps; evaluators on a paired remote Mac; any change to Who runs what.

## Decisions

### A run is a session outside the agent tree, with its own record

An evaluator run is an `evaluations` row: id, project, the coordinator that started it, provider, model, effort, mode, folder, state, reason and times. When it starts it gets a session of role `evaluator` with no project, no parent and no repository, as a compile does. That keeps it out of `workspace_context`'s team, the Agents panel's ticket tree, check-ins and `send_message`, which would otherwise hand its replies to the coordinator. The session gives it the scheduler's turn, steps, transcript and usage-limit wait for free. Each run gets a new session, so there is no history to resume across runs.

The session is archived when the run ends, so nothing can start another turn in it. A run whose turn a crash, kill or long quit cut short is ended as failed when the host next starts, "Wiffletree stopped during the run.", and its coordinator is told, as job runs are ended. A run still waiting to deliver its prompt, or waiting for its limit's reset, goes on.

### Isolation is the provider's, as for threads

Claude runs as `-p` with stream-json, `--setting-sources ""`, `--strict-mcp-config` with no server but its driver (`app` or `desktop`), `dontAsk`, `--tools Read,Glob,Grep,Write,Edit`, allow rules scoped to `//<folder>/**`, writes to `~/.claude` denied and auto memory off. No system prompt is appended. Its start is checked as a thread's is: any other tool, any MCP server but its driver, another permission mode or auto memory stops the run. On this Mac (Claude Code 2.1.317) such a run could not read `/etc/hosts` or write `/tmp`, and received no CLAUDE.md.

Codex runs `exec --json --ignore-user-config --ignore-rules` in a workspace-write sandbox rooted at the folder, with no network, no temporary folders, web search disabled, the threads' features off and also `shell_tool`, `unified_exec`, `view_image`, which reads any path, and `image_generation`. Its code mode then has only `apply_patch`, which the sandbox holds to the folder. A run's only MCP server is its driver, `app` for an app run and `desktop` for a full-desktop run; any other MCP call stops the run. No developer instructions are given.

`--ignore-user-config` does not keep `~/.codex/AGENTS.md` out: a probe on Codex 0.160.0 received it. So an evaluator's Codex gets its own `CODEX_HOME` in Wiffletree's data folder, holding only a link to the user's `auth.json`, so sign-in and token refreshes still use the user's one file. The probe with that home received no AGENTS.md.

A separate `CODEX_HOME` still lets Codex find the human's skills under `~/.agents/skills`. A request captured by a local endpoint carried them in its skills catalog, and neither `skip_host_skill_discovery` nor turning off `skill_search` removed them. So the evaluator's Codex also runs with an empty `HOME` of its own, beside its Codex home. Only Codex's bundled system skills (imagegen, openai-docs, skill-creator, skill-installer) remain, as Claude keeps its built-in ones.

The link holds only because Codex rewrites `auth.json` in place. A probe on 0.160.0 confirmed it with a throwaway home: a fake, stale `auth.json` reached through a link, and `CODEX_REFRESH_TOKEN_URL_OVERRIDE` pointing at a local server. Codex refreshed, the refreshed token landed in the link's target with the same inode, and the link stayed a link. The home holds no lock for the ChatGPT token refresh, so two homes share nothing that one home would not.

The environment is cleared and only `HOME`, `USER`, `LOGNAME`, `PATH`, `SHELL`, `TMPDIR`, `LANG` and the `LC_*` locale variables are passed on, so no `WORKSPACE_TOKEN`, `WORKSPACE_SOCKET` or other variable of Wiffletree's or the human's sessions reaches the run or anything it starts.

### The model is checked, pinned and never replaced

`start_evaluation` refuses a provider this Mac has not found signed in, a model the provider's CLI did not list, full IDs such as `claude-opus-5-5` and aliases such as `opus` alike, and an effort the model does not offer. Until the CLI's list has been read, a run is refused with that reason and the service reads the list, so the call succeeds when repeated; Wiffletree never checks against a guess. The profile is pinned on the run's session as given; Who runs what is never consulted.

An alias can move to a newer model without notice, so the run records the model the provider names: Claude's in its start record, Codex's in the `turn_context` of the session record in the evaluator's Codex home, since its JSON stream names none. A run started on a full ID whose provider names another model fails at once, with the reason for the human. A run on an alias records which model it got. The coordinator may see the reported model in `list_evaluations` and the end message. A run whose provider is past its limit when it starts is marked waiting and its turn is held until the reset, as any pinned agent's is. A turn that fails at a limit is retried in the same session at the reset, and the run shows waiting meanwhile.

### Authorization is the human's, on an Inbox card

Each project has an evaluator permission: none yet, off, app or desktop. The first `start_evaluation` in a project with none raises one Inbox card, `evaluators:<project>`, offering App only, Full desktop and Not in this project, and holds the run as waiting. Answering sets the permission and admits or stops the held runs; any other answer is refused, and leaving the card is "Ask me later". `Command::SetEvaluatorPermission` lets the human change it later; it is human-only, and no tool sets it. Archiving a project's coordinator, which is how a project closes, sets it to off and stops the project's runs.

A run's mode must be allowed: desktop needs desktop, app needs app or desktop.

### One screen, one queue, and the human's Start

App-only runs start as soon as they are admitted. A desktop run needs the screen lock, which one run holds at a time across every project; the others stay queued, oldest first. The run at the front takes the lock (`holds_screen`) and waits, with no session yet, on an Inbox card of its coordinator's project, `evaluation:start:<run>`: "Ready to use your screen", naming the run, its model and its apps, with Start now, Later and Skip these runs. Nothing touches the screen without Start now, which gives the run its session; when the provider is at its usage limit, Start now is refused with the reset time and the card stays. Later leaves the card and the run first in line. Skip these runs stops the run and the project's desktop runs queued after it, "Skipped by you.", and each coordinator is told as for any end. The card cannot be dismissed, since that would strand the lock. A run that ends any other way while it waits closes its card, and the lock passes to the next run, which raises its own card.

A desktop run whose turn reaches its provider's usage limit ends as failed instead of waiting: a retry after the reset would take the screen without a fresh Start, perhaps hours later while the human works.

### Full desktop runs through Wiffletree's own driver, in a helper app

The spike (branch `wiffletree/spike-headless-desktop-computer-use-for-claude-a`, `docs/computer-use-spike.md`) found that neither provider's computer use works when Wiffletree launches it. Claude Code 2.1.317 sets it up only in interactive sessions. Codex's Sky service bootstraps with an Apple event that `tccd` charges to the hardened `wiffletree-host` and denies. It also found that macOS charges Screen Recording and Accessibility to a process's responsible process, which for everything an agent starts is `wiffletree-host`; a bundle opened through LaunchServices is its own responsible process, and its grants register under its own bundle ID. The human is removing `wiffletree-host`'s Screen Recording grant, so nothing relies on it.

So a desktop run drives the screen through **Wiffletree Evaluator**, which Wiffletree ships as `Contents/Helpers/Wiffletree Evaluator.app` in its bundle: bundle ID `com.vyttle.wiffletree.evaluator`, `LSUIElement`, the hardened runtime, signed by `scripts/package_macos.sh` with the app's identity, before the app, so a release's Developer ID signature keeps its grants across updates. The release workflow needs no change. An ad-hoc development build's signature changes with every build, so its grants do not survive one; `docs/DEVELOPMENT.md` says how to sign it with a stable identity.

Before the provider starts, the turn opens the helper with `open -n -g <helper> --args serve <socket> <run> <bundle id>…` on `$TMPDIR/wiffletree-<run>-desktop.sock` and opens the run's control connection. The helper creates the socket with mode 600, answers with its process ID and its own grants, read in-process with `CGPreflightScreenCaptureAccess` and `AXIsProcessTrusted`, and whether its Esc listener is in place. A missing grant fails the run before anything touches the screen, naming the System Settings pane to open. The helper quits when the control connection closes, and on its own after 30 seconds without one; the host kills it if it is still there three seconds after the turn ends.

Runs never start the shipped helper in place. The live check on November 23, 2026 found that macOS charges Screen Recording to the outermost bundle: from inside `Wiffletree.app`, the helper's Screen Recording request and checks were made for `com.vyttle.wiffletree` (`tccd`: `AUTHREQ_SUBJECT: subject=com.vyttle.wiffletree`, then "does not allow prompting; returning denied" against the installed Wiffletree's record), while its Accessibility ones were made for `com.vyttle.wiffletree.evaluator`. Its own Screen Recording grant could never apply, and the only grant that would work is Wiffletree's. So `wiffletree-host serve` installs the shipped helper, from the bundle `--app` names or the one it runs from, as `<data folder>/evaluator/Wiffletree Evaluator.app` with `ditto`, replacing a copy whose executable, `Info.plist` or sealed resources differ, and runs start that copy, its own outermost bundle; there `tccd` names `com.vyttle.wiffletree.evaluator` for both services. Grants follow the bundle ID and signature, so an update signed by the same team keeps them. `WORKSPACE_EVALUATOR_APP` names another helper, for development. Granting by hand needs the copy too: System Settings' + picker opens an `.app` rather than entering it, so it cannot reach a helper inside `Wiffletree.app/Contents/Helpers`, and a grant given to that path would be checked as Wiffletree anyway. Settings › Screen control (ticket 5) therefore runs `request` on the installed copy, and its manual route reveals that copy in Finder for the + picker; a copy of the helper elsewhere with the same bundle ID and designated requirement should receive the same grant, which the live check confirms or refutes.

The helper's `request` mode asks for both grants and stays until both are on, or two minutes pass: the human's first `request` exited 35 ms after asking, too soon to answer a prompt for it. Its `check` mode prints the grants without asking.

The provider's one MCP server is the desktop driver, `wiffletree-host desktop-driver-mcp <socket> <run folder>`, named `desktop`, for Claude and Codex alike, with the same start and tool-call checks as the app driver. Its tools are screenshot, click, double_click, right_click, move, type_text, key, scroll, drag, open_app and list_windows, in screen points from the main display's top-left corner. Each is one request on the helper's socket, answered as the automation socket answers. Screenshots are saved inside the run folder by the app driver's rules, never following a link, and report their scale and the display's frame in points. Codex keeps `--ignore-user-config`, so the human's `notify` hook never runs, and `computer_use` stays disabled; Claude is never offered its `computer-use` server.

### The helper, not the model, holds the run to its apps

A desktop run names its apps, one to ten bundle IDs, and no target. Nothing is allowed that the coordinator does not name, and the helper itself never is; the Start card calls out Wiffletree, terminals, System Settings and Finder when they are named. The helper decides each request from what is on the screen at that moment, with pure functions it tests without a screen:

- A screenshot captures each allowed window on its own, with a ScreenCaptureKit filter for that one window, and draws it into a white image of the main display at its frame from the window list, back to front. No other app's window is ever captured, and a pixel divided by the scale is the screen point `list_windows` and the input checks use. (A display filter that included the allowed apps drew Calculator at the image's top left at twice its size on the live check, so its screenshots could not be used to aim.)
- A click, move, scroll or drag goes through only when the topmost on-screen window at the point, at any layer, belongs to an allowed app, so a notification or menu of another app over it refuses the input; a drag checks both ends. Another app's name is never given back.
- Keys and text go through only while an allowed app is frontmost, checked again before every piece of typed text, and are posted to that app's process alone, so no global shortcut such as Spotlight's receives them.
- open_app opens only an allowed app, and waits up to five seconds for it to come to the front, since Stage Manager shows an app in the background only as a thumbnail in its strip; list_windows lists only theirs.

The helper shows "Evaluator using this Mac" in the menu bar, with Stop, for the whole run. A listen-only event tap hears Esc anywhere; the helper's own posted events carry a mark the tap ignores. Either reports on the control connection, after which the helper refuses every request. The host's reader sets the turn's cancel flag at once and the turn tells the service why, so the run ends as stopped, "Stopped: you pressed Esc." or "Stopped from the menu bar.", as `stop_evaluation` ends it. A helper that quits during the run stops it the same way. Windows of other processes, such as the system's open and save panels, are not the app's and stay out of reach.

### An app run drives its own test copy

An app run names its target: the executable, its arguments, which must give a test data folder of its own with `--data-dir`, and the variables it needs. The coordinator creates the data folder first: Wiffletree refuses one that does not exist, canonicalizes it so links and `..` cannot hide an overlap, and refuses one that overlaps its own or the default data folder or that another unended run uses. It also refuses more than one `--data-dir`, the `--data-dir=<path>` spelling, `--automation-socket` among the arguments, and any `WORKSPACE_*` variable but the provider stubs or any `*_TOKEN` variable.

The copy lives for a turn. Before the provider starts, the turn's thread starts the copy with `--automation-socket` on `$TMPDIR/wiffletree-<run>.sock`, in its own process group, from the evaluator's cleared environment plus the target's variables, with a given `PATH` placed before the host's and `WORKSPACE_SKIP_LOGIN_ENV=1`, which keeps the copy's host from adopting the login shell's `PATH`. It waits up to 90 seconds for the socket to answer `window`; a copy that exits or never answers fails the turn, and so the run, with that reason. Whichever way the turn ends, the copy's group and the group of every process it started get SIGTERM, then SIGKILL after five seconds, and the socket is removed. A run waiting at its usage limit has no copy running; the retry starts a new one on the same data folder. The copy's output goes to `evaluators/logs/<run>.log` in Wiffletree's data folder, for the human.

The driver is `wiffletree-host app-driver-mcp <socket> <run folder>`, the run's only MCP server, named `app`. Claude gets it through `--mcp-config` and allow rules for its eleven tools; its start must show exactly that server connected and no other tool. Codex gets it through `-c mcp_servers.app` with `enabled_tools`, and any other MCP call stops the run. Each tool is one or a few socket steps, in window points from the top-left corner. Screenshots are saved as PNG under a relative name inside the run folder and returned as an image with its pixel size and the window's scale. Claude downsizes an image over 2000 pixels on its long edge before the model sees it, so the tool tells the model to sample pixels from a points shot, or a native shot of a window small enough, rather than a native shot of a large window.

The app captures its own window with `CGWindowListCreateImage` on its own window number, at nominal (one pixel per point) or best (native) resolution, drawn into an sRGB bitmap. macOS lets an app capture its own windows without Screen Recording permission. Measured on macOS 27.0.1: launched through `responsibility_spawnattrs_setdisclaim`, so it was its own responsible process and `CGPreflightScreenCaptureAccess` returned false, the app returned its window at 1280×820 and 2560×1640, while `screencapture -l` on the same window failed with "could not create image from window".

### The coordinator hears only the outcome

When a run ends, Wiffletree messages its coordinator: `Run <id> <state> · model <model> · folder <folder> · <duration>`, naming the model the provider reported, or the one asked for when none was. `list_evaluations` gives state, mode, the model asked for and the one reported, folder and times, and a waiting run's reset time. A failure's reason is shown to the human only, since a provider's error can quote the model's text.

### Live check, November 23, 2026

On this Mac (macOS 27, one 3008×1692-point display at 2×, Stage Manager on), with the helper signed by an Apple Development identity and granted Screen Recording and Accessibility, through a development host on its own data folder and only Calculator allowed:

- **Grants.** The installed copy's `check` read both grants; replacing it with a new build signed the same way kept them.
- **The Start gate.** Each run held the screen behind its card and started only when the human pressed Start now; the next run raised its own card when the one before ended. A run parked behind its card survived restarts of the app and host.
- **Calculator only.** Every screenshot showed Calculator and nothing else. Every click outside Calculator's windows was refused, as were keys while Calculator was not frontmost; nothing else was touched.
- **Keys and clicks reached Calculator.** Typed text and a click aimed from a screenshot changed Calculator as expected, for Claude and for Codex.
- **Screenshots match the screen**, once captured window by window (above): Calculator appeared at its `list_windows` frame, and a click on its "7" key from the image pressed 7.
- **Cleanup.** After every run the helper had quit, and pgrep found no helper.
- **Esc stops a run at once.** In a second round with the helper's log lines, the human pressed Esc in three runs. Each time the helper logged "Esc heard: stopping the run", the run ended as stopped, "Stopped: you pressed Esc.", and the helper logged its control connection closing and quit 0.2 to 1.1 seconds after the key. In the first round three runs had ended on their own before the human pressed anything.
- **A host that quits takes the helper with it.** A run whose app and host were quit mid-turn ended as failed, "Wiffletree quit during a turn", and its helper quit 2.4 seconds after it started.
- **Not observed: the menu bar's Stop.** It was offered in the last three runs, and each time the human stopped the run with Esc instead. It reports on the same control connection, through the same `Control::stop` as Esc, which the protocol tests cover; only the menu item's action itself is unexercised.
