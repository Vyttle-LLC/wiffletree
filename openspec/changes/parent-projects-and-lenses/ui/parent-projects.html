Design study · parent projects

Big projects own their spin-offs

Today a project that creates another project loses track of it. In this study the project that creates it becomes its parent. The new project becomes a child, nested under the parent. The two can message each other, and you can still open a child and talk to it directly. A child's questions go to its parent first, so the parent only brings you what it can't settle. Agents moves from the header to the right rail, next to Tickets, where agents are out of the way until you want them. A Needs you page lists everything waiting on you across all Spaces. New pieces have a dashed outline. Its projects, tickets and messages are invented Celadon samples.

Part 3

Talking to a child directly

A child is a full project with its own coordinator, tickets and agents. Selecting it opens its chat. The header names the parent, and you can click it to go back. Messages from the parent show up in the child's chat, labelled. When you message the child yourself, the parent sees a one-line note, so it doesn't contradict you.

How it behaves
  • Spin-offs become children. When a coordinator creates a project, the new project is its child. The parent's chat gets the child's reports. Either one can message the other with send_message, the same way a coordinator and its implementer talk today.
  • One level only. A child can't have children of its own. If a child needs to spin off work, it asks its parent, and the new project becomes a sibling under the same parent. That keeps the sidebar to two levels.
  • The parent fields questions. A child's ask_user goes to its parent first. The parent either answers it, citing the brain or an earlier decision you made, or passes it to you, labelled with the child's name. Product, security, and approval questions always reach you.
  • You can always talk to a child. When you do, the parent gets a one-line note saying what you decided.
  • Coordinators stop sprawling. A coordinator's first choice is to add a ticket to its own project. It creates a child only for a separate outcome: a different repository set, a different reviewer, or work that would make the parent wait.
  • You can build the tree by hand. New project gets a Parent field, and a project's menu gets "Move under…" so you can file an existing project under a parent. "Make this a parent" turns a first-word group like Chrome into a parent project with its own coordinator.
  • Closing. A parent can't be closed while it has open children. Closing a parent is still your decision. A parent can only propose it on Needs you.
  • Agents moves to the right rail for every project, parent or not. Its badge counts working agents. The header's "N working" button is removed.
Open questions for you
  • Folders become parents? I'd keep first-word groups for loose projects. I'd offer "Make this a parent" on a group, but never convert one automatically.
  • Questions routed through the parent: should the inbox show a child's question as soon as it's asked, faded until the parent passes it on? Or only once the parent passes it to you? I'd go with only once passed on, to keep the inbox quiet.
  • Needs you as the home screen: should it open when the app starts, instead of the last project?
