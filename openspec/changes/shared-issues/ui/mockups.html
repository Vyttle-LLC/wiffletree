Study · shared issues

Issues your whole team can see

Issues are the shared backlog: ideas, bugs and requests anyone on the team can file and discuss. They live as Markdown files in a private tracker repository, which Wiffletree keeps in sync on every member's Mac. When someone starts work on an issue, it becomes a project, and that project's tickets stay on their own Mac just as they do today. The issue shows who is working on it and closes itself when the pull requests merge.

Sample data is simulated. Nothing here is implemented host behavior or a real Git operation.

Issues is a workspace page, not a project. It sits beside Repositories and Usage because it spans every project and every member of the team. The orange dot marks an issue that changed since you last looked. "In progress" is filled in automatically: it names who started a project from the issue, which project, and its tickets or PRs. The footer names the tracker repository and when it last synced. States are Triage, Backlog, Todo, In progress, In review, Done and Canceled. In review and Done follow the linked PRs.

The issue page is the discussion. Comments, state changes and the assistant's notes share one timeline, and each change is one commit in the tracker. Start project from issue creates a coordinator whose first message is the issue, and links them. From then on the Work box lists the project, its tickets and PRs. The issue assistant is not a coordinator. It opens on one issue, or on the whole list from "Ask the assistant". It can read issues and search repositories read-only, and it can propose edits, comments, splits and duplicate links. It has no worktree, starts no agents and creates no tickets. Every write is a proposal you apply. Its comments say whose assistant wrote them.

IDs are handed out when the issue reaches the tracker. If two people file at once, the second push is rejected, so Wiffletree fetches, takes the next number and pushes again. Offline, the issue shows a temporary ID until it syncs. The Inbox shows issues assigned to you, mentions, comments on issues you follow, and new urgent issues in your repositories. A conflict pauses only the field that clashed, the way a paused setting does today. Comments are separate files, so they never conflict.
